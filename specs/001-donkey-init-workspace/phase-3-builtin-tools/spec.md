- Q: 网络工具 `fetch_url` 要不要限制它能请求的地址范围？（该工具由 `donkey init` 默认安装、模型可直接调用；不设边界时它可指向本机回环地址、私有网段乃至云主机元数据服务 —— 那条路径往往直连着云凭据，与"读用户自己工作区里的文件"不是同一特权域。）→ A: **完全不限制** —— 协议与地址一律放行，白名单**由用户自管**；这与既有的"路径白名单由用户自管"完全同构（宪法 §2.1：权限交互 / 路径白名单属引擎层能力，材料层只提供能力、不划边界，v1 不承诺）。配套两条强制项：① 网络工具的说明文字 **MUST 显式写明**"不限制协议与地址范围"这一事实及其后果（可读取本机文件 / 可访问内网服务与云主机元数据地址），使用户知情；② 该事实 MUST 作为**已知且被接受的风险**登记进 spec 的风险条目，MUST NOT 以"默认安全"为由省略，也 MUST NOT 被实现成任何隐式限制（黑名单 / 白名单 / 代理 / 沙箱）。
  > **⚠️ 本条已被下一条（Q4 · 读取侧体积与网络侧边界的"完全照搬 OpenCode"决策）覆盖** —— 保留本条仅为记录决策演进：最终口径以 Q4 为准（网络侧**限协议 + 限响应体体积**，详见 FR-089 / FR-090）。
- Q: 读取类工具要不要限制单次读取的体积？（`read_file` 原为"整份读取、无上限"，而同一份设计里差异文本有 64 KiB 上限、旧正文有 256 KiB 上限，三者口径不一致。）→ A: **完全照搬 OpenCode**（用户明确要求先调研 OpenCode 的实际做法再定）—— **读取侧与网络侧都照搬**，OpenCode 的边界即 donkey 的边界。上游依据：`anomalyco/opencode` 分支 `dev` 的 `packages/core/src/tool/read-filesystem.ts` / `plugin/read.ts` / `plugin/webfetch.ts` / `tool/http-body.ts`。
  - **读取侧（照搬 OpenCode 的四个关键设计）**：① **双上限** —— 单次最多 **2000 行**（`MAX_READ_LINES`）且最多 **50 KiB**（`MAX_READ_BYTES`），先到者生效（行数上限挡"行短但极多"，字节上限挡"行少但极长"）；② **单行上限 2000 字符**（`MAX_LINE_LENGTH`），超出 MUST 截断并附显式标记 `... (line truncated to 2000 chars)`（截断 MUST 留痕，模型不得把截断当完整内容）；③ **续读指针** —— 截断时 MUST 返回下一段起始行号，并在给模型的文本末尾附 `[Output truncated. Continue reading with offset: N]`（模型拿到的是**怎么继续**，不是一句"内容太长"）；④ **二进制不进上下文** —— 内容含 NUL 字节 MUST 明确报错，MUST NOT 把乱码塞给模型。
  - **读取侧呈现格式（照搬）**：返回文本 MUST 带页范围说明头（`Read file {path}, lines {start}-{end}`）、每行 MUST 带 `<行号>: ` 前缀；小文件（≤50 KiB 且未指定偏移 / 行数）走整份返回，超大文件或显式指定偏移 / 行数时走分页。
  - **网络侧（照搬 OpenCode 的边界）**：① **协议白名单** —— MUST 只允许 http/https（OpenCode 的协议校验），其它协议 MUST 报错；② **响应体上限 5 MiB**（OpenCode 的 `MAX_RESPONSE_BYTES = MAX_MARKDOWN_BYTES = 5 * 1024 * 1024`）—— MUST 先看 `Content-Length` 声明、再在流式读取过程中守住上限，超限 MUST 报错；③ **非文本 MIME MUST 拒绝**；④ **非 2xx MUST 报错**，MUST NOT 返回正文。
  - **有意的三处偏离（登记在案，不照搬）**：① `list_dir` 的返回类型 `list[str]` 被源提示词明确冻结 → MUST NOT 改为 JSON，故其分页上限与续读指引改由 `read_file` 的目录分支 + 工具说明文字承载；② OpenCode 把图片 / PDF 作为**多模态附件**返回，donkey 的工具函数只能返回文本 → 媒体文件 MUST 明确报错（多模态附件属引擎层能力）；③ OpenCode 默认把 HTML 转成 Markdown（需给工作区引入 HTML 解析依赖） → donkey 保持返回原始正文。
  - **连带修订**：FR-089 / FR-090 由"不限制协议与地址"**改写**为"照搬 OpenCode 的协议白名单与体积上限"；Q3 的"完全不限制"随之被覆盖；源提示词 §4.8 单测 `test_filesystem_read_write` 的"内容一致"期望 MUST 改为"**去掉呈现文本的包装后内容一致**"（因 `read_file` 的返回值不再是纯正文）。
- Q: OpenCode 的命令工具在输出过大时会把**完整输出存成一个文件**、只返回截断预览并把文件位置告诉模型；donkey 是材料层，没有 OpenCode 那个"会话输出目录"，完整输出该往哪儿放？（补充调研结论：OpenCode 的截断由**引擎层**的统一服务 `packages/core/src/tool-output.ts` 施加 —— `MAX_LINES = 2000` / `MAX_BYTES = 50 * 1024` 对**所有工具输出**统一生效（read 与 shell 共用同一组常量），截断时把全文写入全局数据目录下的 `tool-output/` 并保留 7 天，标记为 `[showing lines 1-N of M; full output saved to {file}]`。）→ A: **截断 + 不落盘** —— 照搬 OpenCode 的**截断**与**标记**行为，但**不**照搬"全文存文件"：① 材料层 MUST NOT 把完整输出写入用户工作区或任何引擎层目录（那是引擎层的全局数据目录 + 保留策略的职责，donkey v1 无该机制）；② 输出捕获文件若进变更记录，会污染"改用户文件的工具"这一语义（`run_shell` 本身不是改文件工具）；③ 完整输出 MUST **不落盘**，改由模型自行改跑更窄的命令取剩余部分（donkey 的命令是显式参数数组，不经命令解释器，故"用管道筛"不可行，但改跑 `tail` / 分页类程序可行）。另**重大事实校正**：OpenCode 的 2000 行 / 50 KiB 是**对所有工具输出统一施加**的上限，donkey MUST 照搬这一"统一口径"（读取侧与命令输出侧共用同一组数值，MUST NOT 各设一套）。

## User Scenarios & Testing *(mandatory)*

> 本 Phase 的 **15** 个 User Story 与验收脚本 `tests/e2e/phase/verify_phase_f001_p3.py` 的 **15 个功能场景**（§6.1 ~ §6.15）**一一对应**（故事 US N ↔ 场景 N）。
> **术语定名**：本 spec 中「验收场景」专指 Given/When/Then 验收场景；验收脚本的 `test_scenario_*` 一律称「e2e 黑盒场景」。引用本 spec 的 Given/When/Then 场景时 MUST 显式写作「spec USx 的 Given/When/Then 场景 N」。
> **另有一项非场景的强制退出条件**：CI 工作流文件交付检查（提示词 §6.16 / 本 spec FR-065 / SC-001）—— 它不是用户故事。
> 全部故事共享同一前提：**F001-P1 与 F001-P2 已就绪**（路径解析 + 权限校验 + workspace 骨架模板）；本 Phase 在其之上交付**工具与契约**。

### User Story 1 - 一次 init 得到可用的内置工具与契约库 (Priority: P1)

用户敲下 `donkey init /path/to/ws`，期望该目录立刻变成一个"手上有工具"的智能体工作区：文件工具、命令工具、网络工具齐备，还有一份全体改文件工具共用的变更记录契约库。用户**不需要**再手工写任何一行工具代码。

**Why this priority**: 这是本 Phase 唯一不可替代的价值 —— "把 workspace 从模板骨架变成能干活的工作区"。没有它，`donkey init` 交付的仍是一堆只会读不会动的文档。

**Independent Test**: 可独立验证 —— 对一个新路径执行 `donkey init`，命令以成功状态结束（退出码 `0`），且目标目录的 `tools/` 下出现 3 个内置工具文件、契约库文件、包初始化文件与工具开发规范文档。

**Acceptance Scenarios**:

1. **Given** 一个尚不存在、但父目录已存在的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，目标目录 `tools/` 下存在 `__init__.py` / `changes.py` / `filesystem.py` / `commandline.py` / `webfetch.py` / `README.md` **6** 个文件。
2. **Given** 同一个目标路径，**When** 用户查看工具清单，**Then** 工具清单条目总数为 **54** 条、其中文件型条目 **48** 条、目录型条目 **6** 条，且磁盘上实际存在的目录为 **10** 个。

### User Story 2 - 工具能被真的导入并用起来 (Priority: P2)

用户不满足于"文件在磁盘上"—— 他要确认这些工具**能被加载、能被调用、说明文字完整**。因为工具的说明文字就是模型理解它们的唯一依据。

**Why this priority**: 文件存在 ≠ 工具可用。一个导入即崩的 workspace 比没有工具更糟糕；而缺说明文字的工具等于模型看不见的工具。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在一个**独立进程**中导入 9 个工具函数并读取各自说明文字的长度。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户在独立子进程中导入 `read_file` / `write_file` / `copy_file` / `move_file` / `delete_file` / `list_dir` / `stat` / `run_shell` / `fetch_url`，**Then** 导入全部成功、每个函数的说明文字长度均大于 20 个字符。
2. **Given** 同一个 workspace，**When** 用户导入契约库，**Then** 契约库可被导入且**不含**任何工具函数（它是被复用的契约底座，不是可直接调用的工具）。

### User Story 3 - 命令工具能在新进程里跑并回报结果 (Priority: P3)

用户想让智能体真的执行一条命令，且要看到命令的输出、退出码、以及"是不是超时了"。用户尤其在意：命令是**一次性**的，不是残留一个后台会话 —— 因为将来要支持"中途打断"。

**Why this priority**: 命令执行是工具集里最直接的"干活"能力；同时它必须天然可打断，否则将来的人工介入能力做不出来。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在独立子进程中执行一条回显命令，解析返回结果并检查输出内容、退出码与超时标记。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户在独立子进程中执行回显命令，**Then** 返回值是一段可被标准 JSON 解析的文本，其中输出含命令回显的内容、退出码为 `0`、超时标记为假。
2. **Given** 一个超时标记为真的返回结果，**When** 模型据此决策，**Then** 模型可区分"命令失败"与"命令超时"两种情况 —— 超时以**返回结果里的结构化标记**表达，MUST NOT 以异常形式抛给模型（FR-031）。
3. **Given** 一条输出远超上限的命令，**When** 用户执行它，**Then** 返回结果含"已截断"标记与"共多少行"的说明，MUST NOT 把完整输出原样返回，也 MUST NOT 在工作区里留下输出文件。

### User Story 4 - 文件工具的七个动作都能用且不破坏旧用法 (Priority: P4)

用户要读写、复制、移动、删除、列目录、看文件属性 —— 七个动作覆盖日常全部文件操作。更重要的是：**将来新增的能力不能破坏今天的用法**，用户今天写的调用脚本明天还得能跑。

**Why this priority**: 这是文件工具的功能面；同时"向后兼容"是材料层可持续演进的前提 —— workspace 会被用户长期持有。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在独立子进程中完成"写 → 读 → 复制 → 列目录 → 看属性 → 删除"的连续操作并断言每步结果。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户写入一个文件后立刻读回，**Then** 读回的内容包含写入的内容（去掉呈现文本的包装后逐字一致）。
2. **Given** 一次复制操作，**When** 用户检查目标文件，**Then** 目标文件存在且内容与源文件一致。
3. **Given** 一次列目录操作，**When** 用户检查结果，**Then** 结果是一个名称列表，且包含刚写入的文件名。
4. **Given** 一次看属性操作，**When** 用户检查结果，**Then** 结果是一个可直接取字段的映射（而非一段 JSON 文本），其中"是文件"为真、体积大于零。
5. **Given** 一次删除操作，**When** 用户检查磁盘，**Then** 目标文件已不存在。
6. **Given** 一个**体积 ≤ 50 KiB 但行数 > 2000** 的文件（**区分样本** —— 字节上限未触发，**行数上限 MUST 仍无条件生效**，见 FR-092 / FR-095 / FR-098(d)），**When** 用户读取它，**Then** 返回内容被截断、且附上"下一段从第几行继续"的指引（模型据此可续读），MUST NOT 一次性返回整个文件。
7. **Given** 一个二进制文件，**When** 用户读取它，**Then** 读取**明确报错**，MUST NOT 把乱码当作正文交给模型。

### User Story 5 - 网络工具能拉取网页 (Priority: P5)

用户要智能体能查资料。抓取工具需要能按方法发请求、带自定义请求头、有超时保护，并如实回报状态码、正文、响应头与最终地址。

**Why this priority**: 只读能力里最容易独立验证、也最容易被后续功能复用的一块；它与写操作解耦（不产生任何文件变更）。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在带网络拦截的独立子进程中请求一个地址并断言状态码与正文。

**Acceptance Scenarios**:

1. **Given** 一个可被拦截的地址，**When** 用户发起一次请求，**Then** 返回值是一段可被标准 JSON 解析的文本，其中状态码为 `200`、正文含预期内容。
2. **Given** 请求超时，**When** 异常透传到调用方，**Then** 调用方收到明确的超时异常（而非被吞掉或改写成一个含糊的失败）。
3. **Given** 一个非 http/https 的地址，**When** 用户发起请求，**Then** 请求**被拒绝并明确报错**，MUST NOT 真的发出去。
4. **Given** 一个体积超过上限的响应，**When** 用户发起请求，**Then** 请求**被拒绝并明确报错**，MUST NOT 把超大响应整个读进来。

### User Story 6 - 示例 Skill 的三层结构齐备 (Priority: P6)

用户会照着示例写自己的 Skill。示例必须把"三层渐进披露"讲清楚：第一层是头部元信息（名称 + 描述两字段），第二层是正文主体，第三层是附属资源（参考文档 / 脚本 / 模板）。用户**照抄示例**就能写出一个合规的 Skill。

**Why this priority**: 示例是用户的事实上的模板；示例本身不合规或层次缺失，会把不合规的写法复制到用户的工作区里。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，检查示例 Skill 文件的头部元信息块、正文非空、以及第三层子目录中至少有一个文件。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户读取示例 Skill 文件，**Then** 文件以元信息分隔符开头，含名称与描述两个字段。
2. **Given** 同一个文件，**When** 用户检查正文，**Then** 正文非空且含第二层说明。
3. **Given** 示例 Skill 目录，**When** 用户统计第三层子目录中的文件，**Then** 至少存在 **1** 个文件。

### User Story 7 - 找文件找内容不归内置工具管 (Priority: P7)

用户偶尔会疑惑：为什么内置文件工具里没有"按文件名搜"和"按内容搜"？答案是**分工**：那属于引擎侧的检索中间件，内置工具只管对单个文件或目录的精确操作。

**Why this priority**: 这是一条**边界**约束而非功能 —— 但一旦越界（例如在文件工具里自己实现检索），材料层与引擎层职责重叠，将来中间件接入时会产生两套行为。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，逐个检查 3 个内置工具文件的正文，确认其中不含那两个检索能力的名字。

**Acceptance Scenarios**:

1. **Given** 三个内置工具文件，**When** 用户逐个检查其正文，**Then** 三个文件均不含检索能力名（按文件名搜 / 按内容搜）。
2. **Given** 同一批文件，**When** 用户检查它们的职责，**Then** 文件工具只覆盖读 / 写 / 复制 / 移动 / 删除 / 列目录 / 看属性七件事。

### User Story 8 - 删掉内置工具后再 init 会补回来 (Priority: P8)

用户手滑删了 `tools/filesystem.py`。他期望再跑一次 init 就能补回来，而不是自己回忆文件内容。

**Why this priority**: 幂等性是 `donkey init` 的核心契约（业务验收 AC-3）—— 补齐能力是这一契约最直观的表现。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，删掉一个内置工具文件，再次执行 `donkey init`，断言该文件重新出现且命令退出码为 `0`。

**Acceptance Scenarios**:

1. **Given** 一个已生成的 workspace 且其中一个内置工具文件被删除，**When** 用户再次执行 `donkey init`，**Then** 命令以退出码 `0` 结束且被删文件重新出现。

### User Story 9 - 强制重置不会误伤我自己的工具 (Priority: P9)

用户在自己的 `tools/` 目录里写了 `my_custom_tool.py`。他用强制重置恢复出厂状态时，**最怕的是自己的工具被删掉**。

**Why this priority**: 这是数据安全底线 —— 强制重置的作用域一旦越界，用户会失去自己的工作成果。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，新建一个清单外的自定义工具文件，执行带强制标志的 init，断言该文件仍在、且内置工具文件已被恢复成出厂内容。

**Acceptance Scenarios**:

1. **Given** 用户在 `tools/` 下新建了一个不在清单内的自定义工具文件，**When** 用户执行带强制标志的 init，**Then** 命令以退出码 `0` 结束且该自定义文件仍然存在。
2. **Given** 同一个 workspace，**When** 用户检查内置工具文件的内容，**Then** 该文件已被恢复成出厂内容（不含用户自定义工具里的字符）。

### User Story 10 - 生成出来的工具能被另一个进程真正用起来 (Priority: P10)

用户把工作区拷给同事。同事在自己的机器上打开这个目录，加载其中的工具 —— 工具必须**能被真正加载**，而不是只在生成它的那台机器上、只在刚生成的那一刻可用。

**Why this priority**: 这是"工作区可移植"这一产品主张的落地检验；生成物若绑死在生成机上，工作区就不可携带。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在一个**独立子进程**中导入全部 9 个工具函数并断言它们全部可调用。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户在独立子进程中导入全部 9 个工具函数，**Then** 导入全部成功、9 个函数全部可调用。

---

### User Story 11 - init 阶段不做配置检查 (Priority: P11)

用户明确知道：初始化只负责"把工作区搭起来"，不负责"检查你配得对不对"。所以即便内置工具文件有问题，init 也不该报错。

**Why this priority**: 这是一条**职责边界** —— 配置检查属于另一个阶段；越界会让用户在还没开始配置时就撞上一堆看不懂的报错。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，断言退出码为 `0`，且过程中未触发任何配置类检查。

**Acceptance Scenarios**:

1. **Given** 一个尚不存在、但父目录已存在的目标路径，**When** 用户执行 `donkey init`，**Then** 命令以退出码 `0` 结束，初始化阶段未对工作区内的工具 / 配置做合法性判定。

---

### User Story 12 - 写文件会带回"改了什么" (Priority: P12)

用户改一个文件，希望知道**到底改了什么**：旧内容是什么、新内容是什么、差异在哪。用户要能**先看再决定**（预览不落盘），也要能**防止覆盖别人的改动**（别人刚改过就拒写）。

**Why this priority**: 这是本 Phase 的"diff-ready 地基" —— 材料层先把变更原材料完整交出，将来引擎层才能渲染差异、人工确认、回滚。**交出原材料 ≠ 实现审阅流程**（业务验收 AC-5 不被违反）。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在独立子进程中连续写同一文件两次，断言两次返回的变更记录（版本 / 动作 / 旧版本指纹 / 新版本指纹 / 差异文本）。

**Acceptance Scenarios**:

1. **Given** 一个尚不存在的目标文件，**When** 用户首次写入，**Then** 返回结果标明动作为"创建"、已落盘，且变更记录中旧版本存在标记为假、旧版本指纹**为 `null`**、新版本指纹非空、差异文本含新增行。
2. **Given** 同一文件已存在，**When** 用户再次写入不同内容，**Then** 返回结果标明动作为"更新"，变更记录中旧版本指纹等于**上次写入后**的指纹，差异文本同时含被替换行与新增行。

---

### User Story 13 - 先看后写，不落盘 (Priority: P13)

用户想在真正动手前先看看差异。于是他要求"只算不写"—— 文件内容必须**一个字节都不变**，连临时文件都不能留下，但预览结果仍然要完整可用。

**Why this priority**: "先看 diff 再决定写不写"是差异审阅的基本交互；没有它，将来引擎层的差异审阅无从落地。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在独立子进程中先写入旧内容、再以预览模式写入新内容，断言文件内容未变、返回记录标明未落盘、差异文本非空、且目录下无临时文件残留。

**Acceptance Scenarios**:

1. **Given** 一个已存在内容的文件，**When** 用户以预览模式写入新内容，**Then** 返回结果标明未落盘、变更记录同样标明未落盘、差异文本含被替换行，且文件内容**逐字节未变**。
2. **Given** 同一次预览，**When** 用户检查工作区目录，**Then** 目录中**不存在**任何临时文件残留。

---

### User Story 14 - 写失败不会毁掉旧内容 (Priority: P14)

用户担心最坏情况：写到一半失败，把原来好好的文件截成半截 —— 那就再也回不去了。他需要的是"要么写成功，要么原封不动"。

**Why this priority**: 这是**数据安全底线** —— 一旦覆盖写把旧内容毁掉，将来任何差异展示与回滚都无从谈起（"旧的那一半永久丢失"）。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，让目标路径的父路径是一个已存在的**文件**（使写入必然失败），断言写入抛错、阻塞文件内容未变、且目录中无临时文件残留。

**Acceptance Scenarios**:

1. **Given** 目标路径的父路径是一个已存在的文件，**When** 用户尝试写入，**Then** 写入失败并抛出异常，且那个作为父路径的文件内容**逐字节未变**。
2. **Given** 同一次失败，**When** 用户检查目录，**Then** 目录中**不存在**任何临时文件残留。

---

### User Story 15 - 删除也有记录、契约版本冻结 (Priority: P15)

用户删了文件，希望"删了什么"也有据可查（旧内容的指纹、可选的旧正文），以便将来能回滚。同时，用户要确信这份契约的版本是**冻结**的 —— 消费方能靠版本号分派，不靠猜字段。

**Why this priority**: 删除是最容易"信息全丢"的写操作；同时版本冻结是"只增不改"承诺的**唯一可检验证据**（消费方按版本分派的前提）。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，在独立子进程中写入后删除，断言返回记录标明动作为"删除"、类型为"文件"、旧版本指纹非空、新版本指纹**为 `null`**、文件确实不在了，且契约版本为 `1`。

**Acceptance Scenarios**:

1. **Given** 一个已存在内容的文件，**When** 用户删除它，**Then** 返回结果标明动作为"删除"、类型为"文件"，变更记录中旧版本指纹非空、新版本指纹**为 `null`**，且文件确实不存在于磁盘。
2. **Given** 同一个 workspace，**When** 用户读取契约版本号，**Then** 版本号为 `1`。

---

### Edge Cases

**写类工具与变更记录类**

- 目标路径的父路径已存在但**是文件** → 写入失败（抛异常），MUST NOT 静默跳过；旧内容 MUST 保持原样；目录中 MUST NOT 留临时文件残留。
- 目标路径已存在且**是目录** → `write_file` MUST 抛"是目录"类错误，MUST NOT 静默跳过、MUST NOT 递归删除目录内容。
- 目标路径**已存在且不可写**（只读） → 抛权限类异常，MUST NOT 静默成功。
- 目标路径**不存在**且父目录**不存在** → 写入 MUST 自动创建父目录（保持"创建父目录"的既有语义）。
- 写入**旧内容存在但不是合法 UTF-8** 的文件 → 指纹与体积 MUST 按**原始字节**计算（MUST NOT 先解码再编码 —— 那会改变指纹）；差异文本的解码 MUST 容错。
- 写入**空内容** → 新内容指纹 MUST 是空内容的指纹（空串的指纹），体积为 `0`；差异文本 MUST 反映"清空"。
- 差异文本**超过 64 KiB** → MUST 截断并把截断标记置真（MUST NOT 把超长差异整段塞进上下文）。
- 请求带回旧正文但旧正文**超过 256 KiB** → MUST 置"旧正文被省略"标记为真，MUST NOT 硬塞（但旧内容的指纹 MUST 仍然存在）。
- 期望指纹与磁盘现状**不一致**（文件在读取后被他人改动） → 写入 MUST 被拒绝（抛"文件已变更"类异常），MUST NOT 写入、MUST NOT 改动文件。
- **复制 / 移动 / 删除时传入不匹配的期望指纹** → MUST 拒绝执行并抛"文件已变更"类异常（FR-019）；MUST NOT 覆盖目标文件、MUST NOT 执行移动、MUST NOT 删除；MUST NOT 产生任何磁盘副作用。
- 期望指纹非空但文件**已不存在** → 同样视为不匹配 → 拒绝写入。
- 期望指纹为**空**（未提供） → 乐观锁 MUST 被关闭（正常写入）。
- **相对路径** → MUST 以工作区根为基准，MUST NOT 依赖进程当前目录；**绝对路径** → MUST 原样可用（MUST NOT 被工作区边界拦截 —— 路径白名单由用户自管）。
- **环境中存在指向别处的工作区根覆盖变量** → MUST 被**忽略**；工作区根恒为"存放 `tools/` 的那个目录"（FR-002 / FR-104），MUST NOT 因该变量而改变相对路径的基准或写入落点。
- **把 `tools/` 目录整体移走或另置** → 工作区根随之改变（这正是"由自身位置推导"的语义）；相对路径 MUST 以新的所在位置为基准，MUST NOT 回退到任何环境变量或进程当前目录。
- **用户自写工具与内置工具位于不同目录** → 各自的契约库副本 MUST 各自以自身位置推导工作区根；MUST NOT 存在跨目录共享的隐式根。
- 读取的文件**超过 2000 行** → MUST 截断并给出续读指针（下一段起始行号）；MUST NOT 把整个文件塞进返回值。
- 读取的文件**超过 50 KiB** → 同上（字节上限先于行数上限生效时，按字节截断）；MUST NOT 把整个文件塞进返回值。
- 读取的文件**体积 ≤ 50 KiB 但行数 > 2000** → **行数上限无条件生效**（字节上限未触发也 MUST 截断）→ MUST 截断并给出续读指针（下一段起始行号）—— FR-092 / FR-095 / FR-098(d)。
- 单行**超过 2000 字符** → MUST 截断该行并附 `... (line truncated to 2000 chars)` 标记；MUST NOT 静默砍掉。
- 请求的行数**超过 2000** → MUST 截到 2000 行；MUST NOT 报错。
- 请求的起始行**越过文件末尾** → MUST 明确报错（OpenCode 的起始行越界口径），MUST NOT 返回空内容冒充成功。
- 读取**二进制文件**（含 NUL 字节）→ MUST 明确报错，MUST NOT 返回乱码。
- 读取**图片 / PDF** → MUST 明确报错（多模态附件属引擎层，见已知缺口登记）。
- 读取一个**目录** → MUST 按目录分支呈现（条目列表 + 续读提示），MUST NOT 报"是目录"类错误。
- 列目录的**条目超过 2000** → MUST 截断；MUST NOT 追加超出上限的条目。
- 网络请求使用**非 http/https 协议** → MUST 报错，MUST NOT 发起请求。
- 网络响应**超过 5 MiB** → MUST 报错；MUST NOT 先把响应读进内存再判大小（超限 MUST 在读取过程中即被拦下）。
- 网络响应为**非文本 MIME** → MUST 报错。
- 网络响应状态码**非 2xx** → MUST 报错，MUST NOT 返回正文。
- 网络请求的**超时值超过 120 秒** → MUST 报错（OpenCode 的超时上限）。
- 路径指向**工作区之外** → 变更记录中的相对路径字段 MUST 回退为绝对路径（MUST NOT 抛异常）；越界记录由将来的引擎层按相对路径判定审阅范围。
- **预览模式** → MUST NOT 产生任何磁盘副作用（不建父目录、不写文件、不移动、不删除、不留临时文件），但 MUST 返回完整变更记录（已落盘标记为假）。
- **复制 / 移动 / 删除时开启预览** → MUST 无任何磁盘副作用（不写目标、不移源、不删文件），但 MUST 返回完整变更记录（已落盘标记为假）；期望指纹不匹配时 MUST **先拒绝执行**、MUST NOT 返回预览（FR-019 / FR-020）。
- **移动**操作 → 变更记录描述**目标路径**；源路径与源相对路径两个字段 MUST 出现。
- **复制**操作 → 变更记录描述**目标路径**；源路径与源相对路径两个字段 MUST 出现；元数据复制失败 MUST 被忽略（MUST NOT 使整个复制失败）。
- **删除目录** → MUST 按**目录粒度**记录（不枚举内部逐文件差异）；旧正文 MUST NOT 被附带（目录不是文件）。
- **删除不存在的路径** → 抛"文件不存在"类异常，MUST NOT 静默成功。
- **命令工具的副作用** → 命令造成的文件改动 MUST NOT 进变更记录（命令绕过了工具的写路径）；此缺口 MUST 写进工具说明文字，MUST NOT 在本 Phase 试图拦截。
- **命令超时** → MUST 被掐断并如实回报超时标记与返回码 `-1`；MUST NOT 无限等待；MUST **以返回 JSON 的方式**表达，MUST NOT 抛出超时异常（FR-031）。
- **命令的工作目录** → MUST 默认是工作区根；相对工作目录 MUST 同样以工作区根为基准。
- **命令输出超过 2000 行或 50 KiB** → MUST 截断、MUST 把 `truncated` 置真、MUST 附 OpenCode 式标记（FR-100）；MUST NOT 把完整输出返回，MUST NOT 落盘保存完整输出（FR-101）。
- **命令输出恰在上限之内** → `truncated` MUST 为假，MUST NOT 出现截断标记。
- **命令包含管道 / 重定向** → 本 Phase 不支持（命令被显式拆成参数数组，不经命令解释器）；MUST NOT 因此崩溃，MUST 如实回报执行失败。
- **网络请求超时** → 异常 MUST **透传**给调用方，MUST NOT 被吞掉或改写成含糊失败。
- **网络请求失败（网络 / 协议错误）** → 同上，异常 MUST 透传。
- **网络请求返回非 2xx** → MUST 如实回报状态码（返回结果里**没有**"成功 / 失败"二值字段）；MUST NOT 抛异常。
- **网络请求跟随重定向** → 返回结果中的地址 MUST 是**重定向之后**的最终地址。

**生成与幂等类**

- 用户删掉某个内置工具文件后再次 init → MUST 补齐（清单内缺失条目）。
- 用户删掉某个 Skills 第三层文件后再次 init → MUST 补齐（清单内缺失条目）。
- 用户在 `tools/` 下新建**清单外**的文件 → MUST 原样保留；带强制标志时 MUST 仍然保留。
- 用户改了某个内置工具文件的内容 → 非强制模式下 MUST 完全不动；带强制标志时 MUST 恢复出厂内容。
- 带强制标志时 `skills/example/` 下的第三层文件 MUST 恢复出厂内容；**清单外**的第三方文件 MUST 保留。
- 带强制标志时"目录条目" MUST NOT 删除目录本身、MUST NOT 删除目录内任何文件（清理由各自的清单条目负责）。
- **带强制标志时契约库已存在** → MUST 保留原样、MUST NOT 覆盖（MUST NOT 把它当作"恢复出厂"处理）—— 契约库是用户自写工具的依赖，覆盖它会让用户代码失效（FR-105）。
- 清单条目顺序被打乱 → MUST NOT 影响结果（写文件前确保父目录存在）。
- 安装包内**缺**某个新模板源文件（如 `tools/changes.py.txt`） → MUST 按模板生成类失败处理（退出码 `3`），MUST NOT 静默生成半残工作区（"工具在、契约库不在"）。
- 内置工具文件与契约库文件 MUST **同批**生成 —— 二者缺一则文件工具导入即失败，MUST NOT 出现半残工作区。

**阶段边界类**

- F001-P2 的若干断言编码的是 P2 的**阶段边界**（清单条数 / 工作区内无任何 `.py` 文件 / 退出码集合恰为 `{0,1,2,3}`），本 Phase 按设计要打破它们 → MUST **显式改写**这四处断言为**动态口径**；MUST NOT 靠"改红 P2 的测试"或"让 P2 红着提交"蒙混过关；**本 Phase 引入的唯一一处通则例外**（契约库豁免于强制重置，FR-105）MUST 只作用于契约库一个条目，MUST NOT 削弱 P2 通则对其余条目的成立；P2 的**持久**不变量 MUST NOT 被改动。
- F001-P2 的 e2e 场景 11（"还没有内置工具文件"） MUST 同样改写 —— 它的"无内置工具"边界断言移交本 Phase 的场景 7 与场景 1。
- 本 Phase MUST NOT 触碰三个记忆库文件（其结构属 F001-P2 域）；MUST NOT 在 init 阶段做记忆库结构健康检查。
- Skill 第三层演示脚本含 `__main__` 入口块 → **不算**"工作区入口文件"违例（授权来源：宪法 §6.3 例外 E-02 + §5 章 [D-19] 的 N-01 边界澄清，见 FR-050）；但"工作区内不得出现 Python 入口"形态的**门禁** MUST NOT 以此判为违例。

**其它边界**

- 初始化阶段生成内置工具失败（写入失败 / 权限被撤销 / 磁盘满） → MUST 归入**同一个**退出码 `4`（两类成因对用户的修复动作相同：重装 / 检查权限 / 重试 init），MUST NOT 各占一个码值。
- 初始化阶段**生成物导入预演失败** → 本 Phase **不做**导入预演（FR-072），故此类失败**不**在 `donkey init` 阶段暴露；生成物的可导入性由集成测试层（生成器回归测试）与 F002 的 `donkey load`（用户可见的导入验证）分别承担。
- 并发执行 `donkey init` → 不在本 Phase 职责范围内。
- 平台差异（Windows 上文件被占用）→ 按普通的写入失败处理，MUST NOT 强制删除被占用的文件。
- **风险登记（已按 OpenCode 收紧）· 网络访问边界**：网络工具**限协议**（只允许 http/https）且**限响应体体积**（5 MiB），非文本 MIME 与非 2xx 一律报错（FR-089）→ 材料层这一侧的边界与 OpenCode 等价；**目标地址范围仍不设限**（回环地址 / 私有网段 / 云主机元数据地址均可请求）—— OpenCode 亦不限制地址，其对应能力在**引擎层权限机制**里，而 donkey v1 无该机制（宪法 §2.1）。后果与知情义务 MUST 写进工具说明文字（FR-090）。
- **风险登记（跨 Feature）· 工具扫描器对无工具模块的容忍**：`tools/changes.py`（契约库）与 `tools/__init__.py` 含 **0** 个工具函数 → 未来的工具扫描器若按"每个 `tools/*.py` 至少 1 个 `@tool`"判定，会把这两个文件误判为坏工具模块（FR-091）。本 Phase MUST NOT 因此给契约库塞工具函数来"凑数"；该风险 MUST 由后续 Feature（工具扫描器所属阶段）消解。
- **已知缺口（v1 不补）· 多模态附件**：OpenCode 把图片 / PDF 作为**多模态附件**直接交给模型；donkey 的工具函数只能返回文本 / JSON 文本，无法交付附件 → `read_file` 遇媒体文件 MUST 明确报错（FR-096）。多模态附件交付属**引擎层**能力。
- **已知缺口（v1 不补）· 读取呈现改变了返回值语义**：照搬 OpenCode 后，`read_file` 的返回值不再是**纯文件正文**，而是带页范围说明头 + `<行号>: ` 行号前缀（+ 截断时的续读提示）的**呈现文本**（FR-094）→ 程序化调用方 MUST NOT 直接把该返回值当正文解析（MUST 自行走标准库读取）；需要纯正文的场景 MUST NOT 依赖 `read_file` 的返回值（详见 FR-015 的『返回值语义变更的显式登记』）。

## Requirements *(mandatory)*

### Functional Requirements

#### 变更记录契约库 `tools/changes.py`（实现要点 §4.1.1）

- **FR-001**: 系统 MUST 在工作区的 `tools/` 目录下生成一个**变更记录契约库** `tools/changes.py`；该模块 MUST 含 **0** 个工具函数（它是契约底座，**不**被模型直接调用），MUST NOT 含任何 Python 入口块（宪法 N-01）。
- **FR-002**: 契约库 MUST 暴露以下**公开契约面**（只增不改：既有函数的名字与语义 MUST 冻结，新增能力 MUST 以新函数形式追加）：`workspace_root()` / `resolve_path(path)` / `relative_path(path)` / `sha256_bytes(data)` / `read_existing_bytes(path)` / `atomic_write_bytes(path, data)` / `build_unified_diff(old_text, new_text, rel)` / `build_change_record(action, path, previous_bytes, new_bytes, *, src=None, include_previous=False)` / `check_expected_hash(path, expected_hash)`，以及异常类 `FileChangedError(RuntimeError)`。**`workspace_root()` 的行为已冻结**：工作区根 MUST 恒等于"存放 `tools/` 的那个目录"（由契约库自身位置推导），MUST **NOT** 读取任何环境变量作为覆盖（源提示词实现中的环境变量覆盖开关**已移除** —— 见 Clarifications 第二轮 Q2 与 FR-104）。
- **FR-003**: 契约库 MUST 冻结三个常量 —— 契约版本 `1`、单条差异文本的最大字节数 `64 KiB`、可附带旧正文的最大字节数 `256 KiB`；契约版本 MUST 仅在**破坏性**变更时递增。
- **FR-004**: 变更记录 MUST 含 **12** 个**必现基线**字段 —— 契约版本 / 动作 / 绝对路径 / 相对工作区根的 POSIX 相对路径 / 变更前是否存在 / 变更前字节数 / 变更前内容指纹（`sha256:<hex>`，**不存在时为 `null`（Python 侧 `None`，MUST NOT 用空串**）/ 变更后字节数 / 变更后内容指纹（**删除后为 `null`**）/ 标准统一差异文本 / 差异是否被截断 / 是否已落盘。**任何动作下这 12 个字段 MUST 全部存在**（单测 MUST 按"基线键集合"断言，防止字段漂移）。
- **FR-005**: 变更记录 MUST 含**条件字段** —— 源路径与源相对路径两个字段**仅**在动作为"复制"或"移动"时出现；旧正文与"旧正文是否被省略"两个字段**仅**在请求带回旧正文时出现（旧正文超限时 MUST 置"已省略"为真且 MUST NOT 附带正文）。
- **FR-006**: 变更记录的生成 MUST 接收**原始字节**（旧字节 / 新字节）而非字符串 —— 指纹与体积 MUST 按原始字节计算，MUST NOT 先解码再编码（那会改变含 BOM 或非法字节文件的指纹）。
- **FR-007**: 统一差异文本 MUST 使用**工作区相对路径**作为差异头（`a/<相对路径>` / `b/<相对路径>`）—— 工作区可搬移，差异 MUST 可移植；工作区之外的路径其相对路径字段 MUST 回退为绝对路径（MUST NOT 抛异常）。
- **FR-008**: 原子写 MUST 在**目标同目录**创建临时文件后以"就地替换"方式落位（跨目录的替换不保证原子）；临时文件名 MUST 以点开头（不污染目录列表的默认视图）；**任何异常路径 MUST 清理临时文件**（MUST NOT 留残留）；落位前 MUST 把内容刷到存储设备。
- **FR-009**: 原子写 MUST 负责创建目标的父目录（保持"写文件时自动建父目录"的既有语义）。
- **FR-010**: 乐观锁检查 MUST 支持"声明期望指纹"—— 不匹配（含"文件已不存在"的情形）时 MUST 抛出"文件已变更"类异常；期望指纹为空时 MUST 关闭该检查。
- **FR-011**: 契约库 MUST NOT 引入任何智能体框架的导入（保持"非工具模块"身份清晰，便于将来的工具扫描器零歧义识别）。
- **FR-012**: 变更记录契约 MUST 遵守**只增不改**三原则 ——（a）**只增不改**：新字段可加，既有字段的名字与语义冻结，消费方 MUST 忽略不认识的字段；（b）**版本分派**：消费方 MUST 按契约版本分派，MUST NOT"靠字段是否存在猜版本"；（c）**单一来源**：任何改文件的工具（内置的与用户自写的）MUST 复用契约库，MUST NOT 自造第二套指纹 / 差异逻辑。

#### 文件工具 `tools/filesystem.py`（实现要点 §4.1）

- **FR-013**: 系统 MUST 在工作区的 `tools/` 目录下生成文件工具模块，该模块 MUST 提供 **7** 个工具函数：`read_file(path, start_line=1, num_lines=None)` / `write_file(path, content, dry_run=False, include_previous=False, expected_hash=None)` / `copy_file(src, dst, dry_run=False, expected_hash=None)` / `move_file(src, dst, dry_run=False, expected_hash=None)` / `delete_file(path, include_previous=False, dry_run=False, expected_hash=None)` / `list_dir(path, include_hidden=True, offset=0, limit=None)` / `stat(path, with_hash=False)`。**四个改文件的工具**（写 / 复制 / 移动 / 删除）MUST **一致地**支持"期望指纹"与"只算不写"两个可选参数。
- **FR-014**: 文件工具的**全部新增参数 MUST 一律可选且带默认值**，且默认值 MUST 复刻旧行为 —— 不传新参数的既有调用方式其行为 MUST **逐字节不变**（例：列目录的"含隐藏项"默认值为真，即旧行为"列出全部子项"）。
- **FR-015**: 读文件 MUST 支持按起始行与行数**局部读取**（便于模型只读差异片段而不必加载整个文件）；`stat` MUST 继续返回可直接取字段的映射（**不**改成 JSON 文本），`list_dir` MUST 继续返回名称列表（**不**改成 JSON 文本 —— 该返回类型的冻结优先于 OpenCode 的分页列表结构，见 FR-097）。**读文件与列目录的返回内容形态由 FR-092 ~ FR-098 定格**（照搬 OpenCode 的双上限 + 行号前缀 + 续读指针）。**返回值语义变更的显式登记**：FR-092 ~ FR-098 把 `read_file` 的返回值从"纯文件正文"改为"呈现文本"（页范围头 + `<行号>: ` 前缀 + 续读提示）—— 这是本 Phase 对既有调用语义的**唯一一处破坏性变更**，已在 Edge Cases「已知缺口」中登记；MUST NOT 被理解为违反"只增不改"（FR-021 约束的是**改文件工具的返回结果字段集合**，与 `read_file` 的**字段值呈现形态**无关 —— 二者不冲突）。
- **FR-016**: 所有**改文件**的工具 MUST 返回统一的变更记录（放在返回结果的 `change` 字段中），且 MUST 经契约库生成 —— MUST NOT 自造指纹 / 差异逻辑。
- **FR-017**: 所有**改文件**的工具 MUST 走**原子写** —— MUST NOT 直接覆盖写已有文件（那会毁掉旧内容，使将来的差异展示与回滚无从谈起）；复制操作 MAY 额外复制文件元数据（失败 MUST 被忽略，MUST NOT 使整个操作失败）。
- **FR-018**: 写文件 MUST 保持"创建父目录"的既有语义；目标已存在且**是目录**时 MUST 抛"是目录"类错误，MUST NOT 静默跳过。
- **FR-019**: 期望指纹不匹配时 MUST 抛出契约库中的"文件已变更"类异常，MUST NOT 写入、MUST NOT 改动文件。**适用范围**：该乐观锁 MUST 覆盖**全部四个**改文件的工具 —— 写文件 / 复制 / 移动 / 删除（FR-013）—— 因为后三者同样会覆盖或移除目标文件；不匹配时 MUST **拒绝执行**（MUST NOT 覆盖目标、MUST NOT 执行移动、MUST NOT 删除），且 MUST NOT 产生任何磁盘副作用。期望指纹为**空**（未提供）时 MUST 关闭该检查（既有调用方式行为不变）。**期望指纹是入参守卫，MUST NOT 出现在变更记录里**（变更记录的字段集由 FR-004 / FR-005 冻结）。
- **FR-020**: 预览模式 MUST **不产生任何磁盘副作用**（不建父目录、不写文件、不移动、不删除、不留临时文件），但 MUST 返回完整变更记录（已落盘标记为假）。**适用范围**：该预览 MUST 覆盖**全部四个**改文件的工具 —— 写文件 / 复制 / 移动 / 删除（FR-013）；复制与移动在预览时 MUST NOT 写出目标文件、MUST NOT 移动源文件；删除在预览时 MUST NOT 移除任何文件。**为何材料层要自带预览**：OpenCode 的工具层不带该能力，是因为它**有**引擎层差异预览 + 人工确认兜底（落盘前算出差异后交权限审批层）；donkey v1 明确不做那一层（AC-5），故材料层 MUST 自行补上这一层兜底。
- **FR-021**: 返回结果的字段 MUST **只增不改** —— 写文件保留"路径"与"写入字节数"并追加"动作""已落盘""变更记录"；复制与移动保留"源路径""目标路径"并追加"动作""已落盘""变更记录"；删除保留"路径"与"类型"并追加"动作""已落盘""变更记录"。
- **FR-022**: 相对路径 MUST 以**工作区根**为基准，MUST NOT 依赖进程当前目录；绝对路径 MUST 仍然可用（路径白名单由用户自管，见 `tools/README.md`）。
- **FR-023**: 每个工具函数 MUST 有**完整说明文字**（工具框架以其作为工具描述）；说明文字 MUST 在参数段写清**每个新增可选参数**的语义与默认值。
- **FR-024**: 工具装饰器 MUST 使用智能体框架**内置**的官方装饰器（MUST NOT 自造工具协议）；该导入 MUST NOT 出现在客户端层（宪法 N-04）。
- **FR-025**: 文件工具 MUST **不**包含"按文件名搜"与"按内容搜"两个能力（属引擎侧检索中间件的职责，宪法 §2.5 / §2.6）。
- **FR-026**: 文件工具对契约库的导入 MUST 同时支持"作为工作区 `tools` 包的一部分导入"（相对导入）与"作为顶层模块导入"（绝对导入）两种形态 —— 后者 MUST 作为回退路径存在（MUST NOT 因导入方式不同而失败）。
- **FR-027**: 文件工具 MUST **不**实现"创建 / 修改 / 移动 / 删除"以外的额外动作，MUST NOT 引入子智能体相关字段（宪法 N-02）。

#### 命令工具 `tools/commandline.py`（实现要点 §4.2）

- **FR-028**: 系统 MUST 在工作区的 `tools/` 目录下生成命令工具模块，该模块 MUST 提供 **1** 个工具函数 `run_shell(command: str, timeout: int = 60, cwd: str | None = None)`。**`timeout` 不设上限** —— 与 `fetch_url` 的 120 秒上限（FR-037）构成**有意的不对称**：命令工具的超时值由调用方按场景自定，MUST NOT 被实现成任何隐式上限。
- **FR-029**: 命令执行 MUST **每次新建进程**（MUST NOT 使用持久会话）—— 持久会话与将来"中途打断"能力冲突。
- **FR-030**: 命令 MUST 由工具**显式拆成参数数组**执行（MUST NOT 交给命令解释器），从源头避免命令注入；管道 / 重定向因此不支持（本 Phase MUST NOT 承诺支持）。**入参形态**：命令以**单个命令字符串**传入（`command: str`，见 FR-028），由工具内部按 POSIX 引号规则拆成参数数组后**不经 shell** 直接执行 —— "显式参数数组"指的是**执行形态**（`shell=False`），**不**意味着调用方传入数组。
- **FR-031**: 命令执行 MUST 有**显式超时**并可被掐断；超时 MUST 被如实回报（独立的超时标记为真 + 返回码 `-1`），MUST NOT 无限等待、MUST NOT 被伪装成"普通失败"。**超时 MUST 以"返回 JSON"的方式表达，MUST NOT 抛出超时异常** —— 超时是命令执行的**正常结局**之一，模型 MUST 能从返回结果的结构化字段里读到"超时"这一事实并自行决定重试 / 放弃。（与 FR-041 的网络工具异常透传口径构成**有意的不对称**，MUST NOT 被"统一"成同一种行为。）
- **FR-032**: 命令的**工作目录 MUST 默认是工作区根**，MUST NOT 依赖进程当前目录；传入的相对工作目录 MUST 同样以工作区根为基准。
- **FR-033**: 命令工具的返回结果 MUST 含**六个既有字段** —— "标准输出""标准错误""返回码""是否超时""工作目录""实际执行的参数数组"；其中既有字段的语义 MUST 冻结（只增不改），新增字段 MUST 以追加方式出现（FR-100 新增的 `truncated` 即属此类 → 实际字段共 **7** 个）。
- **FR-034**: 命令工具 MUST **不**依赖任何持久会话中间件（该类中间件被永久禁用）。
- **FR-035**: 命令工具的说明文字 MUST 写明**已知缺口** —— 命令造成的文件副作用**不**进变更记录（命令绕过工具的写路径，将来的引擎层靠工作区快照对账）；本 Phase MUST NOT 试图拦截该副作用。
- **FR-036**: 命令工具的说明文字 MUST 完整（参数段写清超时与工作目录的语义与默认值），且 MUST **与实际行为一致** —— MUST NOT 保留任何与实现矛盾的异常声明（例如声称超时会"重新抛出超时异常"，而实现是捕获后返回 JSON，见 FR-031）。

#### 网络工具 `tools/webfetch.py`（实现要点 §4.3）

- **FR-037**: 系统 MUST 在工作区的 `tools/` 目录下生成网络工具模块，该模块 MUST 提供 **1** 个工具函数 `fetch_url(url, method="GET", headers=None, timeout=30)`；**超时值上限 MUST 为 120 秒**（照搬 OpenCode 的超时上限），超过上限 MUST 报错。
- **FR-038**: 网络请求 MUST 使用**同步**客户端、每次新建连接（MUST NOT 持久化会话凭据）；MUST 有**显式超时**（默认 30 秒 —— 与 OpenCode 的默认超时一致）；MUST 支持请求方法与自定义请求头。
- **FR-039**: 网络工具的返回结果形状 MUST **冻结** —— "状态码""正文""响应头""最终地址"四个字段的名字与语义 MUST NOT 改动；MUST NOT 增加"成功 / 失败"二值字段。**（照搬 OpenCode 后的边界）**：返回结果只在**成功**（2xx + 文本 MIME + 未超体积上限）时产生 —— 非 2xx MUST **报错**而非返回正文（FR-089(d)），故"以状态码如实表达"的口径 MUST 收敛为"成功路径的返回形状冻结"，MUST NOT 被实现成"任何状态码都返回正文"。
- **FR-040**: 网络工具是**只读**工具 —— MUST NOT 产生变更记录（返回结果 MUST NOT 含变更记录字段），MUST NOT 落盘任何内容。
- **FR-041**: 网络异常（超时 / 网络 / 协议错误）MUST **透传**给调用方，MUST NOT 被吞掉或改写。**（与 FR-031 的口径差异是有意为之）**：命令工具的超时走"返回结构化标记"，网络工具的异常走"透传抛给调用方"；二者 MUST NOT 被统一成同一种行为。
- **FR-042**: 若将来支持"下载到文件"，MUST **新增独立的工具函数**并复用契约库的原子写与变更记录契约 —— MUST NOT 给现有的只读工具追加"顺手落盘"的副作用参数（会污染只读语义、破坏差异记录的可追溯性）。

#### `tools/` 支撑文件（实现要点 §4.4 / §4.5）

- **FR-043**: 系统 MUST 在工作区的 `tools/` 目录下生成包初始化文件，其正文 MUST 至少说明 —— 该包由初始化阶段自动生成、3 个内置工具模块位于此、契约库位于此且**不含**任何工具函数、用户可自行追加自己的工具模块。**MUST NOT** 在其中定义任何工具函数。
- **FR-044**: 系统 MUST 在工作区的 `tools/` 目录下生成工具开发规范文档；其初始正文 MUST 覆盖 ——（a）工具装饰器的官方导入位置；（b）函数必须有说明文字（作为工具描述）；（c）路径白名单由用户自管，donkey 不强制；（d）推荐的超时配置（命令工具默认 60 秒 / 网络工具默认 30 秒）；（e）错误处理建议（抛出具体的异常类型 / 返回结果中含错误字段）；（f）**工作区根的推导方式** —— 恒为"存放 `tools/` 的那个目录"，本套工具**不读取任何环境变量**（FR-104），移动 `tools/` 即会改变相对路径基准；（g）**契约库与用户自写工具是一套的** —— 强制重置**不会**覆盖工作区里已存在的契约库（FR-105），但契约库与你的工具必须版本匹配，重置 / 升级前请自行备份；（h）**网络工具需要用户自行安装 HTTP 客户端库**（该库是渲染进工作区的模板依赖，donkey 自身不携带、也不保证已安装 —— 缺库时导入即失败，须由用户在自己的工作区里安装）。
- **FR-045**: 工具开发规范文档 MUST 含一个"改文件的工具怎么写（变更记录契约）"小节，MUST 说明 ——（a）**必须**用契约库的原子写函数落盘，MUST NOT 直接覆盖写；（b）写前取旧字节、写后生成变更记录并放进返回结果的 `change` 字段；（c）变更记录的模式由契约版本冻结且**只增不改**、消费方按版本分派；（d）**MUST** 提供"声明期望指纹"的乐观锁（内置的写 / 复制 / 移动 / 删除四个改文件工具**均已提供** —— 用户自写工具 MUST 遵循此形态），并**建议**提供"只算不写"的预览开关（内置的写 / 复制 / 移动 / 删除四个改文件工具**均已提供**）；（e）落盘后把"已落盘"置真、预览模式保持为假；（f）**不要自己造指纹 / 差异逻辑** —— 契约库是全工作区唯一的变更记录产地。
- **FR-046**: 工具开发规范文档 MUST 明确说明契约库**是契约库、不是工具**（含 0 个工具函数，只被导入）；MUST NOT 引导用户往契约库里加工具函数。

#### Skills 示例三层（实现要点 §4.6）

- **FR-047**: 示例 Skill 的**第一层**头部元信息 MUST **恰含**名称与描述两个字段（宪法 D-07 —— MUST NOT 含任何自定义额外字段）；头部 MUST 以元信息分隔符开头。
- **FR-048**: 示例 Skill 的**第二层**正文主体 MUST 非空，且 MUST 讲清三层模型 —— 第一层头部元信息（并说明会被注册为独立工具）、第二层正文（模型调用第一层工具时返回）、第三层附属资源（由内置工具或引擎侧检索中间件读取）；正文 MUST 给出"如何按需使用第三层"的具体指引，且该指引中的**示例路径 MUST 以工作区根为基准**（与命令工具的工作目录基准一致 —— FR-032），MUST NOT 使用"相对 Skill 目录"的路径而未说明基准 —— 否则模型照抄示例会**跑不通**。

#### 异常、退出码与客户端映射（实现要点 §5）

- **FR-071**: 系统 MUST 定义内置工具生成类错误，归属 `donkey init` 的错误基类之下，并 MUST 对应退出码 `4`；异常层次 MUST 保持为 —— 总基类 ← `donkey init` 基类 ← {路径不存在（1）、路径权限（2）、模板生成（3）、内置工具生成（4）}。
- **FR-072**: 内置工具生成类错误 MUST 合并**两类**失败成因 ——（a）3 个内置工具文件写入失败；（b）示例 Skill 三层写入失败。二者对用户的修复动作相同（重装 donkey / 检查权限 / 重试 init），按奥卡姆剃刀 MUST 合并为**同一个**退出码 `4`，MUST NOT 各占一个码值。**本 Phase MUST NOT 在初始化阶段做"生成物导入预演"** ——（i）**工具导入验证是 `donkey load`（F002）的功能**，不在 `donkey init` 的职责内；（ii）3 个内置工具是稳定产物，MUST NOT 为其每次 init 都付出一次导入预演的算力代价；故源提示词 §5 退出码表中的第三类成因"集成预演导入失败"**在本 Phase 不成立**（本条取代该口径）。生成物的可导入性由两处分别承担：本 Phase 的**集成测试层**（`tests/integration/test_init_to_load.py` —— 生成器自身的回归测试，**非产品能力**）与 F002 的 `donkey load`（**用户可见的导入验证能力**）。
- **FR-073**: 客户端的异常 → 退出码映射 MUST 由**单一全局映射表**驱动，MUST **追加一行**"内置工具生成类错误 → 退出码 `4`"；其余异常处理逻辑 MUST NOT 因此改动（按类型查表自动生效）；客户端层 MUST NOT 因本 Phase 引入任何智能体框架的导入（宪法 N-04）。

#### 全局约束与治理口径（实现要点 §8 / §9）

- **FR-076**: 生成的工具文件 MUST NOT 含任何 Python 入口文件形态、 MUST NOT 含子智能体相关目录或字段、 MUST NOT 含任何智能体框架的可观测性后端相关内容（宪法 N-01 / N-02 / N-12）。
- **FR-077**: 工具装饰器的官方导入 MUST 仅出现在**渲染进用户工作区**的产物中；donkey 自身的核心层与客户端层 MUST NOT 引入该导入（宪法 N-04 / N-12 / D-17）。
- **FR-078**: 本 Phase MUST 遵守"禁止使用任何智能体框架的可观测性后端"的约束边界 —— 该约束的对象是 **donkey 自有代码路径**（核心层 / 客户端层）的导入与使用；渲染进用户工作区的产物属**用户代码路径**，donkey 自身 MUST **永不**导入它。**该边界推理 MUST 在本 spec 中显式登记**（否则按门禁冒烟口径复核时会误判为门禁失败）；同时门禁冒烟 MUST 限定为"donkey 自有代码路径"的导入链，MUST NOT 拿"用户导入渲染产物"的语境去复核它。
- **FR-079**: 渲染产物本身 MUST NOT 含任何可观测性后端相关字样（工作区侧的持久不变量）。
- **FR-080**: 依赖归属 MUST 写清 —— HTTP 客户端是**渲染进用户工作区**的**模板依赖**（用户在自己的工作区里跑网络工具时才需要），**donkey 自身的运行期依赖 MUST 仍恰为 1 个**（不得因本 Phase 而变为 2 个）；HTTP 测试用的拦截库 MUST 声明为**开发期依赖**（MUST NOT 进运行期依赖）。
- **FR-081**: 本 Phase MUST **不**引入任何智能体框架中间件挂载（宪法 §2.7 的 10 项录用中间件属另一个阶段）、MUST NOT 触发模型连通性测试、MUST NOT 构造记忆库结构、MUST NOT 实施任何配置静态检查。
- **FR-082**: 本 Phase MUST NOT 实现差异审阅界面 / 人工审批 / 回滚流程（MUST NOT 在工作区内出现任何差异审阅入口）—— **交出变更原材料 ≠ 实现审阅流程**，本 Phase 交付的变更记录 MUST NOT 被理解为已实现审阅能力（业务验收 AC-5）。
- **FR-083**: 本 Phase MUST NOT 把命令工具造成的文件副作用纳入变更记录（命令绕过工具的写路径）—— 该缺口 MUST 以**文档化口径**满足（写进工具说明文字），MUST NOT 试图拦截。
- **FR-084**: 本 Phase MUST NOT 在契约库中新增任何工具函数；MUST NOT 实现三方合并 / 冲突解决 / 补丁应用算法；MUST NOT 在文件工具中实现检索能力。
- **FR-085**: 本 Phase MUST NOT 触碰三个记忆库文件，MUST NOT 在初始化阶段做记忆库结构健康检查。
- **FR-086**: 本 Phase 的交付物 MUST 通过静态检查（代码规范 + 类型检查）且零 error。
- **FR-087**: 本 Phase MUST 保持 `donkey init` 的幂等性契约 —— 重复执行 MUST NOT 破坏已存在文件；带强制标志时其作用域 MUST 严格限定在清单条目内（清单外的一切路径 MUST NOT 被删除或改写），**唯一例外是契约库**（FR-105）。
- **FR-088**: 本 Phase MUST NOT 对客户端引入除"异常映射表追加一行"之外的任何行为变更。

- **FR-089**: 网络工具 MUST 照搬 OpenCode 的访问边界 ——（a）**协议白名单**：MUST 只允许 http / https 两种协议，其它协议 MUST 报错（OpenCode 的协议校验）；（b）**响应体上限 5 MiB**：MUST 先依据响应声明的长度判断是否超限，再在读取响应体的过程中持续守住上限，超限 MUST 报错（OpenCode 的 5 MiB 响应体上限 + 流式收集上限）；（c）**非文本 MIME MUST 拒绝**；（d）**非 2xx MUST 报错**，MUST NOT 返回正文。MUST NOT 实现任何形式的地址范围限制（黑名单 / 白名单 / 代理 / 沙箱）—— OpenCode 本身不限制目标地址，其"哪些地址可访问"的判断由**引擎层的权限机制**承担，而 donkey v1 无该机制（宪法 §2.1：权限交互属引擎层能力）。本条取代本 Phase 初稿的"网络侧完全不限制"口径（见 Clarifications 的 Q3 → Q4 决策演进）。
- **FR-090**: 网络工具的说明文字 MUST **逐条写明** FR-089 的四项边界（协议白名单 / 响应体上限 / 非文本拒绝 / 非 2xx 报错）及其触发后果，使用户知情；MUST NOT 保留任何与实际行为不符的措辞。**注**：初稿"显式写明不限制协议与地址"的条款已被 Q4 覆盖 —— 改写为"显式写明已施加的边界"。
- **FR-091**: 契约库含 **0** 个工具函数（FR-001）—— 未来的工具扫描器 MUST 容忍"**无 `@tool` 的辅助模块**"（`tools/__init__.py` 已是同类先例）；该兼容性 MUST 作为**风险登记项**写进本 spec（见 Edge Cases「其它边界」），MUST NOT 被实现为"每个 `tools/*.py` 至少含 1 个 `@tool`"的假设，更 MUST NOT 通过给契约库塞一个工具函数来"凑数"。

**读取侧体积与分页契约（`/speckit.clarify` 追加 · 完全照搬 OpenCode）** —— 依据：OpenCode 上游开发分支的文件系统读取实现与读取工具呈现层（双上限常量、分页实现、给模型的呈现格式构造）。

- **FR-092**: 读取 MUST 受**双上限**约束 —— 单次返回的行数上限为 **2000**（OpenCode 的行数上限），单次返回的字节数上限为 **50 KiB**（OpenCode 的字节上限），**二者先到者生效**。MUST NOT 以"只限行数"或"只限字节"替代 —— 行数上限挡"行短但极多"，字节上限挡"行少但极长"。
- **FR-093**: 单行长度 MUST 有 **2000 字符**上限（OpenCode 的单行上限）；超出的行 MUST 被截断并附显式标记 `... (line truncated to 2000 chars)` —— 截断 MUST **留痕**，MUST NOT 静默砍掉（模型不得把被截断的行当完整内容）。
- **FR-094**: 读取结果 MUST 以 OpenCode 的**呈现格式**交给模型 ——（a）首行 MUST 是页范围说明头（文件形如 `Read file {路径}, lines {起始}-{结束}`，空内容时形如 `Read file {路径}, 0 lines`）；（b）每一行 MUST 带 `<行号>: ` 前缀（前缀仅供模型引用，MUST NOT 被当作文件内容）；（c）截断时 MUST 在末尾附续读提示 `[Output truncated. Continue reading with offset: N]`，其中 `N` 是**下一段的起始行号**。MUST NOT 只回一句"内容太长"而不给续读指引。呈现文本中的路径 MUST 使用**调用方传入的路径字符串**（与 OpenCode 一致），MUST NOT 换成解析后的绝对路径。
- **FR-095**: 小文件（体积 ≤ 50 KiB **且 行数 ≤ 2000** **且** 调用方未指定起始行 / 行数）MUST 走**整份返回**（"整份返回"= 分页代码路径在**未发生截断**时的自然退化 —— 见 FR-098(d)，行数上限**无条件**生效）；其余情形（体积 > 50 KiB，或行数 > 2000，或调用方指定了起始行 / 行数）MUST 走**分页返回**。分页时起始行缺省为 **1**，请求的行数 MUST 被截到 **2000** 行。
- **FR-096**: 内容含 NUL 字节的文件 MUST 被判定为二进制并**明确报错**（OpenCode 的二进制拒绝口径），MUST NOT 把乱码当作正文返回给模型；图片 / PDF 等媒体文件 MUST 同样**明确报错**（donkey 的工具函数只能返回文本，无法交付多模态附件 —— 多模态附件属引擎层能力，见 Edge Cases「其它边界」的已知缺口登记）。`read_file` 遇到**目录**时 MUST 按 OpenCode 的目录分支呈现（首行 `Read directory {路径}, entries {起始}-{结束}`，每行一个条目，截断时同样附续读提示）。
- **FR-097**: `list_dir` MUST 保持返回 `list[str]`（源提示词明确冻结该返回类型，MUST NOT 改为 JSON 对象）；其分页 MUST 由新增的**可选**参数承载 —— 签名 MUST 为 `list_dir(path, include_hidden=True, offset=0, limit=None)`：`offset` 为 **0 基**（跳过 N 个条目；因返回类型被冻结、无 `next` 字段可依，0 基切片偏移是 Python 惯例）、`limit` 为最多返回的条目数（上限 **2000**，与 OpenCode 的行数上限一致；`limit` 超过 2000 时 MUST **截断到 2000**、MUST NOT 报错 —— 与 FR-092 读取侧"截断"口径一致）；且 MUST NOT 改动既有参数 `include_hidden` 的语义。因返回类型被冻结，`list_dir` MUST NOT 承载"已截断 / 续读位置"字段 —— 该指引 MUST 由 `read_file` 的目录分支（FR-096）与工具说明文字共同承载。
- **FR-098**: 上述读取侧契约 MUST 与 OpenCode 保持**行为等价**，而非仅"有上限" —— 任何一项偏离 MUST 在本 spec 中显式登记并说明理由；已知的**五处**有意偏离为 ——（a）`list_dir` 返回类型冻结（FR-097）；（b）媒体文件不支持多模态附件（FR-096）；（c）网络工具**不**把 HTML 转成 Markdown（那会要求工作区引入 HTML 解析依赖，donkey 保持返回原始正文）；（d）**行数上限无条件生效** —— OpenCode 的"整份返回"路径不套行数上限（其行数上限仅在分页路径生效），而本 spec 的 FR-092 要求双上限**先到者生效**且**无条件**适用 → 行数多但体积 ≤ 50 KiB 的文件在本 Phase **仍会被截断**并给出续读指针（收紧方向，绝不会让模型拿到超预期体积的上下文）；（e）`list_dir` 的排序为**名称代码点序**（与源提示词模板正文一致）—— OpenCode 用"目录优先 + 本地化序"，后者是它的**呈现层（UI）**选择，且 `localeCompare` 的结果依赖运行环境 locale（跨机器不稳定）。除这五处外，MUST NOT 自行增删 OpenCode 的边界项。

**工具输出的统一上限（`/speckit.clarify` 追加 · 完全照搬 OpenCode）** —— 依据：OpenCode 上游开发分支的统一工具输出截断服务 —— OpenCode 由**引擎层**的同一套服务对**所有工具输出**施加同一组上限（2000 行 / 50 KiB），read 与 shell 共用。

- **FR-099**: 工具输出的体积上限 MUST 是**一组统一常量** —— 行数上限 **2000**、字节上限 **50 KiB**，**读取侧与命令输出侧 MUST 共用同一组数值**（OpenCode 的统一输出上限常量），MUST NOT 各设一套；两者先到者生效。
- **FR-100**: 命令输出超限时 MUST 截断，MUST 在返回结果中把 `truncated` 置为**真**（未截断时为**假** —— 该字段为**新增**，既有字段语义不变，符合只增不改），并 MUST 在输出末尾附 OpenCode 式的标记 `[showing lines 1-{已保留行数} of {总行数}; full output not saved]`。
- **FR-101**: 完整命令输出 MUST **不落盘** —— 材料层 MUST NOT 把完整输出写入用户工作区、临时目录或任何引擎层目录；MUST NOT 为此新增清单条目（FR-052 的 8 条追加 MUST 保持不变）。模型取剩余部分 MUST 自行改跑更窄的命令（donkey 的命令是显式参数数组，不经命令解释器，故管道 / 重定向不可行，但改跑分页类程序可行）。
- **FR-102**: 命令工具的说明文字 MUST 建议模型"**依赖自动截断**，除非自行过滤输出更划算"（照搬 OpenCode 的工具说明口径）。
- **FR-103**: 因本 Phase MUST NOT 新增清单条目（FR-052），各工具模块 MAY 各自定义该组常量的本地副本，但**数值 MUST 与本 spec 逐字一致**，且单元测试 MUST 断言读取侧与命令输出侧两处数值相等（防止将来漂移）。

- **FR-104**: 本 Phase 生成的**全部工具模块** MUST **不**读取任何环境变量来决定自身行为（路径基准、超时、开关、模式选择等一律 MUST NOT 受环境变量影响）—— 用户原则"**智能体不允许被环境变量所影响**"。工作区根 MUST 恒为"存放 `tools/` 的那个目录"（FR-002）；MUST NOT 依赖进程当前目录 / HOME / 属主隐藏目录约定来推导任何行为（宪法 §2.2 路径绝对化原则的延伸）。**边界**：命令工具启动的子进程**继承**父进程环境（操作系统标准行为，`PATH` 等必需），该继承 MUST NOT 被视作对本条的违反；但工具自身 MUST NOT 读取继承来的环境变量来决定行为。
- **FR-105**: **契约库豁免于强制重置** —— 带强制标志执行时，一旦工作区中**已存在**契约库，MUST **保留其原样**（MUST NOT 覆盖、MUST NOT 删除后重建、MUST NOT 因其内容与出厂版本不同而改动它）；契约库**不存在**时，MUST 按出厂内容正常创建（与"无则增"通则一致）。理由：契约库与用户自写工具是**一套**的（用户工具 import 它），它已属"用户材料"而非"出厂模板"，覆盖它等于单方面毁掉用户代码的依赖。**本条是本 Phase 对 F001-P2 通则"带强制标志时清单内文本条目先删后重建"的**唯一一处例外**，仅适用于契约库一个条目 —— MUST NOT 削弱该通则对其余全部条目的成立（FR-069）。`tools/README.md` MUST 说明"契约库与你的工具是一套的，重置前先备份"（FR-044）。

### Key Entities

- **内置工具函数（9 个）**：`filesystem.read_file` / `write_file` / `copy_file` / `move_file` / `delete_file` / `list_dir` / `stat`（文件工具，7 个）+ `commandline.run_shell`（命令工具，1 个）+ `webfetch.fetch_url`（网络工具，1 个）；每个都有完整的说明文字（工具框架以其作为工具描述），全部由初始化阶段渲染进工作区，用户可编辑 / 删除。
- **变更记录契约库**：`tools/changes.py` —— 全工作区**唯一**的变更记录产地，含 **0** 个工具函数；对外暴露 9 个公开函数 + 1 个异常类 + 3 个冻结常量；内置工具与用户自写工具 MUST 复用它（MUST NOT 各造一套）。
- **变更记录**：一次文件变更的"原材料"，含 **12** 个必现基线字段（契约版本 / 动作 / 绝对路径 / 相对路径 / 旧存在标记 / 旧字节数 / 旧指纹 / 新字节数 / 新指纹 / 统一差异文本 / 差异是否截断 / 是否已落盘）+ 4 个条件字段（源路径 / 源相对路径 / 旧正文 / 旧正文是否被省略）；其契约版本当前为 `1`，**只增不改**。
- **变更动作（5 种）**：创建 / 更新 / 删除 / 复制 / 移动 —— 是变更记录的"动作"字段取值；每种动作下 12 个基线字段 MUST 全部存在。
- **四条硬规则（R-D1 ~ R-D4）**：（R-D1）**原子写** —— 写到一半失败 MUST NOT 把旧文件截成半截；（R-D2）**不丢旧内容** —— 写前 MUST 记下旧内容的指纹与体积；（R-D3）**可预览** —— MUST 支持只算不写；（R-D4）**并发安全** —— MUST 支持乐观锁，避免覆盖他人改动。**R-D3 与 R-D4 的覆盖范围**：MUST 覆盖**全部四个**改文件的工具 —— 写文件 / 复制 / 移动 / 删除（FR-013 / FR-019 / FR-020）。**为何材料层自带 R-D3**：OpenCode 的工具层不带预览能力，是因为它**有**引擎层差异预览 + 人工确认兜底；donkey v1 不做那一层（AC-5），故 MUST 由材料层补上。
- **文件已变更异常**：契约库定义的乐观锁失败异常 —— 调用方声明的期望指纹与磁盘现状不符时抛出，调用方应重读后重试而非覆盖。**覆盖范围**：写 / 复制 / 移动 / 删除**四个**改文件的工具**均**支持期望指纹（FR-013 / FR-019）。
- **内置工具生成类错误**：内置工具与示例 Skill 生成失败的统一错误类，归属 `donkey init` 错误基类，对应退出码 `4`；合并**两类**失败成因（3 个内置工具文件写入失败 + 示例 Skill 三层写入失败 —— 二者对用户的修复动作相同，按奥卡姆剃刀合并为一个码值）。**不含**"导入预演失败"（本 Phase 不做导入预演，见 FR-072）。
- **Skills 三层模型**：第一层（头部元信息，名称 + 描述两字段必填，被注册为独立工具）/ 第二层（正文主体，模型调用第一层工具时返回）/ 第三层（附属资源，由内置工具或引擎侧检索中间件按需读取）—— 示例 Skill MUST 三层齐备。
- **模板清单**：donkey 维护的"模板文件清单"，位于安装包内；本 Phase 追加 8 条后累计 **54** 条（45 个文本型 + 3 个数据库型 + 6 个目录型），是渲染的依据。
