## Clarifications

### Session 2026-10-21

- Q: 用户少写参数时（`donkey init` 没给路径 / `donkey` 没写子命令）命令应该返回哪个退出码？ → A: C —— 参数用法错误一律归入退出码 `1`（与"路径 / 输入不合法"同族），退出码 `2` 严格只表示权限不足；不占用 v1.x 预留码 5-10。
- Q: `donkey init` 的 `--name` 参数要保留吗？ → A: 不保留 —— CLI 只接受 `<PATH>` 与 `--force`；workspace 名称一律取路径末段（basename），避免"路径说一套、名字说另一套"造成的身份混淆。
- Q: 名字若由路径派生，还需要校验其合法性吗？ → A: 不校验 —— 与立项书"v1 不引入 workspace 路径 basename 命名约束"一致，basename 允许任意字符（含 `-` / `.` / 空格 / Unicode）。
- Q: 验收脚本用什么方式调用 `donkey` 命令？ → A: 优先调用 PATH 上的 `donkey`，不可用时回落到以当前解释器执行模块入口（`python -m donkey`）；两种方式 MUST 产生完全相同的退出码与文件系统副作用。
- Q: 验收脚本的场景数取 6 个还是 7 个？ → A: 7 个 —— 在提示词枚举的 6 个场景之外补 1 个"名称派生与结果摘要回显"场景（覆盖本次"名称恒取路径末段"的决策），与 F001-P3 提示词中"F001-P1 的 7 个 verify 断言"口径对齐。
- Q: 当 path 解析后末段名为空时（文件系统根 `/`、盘符根 `D:\`、UNC 共享根），`donkey init` 应该怎么表现？ → A: A —— 判定为路径类错误，退出码 `1`；规则表述为"解析后末段名为空 ⇒ 路径非法"，一次覆盖所有根形态，不逐个枚举。
- Q: 宪法 §4.6 的"单元测试覆盖率 ≥ 80%（`donkey.core`）"应落在哪一层？ → A: 落 spec —— 追加 SC-016 作为 Success Criteria，再由 plan 增第 12 个门（G12）、tasks 增覆盖率任务与 `pytest-cov` 依赖；覆盖率以独立命令度量，不写入 pytest 全局 `addopts`。
- Q: 澄清决策 3（basename 字符合法性不校验）如何进入追溯矩阵？ → A: 不新增 FR 编号 —— 由 FR-003 补一条 MUST 子句承载，并在 US7 增验收场景 4、FR-024 增一条测试类别作为落点。
- Q: SC-012「100% 的失败场景都要有下一步」由哪一层承载？未登记异常子类的兜底是否也要带下一步？ → A: 落 FR 层 —— 扩写 FR-019（不新增 FR 编号），适用面限定为面向用户的三类失败（路径类 / 权限类 / 参数用法类）；未登记 `WorkspaceInitError` 子类的兜底属内部防御路径，不强制带下一步；SC-012 同步限定为这三类，US2 / US3 验收场景原地追加对应断言。

### User Story 1 - 新建 workspace 根目录 (Priority: P1)

用户在自己的机器上敲一条 `donkey init <路径>`，希望 donkey 立刻在指定位置建立 workspace 根目录并明确回报成功，**不需要**阅读任何文档就知道该命令已经生效。

**Why this priority**: 这是 `donkey init` 唯一不可替代的价值——"把 workspace 落地"。其它故事（错误分支、幂等、命名）都是围绕它的保护与修饰；没有 P1，整个 F001 没有任何可用产物。

**Independent Test**: 可独立验证——对一个新路径执行 `donkey init <路径>`，命令以成功状态结束且该目录出现在文件系统中（不需要任何模板内容即可判定通过）。

**Acceptance Scenarios**:

1. **Given** 一个尚不存在、但其父目录已存在的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以成功状态结束（退出码 `0`），且该目标路径成为真实存在的目录。
2. **Given** 一个尚不存在、但其父目录已存在的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令输出一行结果摘要，其中包含 workspace 的**绝对路径**与**名称**，其中**名称取该路径的末段名**（与 spec US7 的 Given/When/Then 场景 1 同一口径：US1 只交付这条最小派生，US7 负责其边界收紧 —— 不校验、不提供第二命名来源）。

---

### User Story 2 - 路径不合法时给出明确指引 (Priority: P2)

用户给出的路径写错了（比如父目录根本不存在，或路径里混进了非法字符）。此时 donkey **不应该**在其它位置偷偷建目录，也**不应该**抛出一大段看不懂的堆栈，而应明确告诉用户"路径有问题"并把可执行的修复动作讲清楚。

**Why this priority**: 失败路径的可用性与成功路径同等重要——用户第一次上手时写错路径是高频场景；若报错含糊，用户无从判断是路径问题还是权限问题，也无法自助恢复。

**Independent Test**: 可独立验证——对父目录不存在的路径执行 `donkey init`，命令以路径类失败状态结束（退出码 `1`），错误输出出现在标准错误流中且能读出"父目录不存在"或对应错误类别名。

**Acceptance Scenarios**:

1. **Given** 一个父目录不存在的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `1` 结束，且**不会**创建任何目录（包括缺失的父目录）。
2. **Given** 一个父目录不存在的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 标准错误输出中包含可识别的路径类错误标识（错误类别名或"父目录不存在"字样），且包含一条用户可执行的下一步（建目录 / 换路径）。
3. **Given** 一个包含非法字符的路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `1` 结束，并按路径类错误报告，不产生未捕获的异常堆栈。
4. **Given** 文件系统根目录本身（`/` 或盘符根），**When** 用户执行 `donkey init <根目录>`，**Then** 命令以退出码 `1` 结束（workspace 不能建在根上），且根目录下**不**出现任何新建内容。

---

### User Story 3 - 权限不足时说清缺哪种权限 (Priority: P3)

用户的目录权限被其它程序收紧（父目录只读、目标目录不可写等），导致 workspace 建不出来。用户需要知道**到底缺哪种权限、对哪个路径缺**，才能自己动手修，而不是只知道"失败了"。

**Why this priority**: 权限问题在共享服务器 / 受管环境里非常常见；笼统的"权限错误"会把排查成本转嫁给用户。这条是"可自助恢复"体验的另一半。

**Independent Test**: 可独立验证——把父目录设为只读后执行 `donkey init`，命令以权限类失败状态结束（退出码 `2`），且错误输出中同时出现缺失的权限种类与对应路径。

**Acceptance Scenarios**:

1. **Given** 一个只读的目标父目录，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `2` 结束，且不创建任何目录。
2. **Given** 任何权限不足的路径，**When** 命令报错，**Then** 错误输出同时指明"缺失的权限种类"（读 / 写 / 执行）与"对哪个路径缺失"，且包含一条用户可执行的下一步（调整权限）。

---

### User Story 4 - 重复执行不报错、不破坏 (Priority: P4)

用户会反复执行 `donkey init`（脚本化、换配置后重跑、忘了有没有跑过）。已存在的 workspace **不是错误**，用户的内容**一个字节都不能被改动**。

**Why this priority**: 幂等性是 `donkey init` 的核心契约（业务验收 AC-3）——一次误伤用户已有内容就会让用户不再信任这个命令。它虽排不到 P1/P2，但它是"可以放心反复跑"的前提。

**Independent Test**: 可独立验证——先建立 workspace 并放入用户文件，再对同一路径执行 `donkey init`，命令以成功状态结束（退出码 `0`），且用户文件内容与修改时间均未变化。

**Acceptance Scenarios**:

1. **Given** 一个已存在的 workspace 目录，**When** 用户不带 `--force` 执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，**不**报"已存在"类错误。
2. **Given** 一个已存在的 workspace 目录（内含用户自建文件），**When** 用户执行 `donkey init <该路径>`，**Then** 已有文件的内容与修改时间保持不变。

---

### User Story 5 - `--force` 先被"记住"但不误伤 (Priority: P5)

用户希望"恢复到出厂状态"，于是加上 `--force`。在本阶段，`--force` 只是一个被记录下来的意图，**尚未**接入重置逻辑；用户不会因为它而在现阶段丢掉任何内容。

**Why this priority**: `--force` 语义在后续阶段（模板重置）才完整兑现。本阶段必须保证它"被接受、被记录、不误伤"，否则后续阶段接入重置时才会暴露契约缺口。

**Independent Test**: 可独立验证——对已存在的 workspace 执行 `donkey init <该路径> --force`，命令以退出码 `0` 结束，且已有内容未被删除或覆盖。

**Acceptance Scenarios**:

1. **Given** 一个已存在的 workspace 目录，**When** 用户执行 `donkey init <该路径> --force`，**Then** 命令以退出码 `0` 结束。
2. **Given** 同一个已存在的 workspace 目录，**When** 用户执行 `donkey init <该路径> --force`，**Then** 已有内容既未被删除也未被覆盖（本阶段不执行重置）。
3. **Given** 任意一次成功的 `donkey init`，**When** 用户查看结果摘要，**Then** 摘要中能看出本次是否带了 `--force`。

### User Story 6 - 清楚知道"这一步只到哪" (Priority: P6)

用户运行完 `donkey init` 后，需要知道这个阶段交付了什么、没交付什么——避免他以为"init 完了却找不到任何配置文件"是 bug。

**Why this priority**: 范围边界是本阶段最容易引起误解的点（模板内容属后续阶段）。把它显式写进契约，能让验收口径清晰、让用户预期与实现对齐。

**Independent Test**: 可独立验证——对一个全新路径执行 `donkey init`，得到的目标路径是一个目录；不要求其中出现任何模板文件；且模板清单 / 模板源缺失不会让本阶段失败。

**Acceptance Scenarios**:

1. **Given** 任何合法路径，**When** 用户执行 `donkey init <该路径>`，**Then** 结果中"模板条目数 / 新建文件数 / 跳过文件数"三个计数均为 `0`，且目标路径是一个目录。
2. **Given** 模板清单或模板源文件缺失 / 损坏，**When** 用户执行 `donkey init`，**Then** 本阶段**不**因此失败（模板内容生成不在本阶段职责内）。
3. **Given** 任意一次成功的 `donkey init`，**When** 用户查看结果摘要，**Then** 摘要中的模板相关计数明确为 `0`，不暗示"已生成模板"。

### User Story 7 - workspace 的名字就是它的位置 (Priority: P7)

用户只需要给一个路径，workspace 就有了唯一的名字——**路径的最后一段**。不存在"路径叫 A、名字叫 B"的情况，用户回头看任何一个 workspace，永远能凭名字和路径互相印证。

**Why this priority**: 名字会在后续阶段被写进 README 标题、provider 配置注释和 workspace manifest，名字与路径必须始终一致，否则用户会怀疑"我建的是哪个"。这条不阻断"能不能建目录"的主线，故排在最后。

**Independent Test**: 可独立验证——对任意路径执行 `donkey init`，结果中的 workspace 名称等于该路径的末段名；且命令不接受任何额外的命名参数（传入即失败）。

**Acceptance Scenarios**:

1. **Given** 任意合法路径，**When** 用户通过**命令行**执行 `donkey init <路径>`，**Then** 结果中的 workspace 名称等于该路径的末段名称（命令行通道不存在第二个命名来源）。
2. **Given** 任意合法路径，**When** 用户执行 `donkey init <路径>`，**Then** 命令只接受路径与强制开关两个参数；用户额外传入命名类参数时 MUST 以退出码 `1` 失败（不静默忽略）；且错误输出含用法提示（usage）作为一条用户可执行的下一步（spec FR-019 / SC-012 的参数用法类）。
3. **Given** 任意一次成功的 `donkey init`，**When** 用户查看结果摘要，**Then** 摘要同时给出 workspace 的**绝对路径**与**名称**，且二者相互印证。
4. **Given** 一个末段名含空格或 Unicode 字符的合法路径（如 `.../我的 工作区`），**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，且结果中的 workspace 名称**原样等于**该末段名（不校验、不改写、不拒绝）。

### Edge Cases

**路径类（归入退出码 `1`）**

- 父目录不存在（含多级父目录全部缺失）→ 报"父目录不存在"；**MUST NOT** 自动补建缺失的父目录。
- 相对路径且以进程工作目录为基准解析后父目录仍不存在 → 同样按路径类错误处理。
- 路径中含 NUL 字节等非法字符 → 按路径类错误处理，不产生未捕获异常堆栈。
- 目标路径已存在但**不是目录**（是一个普通文件）→ 按路径类错误处理，不静默"成功"，不覆盖该文件。
- 父目录存在但本身是文件 → 按路径类错误处理。
- 目标是一个指向不存在目标的悬空符号链接 → 按路径类错误处理。
- 路径超出操作系统长度限制 → 按路径类错误处理。
- 传入空字符串路径 → 按路径类错误处理（不得把进程工作目录误当成 workspace 根）。
- 路径解析后末段名为空（文件系统根 `/`、盘符根 `D:\`、UNC 共享根，以及 `/.`、`//` 等等价写法）→ 按路径类错误处理（退出码 `1`）；根目录的"父目录"就是它自己且存在，因此**必须**靠"末段名为空"这条判据拦住，MUST NOT 在根目录创建任何内容。
- 目标已存在（合法目录）→ **不是**错误：路径校验与权限校验通过即成功。

**权限类（归入退出码 `2`）**

- 目标尚不存在时，父目录缺失写权限 → 报"写权限缺失"。
- 目标尚不存在时，父目录缺失执行权限 → 报"执行权限缺失"（无法在其中创建子项）。
- 目标已存在时，目标自身缺失读 / 写 / 执行权限中的任意一种 → 报对应权限缺失。
- 权限判定以**当前运行用户的实际访问能力**为准；`0o555` 目录不含任何写位，按 POSIX 语义**即使以特权账号（如 root）运行 `os.access(dir, W_OK)` 亦为 False**，故权限断言**不依赖特权账号**，验收以只读目录模拟为准（`research.md` R-04）。

**其它边界**

- 参数用法错误（缺少子命令 / 缺少必填位置参数 / 未知子命令或未知参数，含用户误传命名类参数）→ 归入退出码 `1`（与"路径 / 输入不合法"同族），错误输出须附用法提示；MUST NOT 复用退出码 `2`（`2` 严格只表示权限不足）。
- `--force` 与已存在 workspace 组合 → 本阶段成功且不重置。
- 目标路径带尾部分隔符（如 `.../ws/`）→ 名称取解析后的末段目录名，与不带分隔符等价。
- 库 API 被程序化调用时若显式传入空名字 → 视为未指定，回落为路径末段名（CLI 不暴露该入口）。
- 库 API 被程序化调用时若显式传入非空名字 → 采用该名字作为 workspace 名称（CLI 通道不可达此路径）。
- 路径末段含 `-` / `.` / 空格 / Unicode 等任意字符 → 一律接受，不校验命名合法性（与立项书"v1 不引入 basename 命名约束"一致）。
- 同一路径被并发执行 → 不在本阶段职责范围内。
- 模板清单 / 模板源文件缺失或损坏 → **不**在本阶段失败面内（属后续阶段的模板类错误码）。

> **明确排除**：模板清单损坏 / 模板渲染失败 / 内置工具生成失败 —— 这三类属 F001-P2 / F001-P3 的错误码域，本阶段不加载清单、不渲染内容，因此不会触发。

## Requirements *(mandatory)*

### Functional Requirements

#### 核心库 API（实现要点 §4.1）

- **FR-005**: 系统 MUST 提供核心库门面 API `init_workspace(path, name=None, force=False) -> InitResult`；`path` MUST 接受字符串与路径对象两种形态并在内部统一解析为绝对路径；`name` 缺省为 `None` —— 此时名称取解析后路径的末段名；显式传入**非空字符串**时 MUST 以该值为准；传入空字符串视为未指定 —— MUST 回落为解析后路径的末段名；v1 的 CLI 通道 MUST NOT 传入该参数（命令行通道的名称恒由路径派生）；`force` 缺省为假值。
- **FR-006**: `init_workspace` MUST 返回一个不可变的结果对象，其字段与顺序固定为：`workspace_path`（workspace 绝对路径）、`name`（workspace 名称；名称定夺规则见 FR-005）、`force`（是否请求强制重置）、`templates_loaded`（模板清单条目数）、`files_created`（本次新建文件数）、`files_skipped`（已存在而跳过的文件数）。该契约是后续阶段共同依赖的稳定接口，字段语义不得在本阶段之后无版本号变更。
- **FR-007**: 本阶段的结果对象中，`templates_loaded` / `files_created` / `files_skipped` MUST 均为 `0`（本阶段只创建根目录，不加载清单、不写文件）。
- **FR-008**: 校验通过后系统 MUST 创建 workspace 根目录；目标已存在时 MUST NOT 报错，MUST NOT 视为失败。
- **FR-009**: 系统 MUST NOT 自动创建缺失的父目录——父目录缺失属于用户需修复的路径问题（退出码 `1`）。

#### 核心逻辑与校验（实现要点 §4.2）

- **FR-010**: 路径解析 MUST 产出绝对路径；相对路径以进程工作目录为解析基准解析一次，此后 workspace 内部的一切相对引用 MUST 以该绝对路径为唯一根（宪法 §2.2 路径绝对化原则）。
- **FR-011**: 当目标路径的父目录不存在时，系统 MUST 抛出路径类错误（`PathNotFoundError`）→ 退出码 `1`。
- **FR-012**: 当路径解析后的末段名为空时（文件系统根 `/`、盘符根 `D:\`、UNC 共享根等一切根形态），系统 MUST 抛出路径类错误（`PathNotFoundError`）→ 退出码 `1`，并 MUST NOT 在根目录创建任何内容。该规则 MUST 以"末段名为空"这一平台无关判据表达，MUST NOT 依赖对具体根形态的逐个枚举；名称的抽取 MUST 基于路径对象的末段名属性，MUST NOT 以手写字符串切分实现（后者会把盘符误判为名字）。
- **FR-013**: 当路径含非法字符（如 NUL 字节）时，系统 MUST 抛出路径类错误（`PathNotFoundError`）→ 退出码 `1`。
- **FR-014**: 权限校验 MUST 区分两种情形——目标尚不存在时校验**父目录的写权限 + 执行权限**（能否在其中创建子项）；目标已存在时校验**目标自身的读 + 写 + 执行权限**（读、写、进入目录均依赖执行位）。任一权限不足 MUST 抛出权限类错误（`PathPermissionError`）→ 退出码 `2`。
- **FR-015**: 权限类错误信息 MUST 同时包含"缺失的权限种类"（读 / 写 / 执行）与"对哪个路径缺失"，以便用户自助修复。
- **FR-016**: 校验类能力 MUST 无副作用：MUST NOT 写文件、创建目录或改动任何状态（失败一律以异常表达）；`check_path` MUST 返回解析后的绝对路径（可被调用方直接使用）；`check_permission` MUST 无副作用，其判定结果通过**正常返回**（权限充足）或**抛出 `PathPermissionError`**（权限不足）表达。
- **FR-017**: 系统 MUST 提供一个综合校验入口，串联"路径解析 → 权限校验 → 名称定夺"，并向调用方交付三元组（绝对路径、最终名称、强制标志）；名称定夺规则见 FR-005（`name` 为 `None` 或空串时取解析后路径的末段名，`name` 为非空串时采用该值）；CLI 入口 MUST NOT 提供任何命名输入通道（命令行场景下名称恒由路径末段派生）；路径解析后末段名为空的路径仍 MUST 按 FR-012 拒绝；该入口 MUST NOT 把"目标已存在"当作错误（幂等设计）。

#### CLI 入口（实现要点 §4.3）

- **FR-001**: 系统 MUST 提供 `donkey init` 命令入口；本阶段 `init` 是唯一注册的子命令；未指定子命令时 MUST 以退出码 `1` 失败（退出码映射口径见 FR-018），并在错误输出中附上用法提示。
- **FR-002**: `init` MUST 接受一个必填位置参数作为 workspace 目录路径（绝对或相对均可）；缺失该参数 MUST 以退出码 `1` 失败（退出码映射口径见 FR-018），并在错误输出中附上用法提示。
- **FR-003**: `init` 的参数面 MUST 仅含两个参数——必填位置参数 `path` 与布尔开关 `--force`；MUST NOT 提供 `--name` 或任何等价的独立命名参数。workspace 名称 MUST 一律由路径末段派生，MUST NOT 存在"路径与名称可以各说各话"的入口。末段名的**字符合法性 MUST NOT 被校验**——`-` / `.` / 空格 / Unicode 等任意字符一律接受（依据 spec 澄清决策 3 与 Assumptions「命名口径」）。
- **FR-004**: `init` MUST 支持布尔开关 `--force`；本阶段该开关仅被记录并回显，MUST NOT 触发任何删除或重置行为。
- **FR-018**: 异常到退出码的映射 MUST 由**单一全局映射表**驱动，且 MUST 覆盖本阶段的两个具体错误类；未登记的子类 MUST 回落到路径类退出码 `1`；MUST NOT 使用宽泛的异常捕获吞掉未分类错误。参数用法错误（缺少子命令 / 缺少必填位置参数 / 未知子命令或参数）MUST 归入退出码 `1`，MUST NOT 使用参数解析器的默认失败码 `2`（`2` 严格只表示权限不足）。
- **FR-019**: 失败信息 MUST 写入标准错误流，且 MUST 包含可识别的错误标识（错误类别名，或"父目录不存在" / "权限"等关键词），以便脚本与用户判断失败类别；失败信息 MUST 同时包含**一条用户可执行的下一步**，该要求适用于**面向用户的三类失败** —— 路径类（"建目录 / 换路径"）、权限类（"调整权限"）、参数用法类（附用法提示）；未登记 `WorkspaceInitError` 子类的兜底属内部防御路径，MUST NOT 被本条约束。
- **FR-020**: 成功时 MUST 输出一行结果摘要，至少包含：workspace 绝对路径、workspace 名称、是否带强制标志、模板条目数、新建文件数、跳过文件数。
- **FR-021**: 客户端层 MUST 只通过核心库 API 触达文件系统行为，MUST NOT 直接依赖智能体框架、图运行时或数据库驱动（宪法 N-04）。
- **FR-022**: 核心层 MUST NOT 依赖命令行参数解析或进程参数读取（宪法 N-05），亦 MUST NOT 反向依赖任何客户端层（宪法 N-03）。

#### 可执行入口（实现要点 §4.4）

- **FR-023**: 系统 MUST 提供名为 `donkey` 的可执行入口（打包控制台脚本），使 `donkey init` 可直接被调用；MUST 同时提供等价的模块执行入口（如 `python -m donkey`），使未安装控制台脚本的环境也能调用同一套逻辑；两种入口 MUST 产生完全相同的退出码与输出；入口点 MUST NOT 位于核心层（宪法 N-03）。

#### 单元测试（实现要点 §4.5）

- **FR-024**: 系统 MUST 提供不少于 9 个单元测试用例，且 MUST 至少覆盖以下类别：绝对路径解析成功、父目录不存在时报路径类错误、相对路径解析失败时报路径类错误、只读父目录时报权限类错误、正常路径权限校验通过、核心 API 创建根目录且计数为 `0`、已存在目录不被视为错误且内容不变、含空格 / Unicode 等特殊字符的末段名 → 一律接受、名称原样保留。权限类用例 MUST 在 CI 上通过临时目录权限设置模拟，不依赖特权账号；命令行用法错误（缺少子命令 / 缺少必填位置参数 / 未知参数）→ 退出码 `1`；未登记的 `WorkspaceInitError` 子类 → 兜底退出码 `1`。

#### 黑盒验收脚本（实现要点 §4.6）

- **FR-025**: 系统 MUST 提供黑盒验收脚本 `tests/e2e/phase/verify_phase_f001_p1.py`，MUST 覆盖 7 个场景断言（全新创建成功 / 父目录不存在 / 权限不足 / 已存在幂等 / 强制标志 / 本阶段不产出模板内容 / 名称派生与结果摘要回显），且 MUST NOT 引用产品内部实现代码，只以子进程方式观察退出码与文件系统副作用。调用方式 MUST 优先使用 PATH 上的 `donkey`；使用前 MUST 校验该命令解析到的安装位置**位于当前工作树内**，不匹配时 MUST 视为该命令不可用（避免测到已安装的其它版本或其它工作树）；该命令不可用时 MUST 回落到以当前解释器执行模块入口（`python -m donkey`），回落时 MUST 打印一次显式告警而 MUST NOT 静默回落；两种方式 MUST 产生完全相同的退出码与文件系统副作用；回落时 MUST 以**仓库根**为工作目录（由验收脚本自身位置推导），确保被测对象是当前工作树的代码。

#### 全局约束与验收口径

- **FR-026**: 异常层次 MUST 保持为：总基类 ← F001 基类 ← {`PathNotFoundError`, `PathPermissionError`}；每个异常类 MUST 在其说明中标注对应的退出码，便于客户端做退出码映射。
- **FR-027**: 本阶段使用的退出码 MUST 仅限 `0` / `1` / `2`，MUST 落在 `donkey init` 专属段位（`1-10`）内，且 MUST NOT 与其它子命令的段位空间重叠（宪法 N-08）；退出码 `3` / `4` / `5-10` 在本阶段 MUST NOT 被触发。退出码语义 MUST 保持单一含义——`1` = 输入 / 路径不合法（含参数用法错误），`2` = 权限不足。
- **FR-028**: 系统 MUST 保持幂等：无论是否带 `--force`，本阶段 MUST NOT 删除、覆盖或改写任何已存在内容（"恢复出厂"的重置语义属后续阶段）。
- **FR-029**: 系统 MUST NOT 加载或解析模板清单，MUST NOT 生成任何模板文件内容；模板清单或模板源缺失 / 损坏 MUST NOT 导致本阶段失败。
- **FR-030**: 路径类底层失败（目标为普通文件、父目录为文件、悬空符号链接、路径过长、空路径等）MUST 归入路径类错误并以退出码 `1` 报告，MUST NOT 产生未捕获的异常堆栈或非预期退出码。其中"悬空符号链接"与"路径过长"属低频分支，实现时 MUST 覆盖，但**不要求独立测试**；"目标为普通文件" / "父目录是文件" / "空路径"三项 MUST 由**同一个**单元测试用例一并覆盖（**不要求各自独立成例**），以确保本条的 MUST 至少有一处断言落点。
- **FR-031**: 本阶段的交付物 MUST 通过静态检查（代码规范 + 类型检查）且零 error 零 warning。

### Key Entities

- **InitResult（init 结果对象）**：`init_workspace` 的返回值，不可变；字段依次为 —— `workspace_path`（workspace 绝对路径）、`name`（workspace 名称；名称定夺规则见 FR-005）、`force`（本次是否请求强制重置）、`templates_loaded`（模板清单条目数，本阶段为 `0`）、`files_created`（本次新建文件数，本阶段为 `0`）、`files_skipped`（已存在而跳过的文件数，本阶段为 `0`）。
- **核心库门面 API**：`init_workspace(path, name=None, force=False) -> InitResult` —— 客户端层（cli / web / gui）共用的唯一业务入口（宪法 §2.8 / D-08）；失败时以异常表达，不返回错误码。`name` 参数在库 API 层保留以维持立项书 D-1 的稳定签名，但 v1 的 CLI 入口 MUST NOT 暴露对应的用户输入通道（命令行通道的名称恒由路径末段派生）；名称定夺规则见 FR-005。
- **异常类层次**：`DonkeyError`（donkey 总基类）← `WorkspaceInitError`（F001 基类）← {`PathNotFoundError`（退出码 `1`）、`PathPermissionError`（退出码 `2`）}；参数用法错误亦归入退出码 `1`（不新增异常类）；后续阶段在同一基类下追加模板类与内置工具类错误。
- **校验能力契约**：路径解析（返回绝对路径 / 抛路径类错误）、权限校验（返回通过 / 抛权限类错误）、综合校验（返回「绝对路径 + 名称（未指定时 = 路径末段，显式传入时 = 该值）+ 强制标志」三元组 / 抛上述两类错误）——三者 MUST 无副作用，且 MUST NOT 把"目标已存在"当错误。
- **CLI 参数面**：`init` 子命令的两个参数 —— 必填位置参数 `path`（workspace 目录路径）、布尔开关 `--force`（本阶段仅记录）；MUST NOT 存在独立命名参数。
- **退出码段位**：`donkey init` 独占段位 `1-10`；本阶段占用子段 `1-2`（`1` 输入 / 路径 / 参数用法不合法、`2` 权限不足），`3` / `4` 由后续阶段占用，`5-10` 预留。

## Success Criteria *(mandatory)*

- **SC-006**: 对已存在 workspace 执行带 `--force` 的 `donkey init`，命令以成功状态结束（退出码 `0`），且已有内容未被删除或覆盖。
- **SC-007**: 本阶段交付的 workspace 仅需满足"是一个真实目录"；不要求其中出现任何模板文件——验收不得因模板内容缺失而失败。
- **SC-008**: 单元测试不少于 9 个用例且全部通过，覆盖五类场景——路径解析（绝对路径解析成功 / 父目录不存在时报路径类错误 / 相对路径解析失败时报路径类错误）、权限（只读父目录时报权限类错误 / 正常路径权限校验通过）、核心 API 行为（核心 API 创建根目录且计数为 `0` / 已存在目录不被视为错误且内容不变）、CLI 参数用法错误与未登记异常子类兜底（均归退出码 `1`）、含空格 / Unicode 等特殊字符的末段名 → 一律接受、名称原样保留。本条覆盖的类别集合与 FR-024 的类别集合逐字镜像。
- **SC-009**: 静态检查（代码规范 + 类型检查）在核心层、客户端层与测试层零 error 零 warning。
- **SC-010**: 分层边界检查通过——核心层不含命令行解析 / 进程参数依赖，客户端层不含智能体框架 / 图运行时 / 数据库驱动依赖；可执行入口点不位于核心层。
- **SC-011**: 本阶段实际使用的退出码集合恰为 {0, 1, 2}，与其它子命令的退出码段位无交集；且 `1` 与 `2` 各自保持单一语义（`1` = 输入 / 路径 / 参数用法不合法，`2` = 权限不足）。
- **SC-012**: **面向用户的三类失败**（路径类 / 权限类 / 参数用法类）**100%** 都能给出一条用户可执行的下一步 —— 路径类给出"建目录 / 换路径"、权限类给出"调整权限"、参数用法类附用法提示；不出现仅有异常堆栈而无指引的情况。本条口径与 FR-019 逐字一致；未登记 `WorkspaceInitError` 子类的兜底属内部防御路径，不在本判据的适用面内。
- **SC-013**: 单次 `donkey init` 执行在 **10 秒**内返回（纯本地文件系统操作，无网络依赖）；由验收脚本**逐场景计时断言**，阈值留足 CI 抖动余量。
- **SC-014**: 100% 的**命令行**成功执行中，workspace 名称与目标路径末段完全一致；命令行不接受任何独立命名参数（传入即以退出码 `1` 失败），因此"路径"与"名字"永远指向同一个 workspace。
- **SC-015**: 对文件系统根目录（`/` 或盘符根）执行 `donkey init` MUST 以退出码 `1` 结束，且根目录下不出现任何新建内容——根目录"父目录存在"这一表象 MUST NOT 绕过路径合法性判定。
- **SC-016**: `donkey.core` 的单元测试行覆盖率 ≥ 80%（宪法 §4.6 技术指标）；覆盖率 MUST 由覆盖率工具度量，**度量工具与执行命令由 plan 落定**，验收 MUST 给出可复核的覆盖率报告；e2e 黑盒验收脚本**不计入**该覆盖率（MUST NOT 因其不 import 业务代码而拉低阈值）。

## Assumptions

- **仓库与骨架**：仓库已初始化；`donkey/` 包目录已存在，而 `donkey/core/`、`donkey/cli/`、`donkey/web/`、`donkey/gui/` 四个子目录**由本阶段创建**（`web` / `gui` 以 `.gitkeep` 空占位，由后续 F005 / F006 实施，本阶段维持空占位）；`tests/` 下的单元测试层与黑盒验收层目录在本阶段建立，除此之外不引入额外测试目录。
- **版本控制忽略规则**：已配置 `.gitignore`（含 `__pycache__/`、`.venv/`、`.pytest_cache/`、`.mypy_cache/`、`.ruff_cache/`）；`memory/*.sqlite3` 规则尚未存在，但 P1 不产生任何 sqlite3 文件，该规则在 F001-P2 引入 sqlite3 模板时补齐。
- **本阶段自建资产**（原「入口条件资产」）（不依赖任何外部前置资产）：退出码段位常量、异常类层次（总基类 / F001 基类 / 2 个具体错误类）、模板清单 schema 文件、至少 3 个模板源占位文件，本阶段负责创建并建档；其中模板清单与模板源**仅作为后续阶段的入口条件存在**——本阶段不加载、不解析、不校验、不消费。
- **断言数口径**：Phase 提示词正文多处出现"7 个断言 / 7 个场景"的表述，同一提示词的场景枚举给出 6 个 `test_*` 函数、项目 Phase 映射表标注"低（6 断言）"。本 spec 取 **7 个场景**——在提示词枚举的 6 个之外补 1 个"名称派生与结果摘要回显"（覆盖本次"名称恒取路径末段"的决策），既与 F001-P3 提示词中"F001-P1 的 7 个 verify 断言"口径对齐，也确保名称派生这条契约有硬性证据。
- **命名口径**：workspace 名称恒为路径末段（basename），CLI 不提供独立命名参数；basename 的字符合法性一律不校验（与立项书"v1 不引入 workspace 路径 basename 命名约束"一致，允许 `-` / `.` / 空格 / Unicode 等任意字符）。库 API 层的 `name` 形参予以保留，仅为维持立项书 D-1 的稳定签名，v1 的 CLI 通道不暴露它。名称的抽取 MUST 使用路径对象的末段名属性（平台无关），MUST NOT 使用手写字符串切分——手写切分会把盘符根 `D:\` 误判为名字 `D:`。
- **根路径口径**：文件系统根 / 盘符根 / UNC 共享根一律视为非法 workspace 根（末段名为空 → 退出码 `1`）。根目录的"父目录"就是它自己且"存在"，故该判定 MUST 由"末段名为空"驱动，MUST NOT 依赖父目录存在性检查。
- **验收脚本的调用前提**：验收脚本优先调用 PATH 上的 `donkey`；该命令不存在时回落到以当前解释器执行模块入口（`python -m donkey`）。因此无论测试环境是否已安装控制台脚本，验收脚本都 MUST 可运行。
- **权限判定口径**：权限校验以本 Phase 提示词 §4.2 为准（目标不存在 → 校验父目录写 + 执行；目标已存在 → 校验目标读 + 写 + 执行）。项目 README §4.3 中"验证当前用户对 path 有写权限"为简写表述，二者不冲突。
- **路径类错误的归并口径**：目标为普通文件 / 悬空符号链接 / 路径过长 / 空路径等低频异常，以及参数用法错误（缺子命令 / 缺必填参数 / 未知参数），按奥卡姆原则归并到退出码 `1`（"输入不合法"同族），不单独占用新码值；权限类错误独占退出码 `2`。
- **运行平台**：Linux / macOS（权限语义按 POSIX 判定）；Windows 平台不在本阶段范围。
- **特权环境说明**：权限断言**不依赖特权账号**——`0o555` 目录无任何写位，按 POSIX 语义即使以特权账号（如 root）运行 `os.access(dir, W_OK)` 亦为 False（`research.md` R-04）；验收统一以临时设置只读目录的模拟方式为准。
- **术语口径**：本 spec 中 "Phase" = F001-P1（开发阶段）；"子段" = F001 子段 1（退出码 `1-2`）；"段位" = F001 段位 `1-10`；三者严格分层（宪法 §4.3）。
- **范围外**：本阶段不含模板骨架内容、模板清单加载、3 个内置工具、Skills 示例、workspace manifest 写入、名称向模板内容（README 标题 / provider 注释 / manifest）的注入，以及 `load` / `session` / `run` 等其它子命令——它们分属 F001-P2 / F001-P3 / F002 / F003 / F004。本阶段交付的 workspace 根目录为**过渡态**——尚不含宪法 §2.6 要求的 `instruction.md` / `providers/` / `tools/` / `mcp/mcp.json` / `skills/` / `memory/`；§2.6 的符合性由 F001-P2（模板骨架生成）达成。
- **下游流程**：本 spec 只定义"做什么"与"怎样算成功"；实现步骤、任务拆分、依赖版本锁定留给 `/speckit.plan` 与 `/speckit.tasks`。
