### User Story 1 - 一次 init 得到完整可用的 workspace 骨架 (Priority: P1)

用户敲下 `donkey init /path/to/ws`，期望该目录立刻变成一个"能看懂、能改"的智能体工作区：五大必填目录齐备、必填文件齐备、三个记忆库文件就位、还有一份记录身份的工作区清单。用户**不需要**再手工建目录、补空文件。

**Why this priority**: 这是本 Phase 唯一不可替代的价值 —— "把 workspace 变成 workspace"。没有它，`donkey init` 只是一次 `mkdir`，用户拿到的仍是一个空文件夹。

**Independent Test**: 可独立验证 —— 对一个新路径执行 `donkey init`，命令以成功状态结束（退出码 `0`），且目标目录内出现全部必填文件 / 目录 / 三个 sqlite3 文件与工作区清单。

**Acceptance Scenarios**:

1. **Given** 一个尚不存在、但父目录已存在的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，目标目录内存在全部必填文件（`instruction.md` / `README.md` / `.gitignore` / `providers/default.toml` / `providers/README.md` / `mcp/mcp.json` / `skills/example/SKILL.md` / `memory/README.md` / `tools/README.md` / `mcp/README.md` / `skills/README.md`）**及全部 37 个文本模板产物与 3 个 sqlite3 文件**（完整清单见 FR-040）。
2. **Given** 同一个目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 五大必填目录（`tools/` / `mcp/` / `skills/` / `memory/` / `providers/`）及其子目录 `skills/example/` 均为真实存在的目录。
3. **Given** 同一个目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** `memory/` 下三个 sqlite3 文件（`sessions.sqlite3` / `store.sqlite3` / `knowledge.sqlite3`）均存在，且工作区根存在一份记录身份的工作区清单文件。

### User Story 2 - 供应商配置目录开箱即用且可被机器读取 (Priority: P2)

用户打开工作区后第一件事就是配模型。供应商目录必须是**一份机器可解析的完整清单**：26 家供应商各一个配置文件、一个全局默认文件、一份索引说明，且默认全部处于"关闭"状态 —— 用户没配凭据时，这些文件不会给后续检查添乱。

**Why this priority**: 没有可解析的供应商配置，用户配模型这一步就无从下手；配置的"默认关闭"设计则是让出厂态工作区不会因为空凭据而报错。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，用标准 TOML 解析器读取 `providers/` 下的每个文件均**不抛异常**，且每个供应商文件的开关字段为关闭、凭据字段为空。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户用标准 TOML 解析器读取 `providers/default.toml`，**Then** 解析不抛异常，且结果中同时含"默认供应商"与"默认模型"两个字段（出厂态均为空串）。
2. **Given** 一个刚生成的 workspace，**When** 用户用标准 TOML 解析器读取任意一个供应商配置文件，**Then** 解析不抛异常，且该文件的开关字段为关闭状态。
3. **Given** 一个刚生成的 workspace，**When** 用户列出 `providers/` 目录，**Then** 其中恰有 26 个以供应商 id 命名的 `.toml` 文件 + 1 个全局默认文件 + 1 份目录索引说明。

### User Story 3 - MCP 配置起点是合法 JSON (Priority: P3)

用户迟早要接 MCP 服务器。生成的 MCP 配置文件必须**开箱即可被 JSON 解析器读取**，且形状对用户自明 —— 一个空的服务器表，等着用户往里填。

**Why this priority**: 配置文件的"语法合法性"是零成本的高价值保证：一个不能解析的模板会让用户还没开始配置就先踩坑。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，用标准 JSON 解析器读取 `mcp/mcp.json` 不抛异常，且结果中含服务器表字段。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户用标准 JSON 解析器读取 `mcp/mcp.json`，**Then** 解析不抛异常。
2. **Given** 同一个文件，**When** 用户查看其内容，**Then** 其中含一个空的服务器表字段（形如 `mcpServers`），供用户后续填入服务器定义。

### User Story 4 - 示例 Skill 的元信息合规 (Priority: P4)

用户会参考示例 Skill 写自己的 Skill。示例文件的头部元信息必须**只有且必有**两个字段（名称 + 描述）—— 这是 donkey 的 Skills 契约，多余字段会导致加载器解析漂移。

**Why this priority**: 示例文件是用户的事实上的模板；示例本身不合规，会把不合规的写法复制到用户的工作区里。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，读取 `skills/example/SKILL.md` 的头部元信息块，确认其以分隔符开头且含名称与描述两个字段。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户读取 `skills/example/SKILL.md`，**Then** 文件以 frontmatter 分隔符开头，且头部元信息含名称字段（值为 `example`）与描述字段。
2. **Given** 同一个文件，**When** 用户查看 frontmatter 的字段集合，**Then** 字段集合**恰为**名称与描述两项（宪法 D-07 —— Skills frontmatter 不允许自定义额外字段）。

### User Story 5 - 工作区处处带着自己的名字 (Priority: P5)

用户建了工作区，就该处处认得出这是哪个工作区：说明文档的标题、供应商默认配置的注释、工作区清单里的名字字段，三处必须指向同一个名字，且该名字恒等于路径末段。

**Why this priority**: 名字一致性是可移植性的前提（宪法 §2.3）—— 用户把工作区打包带走、在另一台机器上打开，名字仍是同一个。它不阻断"能不能建目录"的主线，故排在模板落地之后。

**Independent Test**: 可独立验证 —— 对末段名为 `foo` 的路径执行 `donkey init`，断言工作区说明文档正文、供应商默认配置文件正文、工作区清单的名字字段三处都含 / 等于 `foo`。

**Acceptance Scenarios**:

1. **Given** 一个末段名为 `foo` 的目标路径，**When** 用户执行 `donkey init <该路径>`，**Then** 工作区说明文档正文含该名字，供应商默认配置文件正文含该名字。
2. **Given** 同一个工作区，**When** 用户读取工作区清单，**Then** 其名字字段**严格等于** `foo`。
3. **Given** 任意合法路径，**When** 用户执行 `donkey init`，**Then** 工作区名称恒为解析后路径的末段名，模板正文中的名字占位符 MUST 被替换为该名称（MUST NOT 残留占位符字面量）。

### User Story 6 - 反复跑 init 不会碰用户写的东西 (Priority: P6)

用户会反复执行 `donkey init`（脚本化、改完配置重跑、忘了跑没跑过）。已存在的文件**一个字节都不能被改动** —— 改过的人设提示词不该被悄悄还原。

**Why this priority**: 幂等性是 `donkey init` 的核心契约（业务验收 AC-3）—— 一次误伤用户内容，用户就再也不敢重复跑这条命令了。

**Independent Test**: 可独立验证 —— 先建工作区并改写其中的提示词文件，再对同一路径执行 `donkey init`，命令以成功状态结束（退出码 `0`），且该文件的内容与修改时间**均未变化**。

**Acceptance Scenarios**:

1. **Given** 一个已存在的 workspace，**When** 用户不带 `--force` 执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，**不**报"已存在"类错误。
2. **Given** 一个已存在的 workspace（其提示词文件已被用户改写），**When** 用户执行 `donkey init <该路径>`，**Then** 该文件的**内容**保持不变。
3. **Given** 同一个文件，**When** 用户比较两次执行前后的修改时间，**Then** 修改时间**完全相同**（不是"内容相同但被重写过"）。
4. **Given** 一个工作区根的 `manifest.json` 已被用户改坏（不是合法 JSON），**When** 用户不带 `--force` 执行 `donkey init <该路径>`，**Then** 命令以退出码 `3` 结束并给出可执行的下一步（工作区清单属"清单外路径"，其**读取失败**属模板生成类错误，与"渲染不动清单外文件"不冲突 —— 见 Edge Cases）。

### User Story 7 - 删掉的文件会被补回来 (Priority: P7)

用户手滑删掉了工作区里的某个模板文件。他期望再跑一次 `donkey init` 就把它补齐 —— 而不是得到一个"永远缺一块"的残缺工作区。

**Why this priority**: 这是幂等的另一半（"有则增"）。只保证"不覆盖"而不保证"补齐"，用户的工作区会随时间腐化。

**Independent Test**: 可独立验证 —— 先建工作区并删除其中一个模板文件，再执行 `donkey init`，命令以成功状态结束（退出码 `0`），且被删文件重新存在。

**Acceptance Scenarios**:

1. **Given** 一个已存在但缺少某个模板文件的 workspace，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，缺失的模板文件被重新生成。
2. **Given** 同一个工作区，**When** 用户检查其它未缺失的模板文件，**Then** 它们的**内容**与**修改时间**均未被改动（补齐不影响其它文件）。

### User Story 8 - `--force` 把模板恢复成出厂状态 (Priority: P8)

用户改乱了模板，想回到出厂状态。他加上 `--force` 后，被改动的模板文件应当**回到出厂内容**。

**Why this priority**: "恢复出厂设置"是 `--force` 的全部意义；没有它，`--force` 只是个被记录但无效果的摆设（F001-P1 已把它记录下来）。

**Independent Test**: 可独立验证 —— 先建工作区并把提示词文件改成自定义内容，再执行 `donkey init --force`，命令以成功状态结束（退出码 `0`），且该文件不再含用户自定义内容。

**Acceptance Scenarios**:

1. **Given** 一个已被用户改写模板文件的 workspace，**When** 用户执行 `donkey init <该路径> --force`，**Then** 命令以退出码 `0` 结束，被改写的模板文件恢复为出厂内容。
2. **Given** 同一个工作区，**When** 用户检查该文件，**Then** 其内容中**不含**用户自定义的字样。
3. **Given** 任意一次带 `--force` 的执行，**When** 用户查看结果摘要，**Then** 摘要中能看出本次带了强制标志。

### User Story 9 - `--force` 也不碰用户自己的东西 (Priority: P9)

用户的 `--force` 是针对**模板**的，不是针对**他自己的文件**。工作区里他自己建的目录、自己写的日志、自己写的工具脚本，都必须安然无恙。

**Why this priority**: 这是 `--force` 最危险的边界 —— 一条"恢复出厂"命令如果会清空用户目录，用户的信任瞬间归零。这是本 Phase 最高优先级的安全属性。

**Independent Test**: 可独立验证 —— 先建工作区并加入用户自建目录与文件，再执行 `donkey init --force`，命令以成功状态结束（退出码 `0`），且用户目录与文件的存在性、内容均不变。

**Acceptance Scenarios**:

1. **Given** 一个含有用户自建目录（如 `media/` 及其内部文件）的 workspace，**When** 用户执行 `donkey init <该路径> --force`，**Then** 命令以退出码 `0` 结束，用户自建目录与其内部文件**依然存在**。
2. **Given** 一个含有用户自建文件（如工作区根的日志文件）的 workspace，**When** 用户执行 `donkey init <该路径> --force`，**Then** 该文件的**内容**保持不变。
3. **Given** 任意一次带 `--force` 的执行，**When** 用户审视工作区，**Then** 强制重置的作用域 MUST 严格限定在模板清单内的条目。

### User Story 10 - 删掉整个工作区再来一次也无妨 (Priority: P10)

用户想彻底重来，删掉整个工作区目录再跑一次 `donkey init`。他期望得到和首次创建**完全一样**的结果。

**Why this priority**: "放弃重做"是最干脆的恢复手段，它必须与"全新创建"等价，否则用户会陷入"删了之后 init 出来的东西不对劲"的困惑。

**Independent Test**: 可独立验证 —— 先建工作区、删掉整个目录、再执行 `donkey init`，命令以成功状态结束（退出码 `0`），且模板文件重新出现。

**Acceptance Scenarios**:

1. **Given** 一个已被用户手动整体删除的路径（其父目录仍存在），**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束（MUST NOT 报"父目录不存在"类错误），模板文件重新生成。
2. **Given** 同一个工作区，**When** 用户检查其目录结构，**Then** 与"全新创建"场景的目录结构一致。

### User Story 11 - 现在还不会出现内置工具文件 (Priority: P11)

用户打开 `tools/` 目录时，不应该看到一堆他没要求过的工具脚本 —— 那些属于后续阶段。今天的 `tools/` 里只有一份说明文档。

**Why this priority**: 范围边界是本 Phase 最容易被误解的点 —— "init 完了却找不到工具"不是 bug。把边界写死能避免用户误判，也能防止实现方提前抢跑下一阶段的工作。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，断言 `tools/` 目录存在但**不含**内置工具脚本文件。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户列出 `tools/` 目录，**Then** 其中**不含**任何内置工具脚本文件（文件系统的 / 命令行的 / 网络抓取三类），也**不含**包初始化文件。
2. **Given** 同一个目录，**When** 用户查看其内容，**Then** 其中有一份工具开发规范说明文档（说明"工具文件还没生成，后续阶段会补上"）。

### User Story 12 - init 不会替我做配置检查 (Priority: P12)

用户可能故意把供应商配置写错，看看 `donkey init` 会不会拦他。答案是**不会** —— init 只负责生成骨架，不负责检查内容。

**Why this priority**: 分工清晰很重要 —— 配置校验是另一条命令的职责。init 越权报错会让用户的调试流程变得莫名其妙。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，命令以退出码 `0` 结束；且 init 阶段 MUST NOT 因工作区内配置内容的合法性而失败。

**Acceptance Scenarios**:

1. **Given** 任意合法路径，**When** 用户执行 `donkey init <该路径>`，**Then** 命令以退出码 `0` 结束，**不**对工作区内的供应商配置 / MCP 配置 / Skill 元信息做合法性判定。
2. **Given** 一个出厂态 workspace（零个启用的供应商），**When** 用户执行 `donkey init`，**Then** 命令仍以退出码 `0` 结束（"全部关闭"是合法的出厂态，不是错误）。

### User Story 13 - `--force` 会重建记忆库文件 (Priority: P13)

用户执行 `--force` 时若以为"记忆库里的历史会话还在"，就会误判。`--force` 的语义是**恢复出厂设置** —— 三个记忆库文件会被删掉重建，历史会话与元数据一并清空。用户需要**事先知道**这一点。

**Why this priority**: 这是本 Phase 唯一一处会造成**真实数据丢失**的默认行为。若用户不知情，`--force` 就从"重置模板"变成了"删会话"。

**Independent Test**: 可独立验证 —— 先建工作区并往记忆库里写入一条会话记录，执行 `donkey init --force`，命令以成功状态结束（退出码 `0`），该记录消失且表结构完好；用户自行备份的文件不受影响。

**Acceptance Scenarios**:

1. **Given** 一个含非空会话记录的记忆库文件的 workspace，**When** 用户执行 `donkey init <该路径> --force`，**Then** 命令以退出码 `0` 结束，记忆库文件依然存在但已被**重建**。
2. **Given** 重建后的记忆库文件，**When** 用户检查其结构，**Then** 历史表与写入表、以及工作区自管的会话元数据表**全部存在**，且会话元数据表内**记录数为 0**（历史与元数据一并清空）。
3. **Given** 用户在执行 `--force` 前自行备份的记忆库文件，**When** 用户检查该备份，**Then** 它依然存在且非空（强制重置不波及其它路径）。
4. **Given** 刚生成的 workspace，**When** 用户阅读记忆库目录下的说明文档，**Then** 其中明确告知"三个记忆库文件会被 `--force` 删掉重建"并给出备份命令示例。
5. **Given** 一次带强制标志的 `donkey init`，**When** 用户查看命令行的输出，**Then** 输出中**额外有一行**显式提示，说明记忆库数据（会话历史与会话元数据）已被清空 —— 用户不必事后翻说明文档才发现历史没了。

### User Story 14 - 记忆库文件开箱就是结构完好的空库 (Priority: P14)

用户拿到的工作区，其记忆库文件必须是**结构完好**的空库 —— 不是 0 字节的占位，也不是缺表的半成品。短期记忆库尤其重要：它要能立刻被写入。

**Why this priority**: 结构完好才能让"init 完就能用"成立；若 init 只留空文件，后续写入路径还得再补 schema 逻辑，把复杂度推给运行时。

**Independent Test**: 可独立验证 —— 对新路径执行 `donkey init`，检查三个记忆库文件全部存在；短期记忆库含三张表与两个索引、元数据表记录数为 0；另两个文件为 0 表占位。

**Acceptance Scenarios**:

1. **Given** 一个刚生成的 workspace，**When** 用户检查 `memory/` 目录，**Then** 三个 sqlite3 文件与该目录的说明文档**全部存在**。
2. **Given** 短期记忆库文件，**When** 用户检查其结构，**Then** 其中存在历史表、写入表与工作区自管的会话元数据表三张表。
3. **Given** 同一个文件，**When** 用户检查会话元数据表的索引，**Then** 标题索引与更新时间索引**均存在**。
4. **Given** 短期记忆库文件，**When** 用户统计会话元数据表记录数，**Then** 结果为 `0`（出厂态为空）。
5. **Given** 长期记忆库占位文件与知识库占位文件，**When** 用户统计其中的表数量，**Then** 两者均为 `0`（v1 仅占位，结构推迟到后续版本）。

### Edge Cases

**前置与根目录类（归入退出码 `1` / `2`）**

- 创建 workspace 根目录失败（权限不足 / 磁盘满 `ENOSPC` / 其它 `OSError`）→ 权限类失败 → 退出码 `2`（FR-038：**阶段 ③ 的一切失败一律归 `2`**）；MUST NOT 以裸 `OSError` 逃逸；错误信息 MUST 指出实际根因（磁盘空间 / 权限），而"下一步"固定句沿用 P1 的 `_NEXT_STEP`。
- 前置校验阶段的路径类失败 → 退出码 `1`（P1 已实现，本 Phase MUST NOT 改动，FR-029）。

**清单与源文件类（归入退出码 `3`）**

- 安装包内的模板清单文件缺失、不是合法 JSON、或结构非法（版本号不是整数 / 条目集合不是列表 / 条目缺路径字段 / 条目格式为未知值）→ 一律按模板生成类错误报告（退出码 `3`），**不**按路径类错误报告（退出码 `1`）—— 用户对二者的修复动作不同（前者"重装 donkey"，后者"建目录 / 换路径"）。**归属权威分类法 ①。**
- 某个模板条目的源文件缺失 → 模板生成类错误（退出码 `3`）。**归属权威分类法 ②。**
- 模板源文件存在但内容不可解析 / 写入失败 / 磁盘满 / 权限在执行中途被撤销 → 模板生成类错误（退出码 `3`）。**归属权威分类法 ③（内容不可解析）与 ④（写入失败 / 磁盘满 / 权限在执行中途被撤销）。**
- sqlite3 结构构造失败（上游 saver 初始化抛错 / 会话元数据表建表失败 / 数据库文件被占用）→ 模板生成类错误（退出码 `3`）。**归属权威分类法 ⑤。**
- 上述各条失败对用户的修复动作相同（重装 donkey / 检查权限 / 重试 init），按奥卡姆剃刀**合并**到同一个退出码 `3`，MUST NOT 各占一个码值；失败成因的完整分类见『模板生成类失败的 7 类成因（权威分类法）』段（权威清单以该段为准）；错误信息 MUST 同时含可识别的错误标识与**一条**用户可执行的下一步（与退出码 `1` / `2` 的指引口径一致）。
- 注入用的清单路径 / 模板根目录指向一个不存在的目录 → 模板生成类错误（退出码 `3`），MUST NOT 静默退化为"空清单"（静默成功会让用户拿到空工作区却收到成功提示）。**归属权威分类法 ①（清单缺失）；注入的模板根目录不存在时，其下的文本源文件随之缺失 → 归入 ②。**
- 上游 saver 包未安装 / 版本不兼容 / 导入失败 → 模板生成类错误（退出码 `3`），错误信息 MUST 指出"运行期依赖缺失或不可用"并给出下一步（重装 donkey）；MUST NOT 静默跳过那两张表（否则 init 结束时结构不完整，用户拿到的是半成品空库）。**归属权威分类法 ⑥。**

**渲染与幂等类**

- 目标路径已存在且**是目录**（而非文件）——**且该条目为文本类（`markdown` / `toml` / `json` / `python` / `text`）或 `sqlite3` 类** → 模板生成类错误（退出码 `3`）；MUST NOT 递归删目录内容。**目录类条目不在本条范围内**——目录条目已存在即按 FR-010 保留不变，MUST NOT 报错。
- 目标文件已存在但**不可写**（只读）→ 非 `--force` 模式下 MUST 跳过（视为"已存在"，不尝试写入）MUST NOT 报错；`--force` 模式下删除失败 → 模板生成类错误（退出码 `3`）。
- 目标文件已存在但用户把它改成了空文件 / 二进制内容 → 非 `--force` 模式下 MUST 原样保留（"存在即跳过"，MUST NOT 依据内容判断是否重写）。
- 模板正文中的未知占位符 → 原样保留，MUST NOT 报错，MUST NOT 替换为空。
- 模板正文中的名字占位符出现在多个文件里 → 每一处 MUST 被替换为同一个工作区名称。
- 工作区名称含空格 / Unicode / 特殊字符 → MUST 原样注入，MUST NOT 转义、MUST NOT 截断。
- 清单条目顺序被打乱（文件条目排在目录条目之前）→ MUST NOT 影响结果（写文件前确保父目录存在）。
- 清单中出现重复条目 → MUST NOT 报错；渲染 MUST 按**唯一路径**处理，以重复项中**最后出现**的条目为准（其 `format` 与源模板生效）；计数按唯一路径计一次；若该路径在渲染开始前已存在则视为"已存在"而跳过。

**`--force` 类**

- `--force` 时模板文件被删除但重建失败 → 模板生成类错误（退出码 `3`），MUST NOT 留下"文件已删、内容未生成"的静默残缺状态而仍返回成功。
- `--force` 重建 sqlite3 时遗留的 `-wal` / `-shm` 附属文件 → MUST 连带删除（残留**可能**携带旧事务内容；实测因盐值不匹配被**安全忽略**，故属**防御性**清理）；非 `--force` 模式下 MUST NOT 触碰它们。
- `--force` 清理目录条目时目录内含清单外的用户文件 → MUST 保留该文件，MUST NOT 删除目录本身；**目录条目在 `--force` 下 MUST NOT 删除目录内的任何文件**（清单内文件的重置由各自的条目负责，见 FR-010）。
- `--force` 与"工作区尚不存在"组合 → 等价于全新创建（无任何已存在内容可重置）。

**memory/ 模板边界类**

- 用户手工把记忆库文件删了 → 再次 init（无 `--force`）MUST 重建它（视为清单内缺失条目）。
- 用户手工把记忆库文件的表删了 / 改成非 sqlite3 文本 → 非 `--force` 模式下 MUST 原样保留、MUST NOT 报错（MUST NOT 在 init 阶段做结构健康检查 —— 那是配置检查阶段的职责，退出码属另一码段）；`--force` 模式下 MUST 删掉重建。
- 用户在 `memory/` 下新建了非清单文件（如笔记、旧库文件）→ MUST 原样保留，`--force` 也不得触碰。
- 长期记忆库 / 知识库占位文件 → MUST 为 0 表 0 索引；MUST NOT 被 donkey 本体的任何运行时路径读取。

**其它边界**

- 工作区内已存在 `manifest.json` 但内容不是合法 JSON → 读取失败按模板生成类错误处理（退出码 `3`）；`--force` 模式下 MUST 覆盖为合法内容。
- 工作区内已存在 `manifest.json` 且用户改过其中的字段 → 非 `--force` 模式下 MUST 原样保留（连创建时间也不刷新）；`--force` 模式下 MUST 覆盖并刷新创建时间。
- 用户手工删掉工作区根的 `manifest.json` → 再次 init MUST 重建它。
- 初始化流程步骤 ⑤（写工作区清单）失败（读取解析失败 / 写入失败）→ 模板生成类错误（退出码 `3`）；**步骤 ④ 已落地的模板文件 MUST 保留**（不删除、不还原）—— 本 Phase MUST NOT 实现任何事务回滚机制。
- 工作区目录被用户重命名后再执行 `donkey init`（不带强制标志）→ 已存在文件 MUST 完全不动（工作区清单的 `name` 字段与模板正文均保留重命名前的名称），故命令行报告的名称（路径末段名）与模板正文内的名称**不一致**；该不一致 MUST NOT 被当作错误（MUST NOT 触发退出码 `3`），但 MUST NOT 被静默当作一致 —— 本 Phase 以**文档化口径**满足（本 Edge Case 已登记 + SC-014 的适用边界已明确），MUST NOT 新增命令行输出；用户须以 `--force` 重新生成才能同步名称。
- 同一路径被并发执行 → 不在本 Phase 职责范围内。
- 平台差异：Windows 下 sqlite3 文件被占用（文件句柄未释放）→ 重建失败按模板生成类错误处理；MUST NOT 强制删除被占用的文件。**（Windows 平台不在本阶段范围，见 Assumptions「运行平台」——此处仅登记未来的处理约定，本阶段 MUST NOT 实现、亦 MUST NOT 纳入验收。）**

## Requirements *(mandatory)*

### Functional Requirements

#### 模板清单加载与校验（实现要点 §4.1）

- **FR-001**: 系统 MUST 提供模板清单加载能力 `load_template_manifest(manifest_path: Path | None = None) -> list[dict]`；`manifest_path` 缺省 MUST 指向安装包内的模板清单文件（与模板源文件同目录）；返回值 MUST 为清单条目列表（`list[dict]`），MUST NOT 被调用方就地修改。
- **FR-002**: 模板清单的 schema MUST 为：版本号字段 `version` 为整数、条目集合字段 `entries` 为列表、每个条目 MUST 含非空字符串的路径字段 `path`、可选的格式字段 `format`（**省略时 MUST 按 `text` 处理**）。任一项不满足（文件缺失 / 不是合法 JSON / 结构非法 / 条目缺路径 / 格式值未知）MUST 抛出模板生成类错误（`TemplateGenerationError`）→ 退出码 `3`；MUST NOT 抛出路径类错误（`PathNotFoundError`，退出码 `1`）。清单条目路径重复时 MUST NOT 报错 —— 渲染 MUST 按**唯一路径**处理（同一路径在一次渲染中只产生一次落地动作），且以重复项中**最后出现**的条目为准（其 `format` 与源模板生效）；计数 MUST 按唯一路径计一次（MUST NOT 对同一路径既计 `created` 又计 `skipped`；本条的"计数"指 `files_created` / `files_skipped`，`templates_loaded` 仍按清单条目总数计，spec FR-017 / FR-026）；**非强制模式下**若该路径在渲染开始前已存在，则按"已存在"规则跳过（spec FR-008；带强制标志时按 FR-009 删后重建）。
- **FR-003**: 模板条目 MUST 支持且仅支持 7 种格式取值 —— `markdown` / `toml` / `json` / `python` / `text`（文本模板类）、`directory`（目录类）、`sqlite3`（数据库类）。未登记的格式值 MUST 按模板生成类错误处理（退出码 `3`），MUST NOT 被静默忽略。
- **FR-004**: 模板清单 MUST 位于安装包内（与模板源文件同目录），并 MUST 与 workspace 根的工作区清单是**两个不同的文件**（宪法 §2.6 / D-01）；二者 MUST NOT 互相覆盖、互为别名或混淆。

#### 模板骨架渲染（实现要点 §4.1）

- **FR-005**: 系统 MUST 提供模板渲染能力 `render_templates(workspace_path: Path, name: str, force: bool, manifest_entries: list[dict], templates_root: Path | None = None) -> tuple[int, int]`，返回二元组 `(本次新建文件数, 本次跳过文件数)`。
- **FR-006**: `templates_root` MUST 可注入（缺省为安装包内的模板根目录）—— 使单元测试 MUST 能在**不破坏已安装包**的前提下构造"源模板缺失"等失败分支。
- **FR-007**: 文本模板类条目（`markdown` / `toml` / `json` / `python` / `text`）的源文件路径 MUST 为 `templates_root / f"{条目路径}.txt"`（条目路径与源文件一一对应，含子目录层级）。源文件缺失 MUST 抛出模板生成类错误 → 退出码 `3`。
- **FR-008**: 文本模板类条目 MUST 遵守"无则增、有则跳过"的幂等规则 —— 目标不存在则写入默认内容（计入新建数）；目标已存在且**未**带强制标志时 MUST **完全不动**该文件（内容与修改时间均不变，计入跳过数）。
- **FR-009**: 带强制标志时，文本模板类条目 MUST 先删除目标文件再按默认内容重建（计入新建数）；MUST NOT 采用"打开覆盖写"的写法（那会保留原文件权限位与修改时间语义，不构成"恢复出厂"）。
- **FR-010**: 目录类条目 MUST 表现为：不带强制标志时目录不存在则创建、已存在则保留；带强制标志时目录不存在则创建、已存在则**保留不变** —— 目录条目 MUST NOT 删除目录本身，MUST NOT 删除目录内的**任何**文件（清单内与清单外一律不动）；其内清单内文件的重置由各自的文本 / sqlite3 条目按 FR-009 / FR-011 负责。**理由**：目录条目若删除文件，会与 FR-012 的"渲染 MUST NOT 依赖清单条目先后顺序"冲突 —— 当前 46 条清单的顺序为「37 文本 → 6 目录 → 3 sqlite3」，目录条目删除会抹掉 6 个目录内的 **34** 个文件（**32** 个本轮新建 + **2** 个 P1 已有的 `mcp/mcp.json` / `providers/default.toml`）且不再生成。**（补充：FR-010 与『目标路径已存在且是目录 → 退出码 3』的适用边界——后者仅约束**文本类与 sqlite3 类条目**；目录类条目已存在时 MUST NOT 报错。）**
- **FR-011**: sqlite3 类条目 MUST 走结构构造器（见 FR-030 ~ FR-032）而非文本复制；不带强制标志时目标已存在则 MUST **完全不动**（保留用户历史，MUST NOT 校验其结构）；带强制标志时 MUST 先删除目标文件，**并 MUST 连带删除同名的 `-wal` / `-shm` 附属文件**（二者是同一模板的附属产物；残留**可能**携带旧事务内容 —— 实测因 WAL 头部盐值不匹配会被**安全忽略**，故连带删除属**防御性**措施；实现与错误信息 MUST NOT 声称"不删必然导致旧数据回放"），再重新构造。
- **FR-012**: 渲染 MUST NOT 依赖清单条目的先后顺序 —— 写入任何文件前 MUST 先确保其**父目录**存在（父目录创建 MUST 限定在 workspace 根之下）；目录条目 MUST 仍被显式创建并计入清单条目总数，但 MUST NOT 成为文件写入的前置条件，**亦 MUST NOT 删除任何文件**（见 FR-010）—— 故目录条目与文件条目的先后顺序不影响最终结果。
- **FR-013**: 渲染 MUST NOT 触碰清单之外的任何路径（用户的自建目录 / 自建文件 / 自定义工具脚本 / 自定义 Skill 目录 / `memory/` 下的非清单文件一律不动）—— 强制重置的作用域 MUST 严格限定在清单条目内；sqlite3 三个模板已被清单收纳，其被强制重置属预期行为（用户已由记忆库目录说明文档告知备份责任）。
- **FR-014**: 模板骨架渲染阶段（FR-027 步骤 ④）发生的一切失败 —— 含清单损坏 / 结构非法 / 源模板缺失 / 渲染失败 / 文件写入失败（磁盘满）/ **权限在渲染中途被撤销** / sqlite3 结构构造失败 —— MUST 统一抛出模板生成类错误（`TemplateGenerationError`）→ 退出码 `3`；MUST NOT 以裸异常（`OSError` / `sqlite3.Error` 等）逃逸到调用方。渲染阶段的一切失败（含权限在渲染中途被撤销）统一归退出码 `3`；失败成因的完整分类见上方『模板生成类失败的 7 类成因（权威分类法）』段。
- **FR-015**: 渲染 MUST 支持模板正文中的名字占位符替换 —— 占位符 MUST 被替换为工作区名称；MUST 同时识别带空格与不带空格两种写法；未识别的占位符 MUST 原样保留，MUST NOT 报错、MUST NOT 替换为空串。工作区名称含空格 / Unicode / 特殊字符时 MUST 原样注入，MUST NOT 转义、MUST NOT 截断。
- **FR-016**: 渲染 MUST NOT 因"目标已存在"而失败 —— 已存在即视为跳过（不带强制标志）或重建（带强制标志），MUST NOT 报"已存在"类错误。
- **FR-017**: 计数口径 —— 新建数与跳过数 MUST 仅统计**文件型条目**（文本模板 + sqlite3 模板）；目录条目 MUST NOT 计入两者。清单条目总数（`templates_loaded`）MUST 统计**全部**条目（含目录条目）。

#### 工作区清单写入与读取（实现要点 §4.2）

- **FR-018**: 系统 MUST 提供独立的工作区清单模块（不与渲染逻辑混同），并至少暴露三个能力 —— 写入、读取、"确保存在"便捷封装；写入返回清单字典，读取在文件不存在时返回"无"，解析失败时 MUST 抛出模板生成类错误（退出码 `3`）。
- **FR-019**: 工作区清单 MUST 落在 workspace 根目录，文件名 MUST 为 `manifest.json`；其字段 MUST **恰好且仅**为四项 —— 版本号（整数，v1 填 `1`）、名字（字符串）、创建时间（带时区的 ISO 8601 时间戳）、donkey 版本号（字符串）。MUST NOT 增加其它字段。
- **FR-020**: 工作区清单的创建时间 MUST 由"本机当前 UTC 时刻"生成，格式 MUST 带时区偏移；不带强制标志且清单已存在时 MUST **保留原创建时间**（不刷新），带强制标志时 MUST 覆盖并刷新为当前时刻。
- **FR-021**: 工作区清单中的 donkey 版本号在 v1 阶段 MUST 取硬编码值 `0.1.0`；MUST NOT 通过导入内部版本符号获取（循环依赖风险）；将来若改为动态获取，MUST 使用包元数据查询方式。
- **FR-022**: 工作区清单 MUST 以人类可读的缩进格式写入（缩进 2 空格）、MUST 保留非 ASCII 字符原文（不转义为转义序列）、MUST 以纯 UTF-8 编码写入且 MUST NOT 携带 BOM 头。
- **FR-023**: "确保存在"便捷封装 MUST 与 `write_workspace_manifest` **严格等价**（共用同一判定顺序）—— 带强制标志时直接覆盖、MUST NOT 先读旧文件；不带强制标志时先读 —— 文件不存在则创建、已存在且解析成功则不覆盖并返回既有内容、已存在但解析失败则抛模板生成类错误（退出码 `3`）；使初始化流程一次调用即完成工作区清单落地。

#### 核心库门面与初始化流程（实现要点 §4.3）

- **FR-024**: 核心库门面 `init_workspace(path, name=None, force=False) -> InitResult` 的函数体 MUST 只做两件事 —— 调用内部初始化流程并构造结果对象；MUST NOT 在门面层承载业务逻辑。
- **FR-025**: 结果对象 `InitResult` 的字段集合、字段顺序与字段类型 MUST 与 F001-P1 冻结的契约完全一致（`workspace_path` / `name` / `force` / `templates_loaded` / `files_created` / `files_skipped`），MUST NOT 增删字段、MUST NOT 改变顺序或类型（该契约为后续阶段的稳定接口）。
- **FR-026**: 结果对象中的 `templates_loaded` MUST 等于**本次加载的模板清单条目总数（含重复条目）** —— 与 FR-002 末尾的"templates_loaded 仍按清单条目总数计"同一口径，MUST NOT 使用去重后的唯一路径数；`files_created` / `files_skipped` MUST 为本次渲染的对应计数（口径见 FR-017）。
- **FR-027**: 内部初始化流程 MUST 按以下顺序执行 —— ① 前置校验（路径解析 + 权限校验 + 名称定夺，复用 F001-P1 已实现的能力，MUST NOT 重新实现）→ ② 加载模板清单 → ③ 创建 workspace 根目录 → ④ 渲染模板骨架 → ⑤ 写入工作区清单。（步骤 ③ 创建 workspace 根目录失败 → 权限类失败 → 退出码 `2`；步骤 ④ / ⑤ 失败 → 退出码 `3`，见 FR-014 / FR-038）
- **FR-028**: 创建 workspace 根目录 MUST 只创建该根目录本身，MUST NOT 自动补建缺失的父目录（父目录缺失已在前置校验阶段判为路径类错误并拒绝，退出码 `1`）；仅 workspace 根**之下**的目录条目 MAY 递归创建其父目录。
- **FR-029**: 前置校验能力 MUST 保持 F001-P1 已实现的契约不变（路径解析返回绝对路径 / 抛路径类错误；权限校验通过则正常返回 / 抛权限类错误；综合校验交付「绝对路径 + 名称 + 强制标志」三元组），MUST NOT 被本 Phase 修改或削弱。

#### sqlite3 结构构造器（实现要点 §4.7.6）

- **FR-030**: 系统 MUST 提供独立模块承载三个 sqlite3 结构构造能力（短期记忆库 / 长期记忆库占位 / 知识库占位）；安装包 MUST NOT 携带任何二进制 sqlite3 模板文件（避免结构定义与代码漂移，宪法 D-05）。
- **FR-031**: 短期记忆库构造 MUST 创建三张表 —— 上游 saver 自有的历史表与写入表（由上游 saver 的**实例**初始化能力创建，MUST NOT 以非实例方式调用）、以及工作区自管的会话元数据表；会话元数据表 MUST 含 6 个字段（会话 id / 标题 / 创建时间 / 更新时间 / donkey 版本号 / 首轮提示词快照），其中会话 id 为主键；并 MUST 创建标题索引与更新时间索引两个索引。**上游 saver 包 MUST 在 `pyproject.toml` 的运行期依赖中正式声明**（donkey 自此有且仅有这一个运行期依赖），其表结构由上游维护，donkey MUST NOT 自行手写这两张表的建表语句（MUST NOT 承担结构漂移风险）。
- **FR-032**: 长期记忆库与知识库占位构造 MUST 只创建**空**的 sqlite3 文件（0 张表、0 个索引），MUST NOT 建任何占位表；MUST NOT 被 donkey 本体的任何运行时路径读取（宪法 D-11）。
- **FR-033**: 结构构造 MUST 具备幂等性（MUST 使用"存在即不重建"的建表 / 建索引写法），已存在的表与索引 MUST NOT 被破坏；构造失败 MUST 统一抛出模板生成类错误 → 退出码 `3`。
- **FR-034**: 短期记忆库的表结构定义 MUST 与项目既有结构文档一致（`harness/report/sessions_sqlite表结构一览.md` §2.2 的字段与索引定义），MUST NOT 由本 Phase 自行发明结构；上游 saver 自有表的列定义由上游包决定，donkey MUST NOT 维护其列定义。

#### 模板生成类失败的 7 类成因（权威分类法）

模板骨架生成失败合并为**七类**成因，七者对用户的修复动作相同（重装 donkey / 检查权限 / 重试 init），按奥卡姆剃刀合并到**同一个退出码 `3`**，MUST NOT 各占一个码值：

- ① 模板清单缺失 / JSON 非法 / schema 非法；
- ② 模板源文件缺失；
- ③ 渲染失败（正文不可解析）；
- ④ 文件写入失败（磁盘满 / 权限在渲染中途被撤销）；
- ⑤ sqlite3 结构构造失败；
- ⑥ 上游 saver 包缺失 / 版本不兼容 / 导入失败；
- ⑦ 目标路径已存在且是目录（**且该条目为文本类或 sqlite3 类**）。

本清单是本 spec 的**唯一权威来源**；`contracts/exit-codes.md §4` 与 `data-model.md §8.1` 是它的**镜像**，冲突时以本清单为准。

#### 客户端异常映射与退出码（实现要点 §4.4 ~ §4.6）

- **FR-035**: 系统 MUST 定义模板生成类错误 `TemplateGenerationError`，MUST 归属于 `donkey init` 的错误基类之下，并 MUST 在其说明中标注对应退出码 `3` 并**引用**本 spec 的『模板生成类失败的 7 类成因（权威分类法）』段，MUST NOT 自行复述该清单；异常层次 MUST 保持为 —— 总基类 ← `donkey init` 基类 ← {`PathNotFoundError`（退出码 1）、`PathPermissionError`（退出码 2）、`TemplateGenerationError`（退出码 3）}。
- **FR-036**: 客户端的异常 → 退出码映射 MUST 由**单一全局映射表**驱动，MUST 登记模板生成类错误 → 退出码 `3`；其余异常处理逻辑 MUST NOT 因此改动（按类型查表自动生效）。
- **FR-037**: 系统 MUST 定义退出码常量 `3` 并在文档中标注其归属（模板骨架生成失败）；本阶段实际使用的退出码集合 MUST 为 `{0, 1, 2, 3}`；退出码 `4` / `5-10` MUST NOT 被本阶段任何代码路径触发，且 MUST 与其它子命令的段位空间无交集（宪法 N-08）。
- **FR-038**: 退出码语义 MUST 保持单一含义 —— `1` = 输入 / 路径 / 参数用法不合法；`2` = **权限不足（发生在前置校验阶段与工作区根目录创建阶段）**；`3` = **模板骨架生成失败（发生在模板骨架渲染阶段与工作区清单写入阶段，含渲染中途权限被撤销、磁盘满、源模板缺失、sqlite3 结构构造失败、上游依赖不可用、目标路径是目录）**。模板清单损坏 MUST NOT 复用退出码 `1`（二者的用户修复动作不同：前者"重装 donkey"，后者"建目录 / 换路径"）。`2` 与 `3` 按**阶段**切分，各自保持单一含义。**阶段 ③（创建 workspace 根目录）的一切失败一律归 `2`** —— 含磁盘满（`ENOSPC`）在内，`mkdir` 抛出的任何 `OSError` MUST 包装为 `PathPermissionError`；该阶段的失败**根因由错误信息承载**（MUST 指出磁盘空间 / 权限等实际原因），而"下一步"固定句仍沿用 F001-P1 的 `_NEXT_STEP`（MUST NOT 改动 P1 已有文案，FR-029）。`3` 侧的"磁盘满"仅指**渲染阶段（步骤 ④）**的写入失败。

- **模板类报错指引口径**（用户决策）：退出码 `3` 的错误信息 MUST 含可识别的错误标识 + 一条用户可执行的下一步，与退出码 `1` / `2` 保持一致。
- **强制清空提示的输出形态**（默认口径，非用户决策项）：该提示属**成功路径**提示，MUST 输出到**标准输出流**（失败信息才走标准错误流）；带强制标志时 MUST **恒定输出**（即使工作区此前不存在 sqlite3 文件 —— 此时亦无数据可清空），故提示文案 MUST 同时涵盖"已清空 / 已重建"两种情形，MUST NOT 写成只在"确有数据被清空"时才成立的断言。
- **工作区清单的写入入口**（默认口径，非用户决策项）：初始化流程调用的"写入工作区清单"能力与"确保存在"便捷封装 MUST **严格等价**（后者 = 带强制标志时直接覆盖、MUST NOT 先读旧文件；不带强制标志时先读后再定），二者由 plan 锁定其一；MUST NOT 产生两套不一致的覆盖语义。
- **工作区清单的强制覆盖口径**（默认口径，非用户决策项）：工作区清单**不在**模板清单条目内，却是 `--force` 唯一会覆盖的"清单外"路径（创建时间随之刷新）—— 此为"恢复出厂设置"语义的有意例外，MUST NOT 与 FR-013（渲染 MUST NOT 触碰清单外路径）冲突（前者约束渲染，后者是独立步骤）。
- **静态检查工具**：代码规范与类型检查工具沿用 F001-P1 已确立的口径（`ruff` + `mypy`），本 Phase 不引入新的检查工具。
- **验收脚本的调用前提**：验收脚本优先调用 PATH 上的 `donkey` 控制台脚本，且校验其解析到的包安装位置位于当前工作树内；不可用时回落到以当前解释器执行模块入口并打印一次显式告警，回落时以仓库根为工作目录 —— 确保被测对象是当前工作树的代码。
- **运行平台**：Linux / macOS（权限语义按 POSIX 判定）；Windows 平台不在本阶段范围。
- **特权环境说明**：权限相关断言**不依赖特权账号** —— 权限失败 MUST 以**注入式构造**产生（`monkeypatch` / mock 在写入边界抛 `OSError(EACCES)`），MUST NOT 依赖运行账号的特权状态：**特权账号（root / `CAP_DAC_OVERRIDE`）会绕过 DAC 权限检查**，其对 `0o555` 目录的 `access(W_OK)` 与实际写入**均成功** → chmod 只读目录的方案在特权环境下**失效**，MUST NOT 作为唯一构造手段（否则 FR-055 第 10 类「渲染中途权限失败」在 root CI 容器中必然假失败）。验收统一以注入式构造为准（plan R-18）。
- **术语口径**：本 spec 中 "Phase" = F001-P2（开发阶段）；"子段" = F001 子段 2（退出码 `3`）；"段位" = F001 段位 `1-10`；三者严格分层（宪法 §4.3）。"清单" = 模板文件清单（安装包内）；"工作区清单" = workspace 根的身份 manifest —— 二者 MUST NOT 混用（宪法 §2.6）。
- **范围外**：3 个内置工具文件 + 包初始化文件 + 示例 Skill 的完整第二层正文与第三层资源（F001-P3）；`donkey load` / `donkey session` / `donkey run` 等其它子命令（F002 / F003 / F004）；任何中间件挂载与模型连通性测试；workspace 路径末段名的合法性校验（v2+）；sqlite3 结构健康检查（属配置检查码段）。
- **下游流程**：本 spec 只定义"做什么"与"怎样算成功"；实现步骤、任务拆分、依赖版本锁定留给 `/speckit.plan` 与 `/speckit.tasks`。
- **宪法 §3.4 的 Phase 级豁免**（默认口径，非用户决策项）：宪法 §3.4 要求 `donkey init` 自动生成 3 个内置 `@tool`（filesystem / commandline / webfetch）作为 Skill Level 3 的标准访问通道 —— 该 MUST 在 **Feature F001 级**由 F001-P3 满足；本 Phase（F001-P2）依 spec FR-066 MUST NOT 生成它们（模板清单中零 `format: "python"` 条目，plan G14）。二者并非冲突，只是 Phase 切分的结果（宪法 §4.3 规则 B：按退出码段位切 Phase）。
