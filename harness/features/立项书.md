## 第 1 章 项目概述

### 1.1 项目名称

**donkey**，取"驴子"之意。

驴子，是一个倔强的、忠实可靠的工作者；**donkey 的职责是提供可靠的引擎，智能体本身是什么形状由用户决定（工作区）**。项目名想表达的核心主张是：**智能体的形态由用户在工作区里手搓定义，而不是由产品方的固定模板定义。**

### 1.2 项目背景与发起原因

#### 1.2.1 智能体产品形态的现状分类

当前市面上的智能体可以按"**智能体形态由谁定义**"与"**执行拓扑**"两个维度划分：

| 类别 | 形态定义方 | 执行拓扑 | 代表 | donkey 是否覆盖 |
|---|---|---|---|---|
| A. 通用型智能体 | 用户（配置文件） | 多 Agent × 多 Session | OpenClaw（`~/.openclaw/<agent>/`，含 SOUL / MEMORY） | 覆盖 |
| B. 编程型智能体 | 产品方（深度适配） | 单 Agent × 多 Session | OpenCode、Claude Code、Codex CLI | 覆盖 |
| C. 技能包型 | 用户（Skills 集合） | 单 Agent × 多 Session | Superpowers 等 Skills 仓库 | 不覆盖：donkey 只负责加载 Skill，不生成 Skill |
| D. 工作流编排型 | 产品方（图/代码） | 单图 × 多 Session | LangGraph 应用、n8n | 不覆盖：非 Agent Loop |
| E. 多智能体协同 | 产品方（编排/消息通道） | 多 Agent 共享上下文 | CrewAI、Aider 群聊式编排、MDA `channels/` | 不覆盖：非 Agent Loop |

**执行拓扑术语约定**：

- **Agent**：一个具备人格（Instructions）、能力（Tools）、知识/工作流经验（Skills）、大脑（Model）的独立实体。
- **Session**：一个 Agent 与一段连续对话的绑定，等价于 LangGraph 的 `thread_id`（`LangGraph_doc/checkpointers.md:39-41`：thread 概念定义 + `{"configurable": {"thread_id": "1"}}` 注入示例）。
- 一个 workspace 目录 **=** 一个 Agent（§1.2.4），一个 Agent 可以有 **多个 Session**。

#### 1.2.2 现有方案的共性局限（痛点归因）

现有智能体（A/B/C/E 类）普遍把"配置 + 工作数据 + 凭据 + 依赖声明"混合存放，典型形态是属主目录下的隐藏目录（`~/.openclaw`、`~/.config/opencode`）。真正的问题**不是"目录隐藏"**（那只是表象，可用 `XDG_CONFIG_HOME`、软链接解决），而是以下四条结构性缺陷：

| # | 缺陷 | 后果 | donkey 的应对 |
|---|---|---|---|
| P1 | **实体边界不清**：一个隐藏目录下可能包含多个 Agent，多个 Agent 共享同一套 Tools / Skills / 依赖 | 无法把"一个智能体"作为原子单位迁移、分享、版本化 | 一个 workspace 目录 = 一个 Agent，workspace 自带 manifest |
| P2 | **不可原子打包**：配置、凭据、依赖、运行数据混放无法"打包即走" | 跨机器迁移要手动挑文件容易漏 | 依赖与配置随 workspace 走；运行数据可选择性导出 |
| P3 | **路径耦合**：依赖进程 cwd、属主 HOME、隐藏目录约定 | 换个路径 / 换个用户就坏 | 所有内部引用以 workspace 绝对路径为唯一根，禁止依赖 cwd / HOME（§5.4） |
| P4 | **软件流程不可改**：智能体主流程写死，难以定制；一些极端业务场景需要在 Agent Loop 中添加中间件，传统智能体软件无法修改或学习成本高 | 智能体"没什么卵用" | 能力分两层：材料层（workspace，面向普通用户）与中间件层（fork，面向极客用户）。diff 审阅、路径权限交互属 harness/前端耦合能力，由产品方内置于引擎代码（fork 改造）。workspace 换不能获得工程级 harness 能力，**正确的切换路径是 fork 引擎**。 |

#### 1.2.3 智能体可移植性的两层模型（本稿核心边界，必须先读）

donkey 的能力分为两层，**可移植性不同**：

| 层 | 包含什么 | 定义方 | 交付方式 | 可移植性 |
|---|---|---|---|---|
| **材料层**（workspace 层） | Instructions、Model、Tools、Skills | **用户** | 一个目录 | 高：zip / git 带走，任意机器开箱即用 |
| **引擎层**（harness / runtime 层） | Agent Loop 图流程、middleware 链、diff 审阅与变更可视化、路径权限交互、前端交互范式、上下文治理策略、客户端渲染 | **产品方（donkey 代码）** | fork donkey 二次开发 | 低：workspace **无任何配置项**可以改变它 |

**为什么引擎层不可配置**：

1. donkey 明确禁止用户在 workspace 内自定义 Agent 图——Agent 图与前端客户端高度绑定，让用户肆意修改图可能引发客户端崩溃（§1.5.3）。一套前端 + 图引擎后端 = 一个大型智能体项目，工程量巨大，因此**图流程无法被 workspace 改变**。如果将智能体比作房子，前端是装修，后端是毛坯房，没有脱离毛坯房的装修。毛坯房中，LangChain 各种功能函数相当于建材（砖头、钢筋），LangGraph 发挥粘合剂、钉子等连接功能。用户提供 workspace 相当于地基，智能体必须跑在 workspace 上面。用户拎包入住，不会考虑房子怎么盖的；为了让房子更个性化，住户会在院子（workspace）里修绿化、搭狗窝。
2. diff 这类能力不是一次模型调用，而是"工具写入 → 拦截变更 → 生成 diff → 前端展示 / 人工确认 → 回写或回滚"的闭环，需要 **harness 中间件 + 客户端渲染 + 状态回滚**协同开发（例如 `after_agent` 阶段拦截、结合 `HumanInTheLoopMiddleware` 的中断-恢复，`LangChain_doc/middleware/built-in.md:618-669`），任何一端不在 workspace 可控范围内。
3. 路径权限同理：既要在引擎侧约束工具边界，又要在客户端侧呈现"哪些路径可写"的交互，两端都是代码。

**由此得到的三条结论**（贯穿全文）：

- **结论 1**：workspace 换一换，可以把智能体从"通用助理"变成"会 Python 的助理"（人格 / Skills / 工具 / 模型变了），但**不能**把 donkey 变成 OpenCode。
- **结论 2**：需要 diff、路径权限等工程级 harness 能力的用户，**唯一官方路线是 fork donkey 本仓库二次开发**；donkey 的职责是让 fork 成本足够低（分层清晰、适配层收敛、workspace 契约稳定），而不是把这些能力做成配置。
- **结论 3**："编程型 workspace"提供的是 **编程人格 + 编程 Skills + 编程工具 + 模型选型**，属于材料层；官方模板不承诺提供 diff 审阅（§4.3、AC-5）。

#### 1.2.4 参照物：Managed Deep Agents（MDA）的"You provide"模型

MDA 官方架构图把"提供给智能体的材料"归纳为 4 类（`Managed_deep_agents/langsmith/python/managed-deep-agents-overview.md:15-16`）：

1. **Instructions** —— 系统提示词（`instructions.md`）。
2. **Tool** —— 带 `@tool` 装饰的函数（`tools/`）。
3. **Skills** —— Agent Skills（`skills/<name>/SKILL.md`）。
4. **Model** —— LLM / VLM。

> **重要参考信息**：MDA 同一文档的能力表实际列出 **12 项**用户侧文件（agent.py / instructions.md / skills/ / tools/ / connectors/ / middleware/ / sandbox/ / memory.py / identity.py / channels/ / schedules/ / evals/，`overview.md:147-159`），且 `define_deep_agent` 还有 `middleware` / `subagents` / `response_format` / `interrupt_on` / `permissions` / `name` / `model` / `tools` 等多个参数（`managed-deep-agents-agent-definition.md:55-64`，参数表覆盖 8 项）。

**donkey 的取舍（关键设计决策）**：只把 4 类材料下放给用户，其余能力全部收归引擎侧统一实现。这不是功能删减，而是把"用户可配置面"从 12 项压缩到 4 项（详见 `overview.md:147-159` 的 12 项表：agent.py / instructions.md / skills/ / tools/ / connectors/ / middleware/ / sandbox/ / memory.py / identity.py / channels/ / schedules/ / evals/），从而让**材料层形态**（人格 / 知识 / 手脚 / 大脑）能够仅靠替换 workspace 完成切换，同时由引擎统一保证安全、上下文治理、HITL、依赖加载的一致性。**注意：收编意味着"由 donkey 决定"，不意味着"由用户配置"**——收编能力同样不在 workspace 可控范围内，改造它们需要 fork（§1.2.3）。收编清单见 §4.2.3。

**Skills 三层渐进披露模型（donkey 核心设计）**：每个 Skill 目录 `skills/<name>/SKILL.md` 的信息按访问频度分为三级，对应三种不同的加载路径：

| 级别 | 内容 | 加载方式 | 触发时机 |
|---|---|---|---|
| **Level 1** | `SKILL.md` frontmatter 必填两字段：`name` + `description` | 由 donkey core 扫描后**自动注册为独立 `@tool`**（工具名 `load_skill_<slugify(name)>`，工具 description = frontmatter description 轻度改写 + 1 句触发短语） | 工具列表常驻（每次模型调用都可见） |
| **Level 2** | `SKILL.md` frontmatter 下方的 Markdown 主体（从第二个 `---` 一直到文件末尾） | 通过 Level 1 工具调用即可披露（返回值含 Level 2 完整内容） | 模型判断 Skill 与当前任务相关时调用 |
| **Level 3** | Skill 目录内的其他文件（`reference/`、`scripts/`、`templates/` 等 SKILL.md 之外的文件） | **按访问类型选用四类工具**：（a）文件操作类（读/写/复制/删除/移动/列表/属性）→ workspace `tools/filesystem.py` 内置 `@tool`；（b）内容搜索类（glob 匹配 + grep 检索）→ 引擎侧 `FilesystemFileSearchMiddleware` 暴露的 `glob_search` / `grep_search` 工具；（c）Shell 执行类 → `tools/commandline.py`；（d）HTTP 拉取 → `tools/webfetch.py` | 模型需要更深层细节 / 实际执行 / 拉取外部数据时调用 |

**Per-skill 工具返回值**：当模型调用 `load_skill_<name>` 时，返回内容为：
1. **Level 2 完整内容**（SKILL.md 主体 Markdown）
2. **Level 3 文件清单**（Skill 目录下所有非 SKILL.md 文件的相对路径列表，**不读内容**——模型要读时按"操作 vs 搜索"分别调 `tools/filesystem.py` 或 `FilesystemFileSearchMiddleware.glob_search/grep_search`）

**为什么是这套设计（容错分析）**：

| 场景 | 效果 |
|---|---|
| 用户删除所有 `tools/*.py` 自定义工具 | ✅ Level 1/2 仍可达（per-skill tool 由 donkey core 注册） |
| 用户清空 `mcp/mcp.json`（无 MCP server） | ✅ Level 1/2 仍可达 |
| 用户禁用 `commandline.py` 工具（出于安全考虑） | ⚠️ Level 3 中的 `scripts/*.py` 不可执行，但仍可读 |
| 用户仅保留 `filesystem.py` 一个内置工具 | ✅ Level 1/2 完全可达；Level 3 中文本文件可达，二进制/脚本需 `commandline.py` |
| workspace 完全没有 `tools/` 目录 | ❌ Level 3 完全不可达（donkey init 阶段生成三大内置工具，避免此场景） |

> **核心设计判断**：donkey init 阶段**自动生成** 3 个内置 `@tool`（filesystem/commandline/webfetch）作为 Skill Level 3 的标准访问通道。这沿用 OpenCode 的内置工具设计（业界验证）。用户**可以删除/重写**这些工具，但默认行为开箱即用——避免"用户不知道 Level 3 怎么读"的体验断裂。详见 §4.6.1 与 §4.3 `core/skills/loader.py`。

#### 1.2.5 donkey 的定位：workspace 即智能体的材料

**donkey 是一个引擎，负责拉起用户手搓的 workspace 目录。**

- 用户通过修改 4 类材料，把同一台 donkey 引擎"调成"通用型 / 加载型（材料层变体，§1.2.3）。
- 一个 workspace 目录 = 这个智能体**材料层**全部定义，**不存在必须依赖 workspace 以外文件才能让 Agent Loop 跑起来配置**。
- workspace 可以存放在任意路径（用户有适配执行权限即可），donkey 不要求它位于属主目录或任何隐藏目录下。
- **引擎工作流程不可变**：diff 审阅、路径权限交互、自定义图流程等引擎层能力。它们的唯一扩展方式是 fork donkey 二次开发。

### 1.3 项目目标

1. **用户可定制的智能体（材料层）**：人格、知识、手脚、大脑完全由 workspace 内的 4 类材料决定，引擎不内置任何"特定用途"的材料默认值。
2. **最小化工作区**：一个 workspace 目录 = 一个智能体**材料层**全部定义，可压缩为 zip 后跨机器迁移并开箱即用。
3. **工作区与 runtime 解耦**：业务定义（workspace）与执行宿主（客户端）分离，客户端形态可扩展（CLI / Web / GUI）。
4. **可验证性**：任何 workspace 在 `donkey run` 之前，都可通过只读命令得到确定"能否运行"结论。
5. **可演进性**：workspace 有格式版本号，donkey 升级时提供迁移路径。
6. **可 fork 性**：需要引擎层能力（diff、权限交互、自定义流程）的用户，通过 fork donkey 二次开发实现；引擎分层与 workspace 契约的稳定是此项前提。fork 后开发者只需做三件事：编写中间件代码，将中间件添加到图中，前端适配图。

### 1.4 项目价值与预期收益

| 价值 | 说明 | 度量方式 |
|---|---|---|
| **高可移植性** | workspace 打包（zip / git）→ 拷贝到任意路径、任意机器 → `donkey load` 通过即可运行 | 迁移验收用例（§3.5）通过率 100% |
| **材料层形态可切换** | 通过替换 workspace，通用型 / 编程型 / 技能型的**人格、知识、手脚、大脑**互转，无需改引擎 | 三套官方模板 workspace 均可 v1 交付并运行 |
| **引擎层能力可 fork** | 需要 diff、配置加载、自定义流程的用户可 fork donkey 二次开发，fork 成本受控 | 提供 fork 指南（配置边界、适配层说明、扩展点清单） |
| **可组合性** | 多个 workspace = 多个独立智能体，可由外部编排为协同形态（v2 由 Scheduler 承担） | §4.5 v2 范围 |
| **降低试错成本** | load 前置 + 静态/动态两阶段检查，避免在 Agent Loop 中途以"看起来像模型抽风"形式暴露 | load 覆盖 §5.5.3 9 项检查清单全部项 |
| **工程可维护** | 引擎与用户逻辑分层清晰，用户无需理解 LangGraph 内部结构即可升级智能体 | 引擎升级不要求用户改 workspace（除格式迁移） |

### 1.5 项目范围边界

#### 1.5.1 使用 AI 编程工具的开发哲学

1. Vibe Coding 已经可以做到程序员全年 0 代码开发。
2. 编程工具无法代替人做需求整理、架构设计、流程设计、设计优化、缺陷修复等工作。
3. 如果 feature 提示词编写到位，通过 SuperPowers、Speckit 这类 TDD 工具，可以写出高质量代码。
4. 如果 feature 提示词改动，则需要重写代码，所以返工的代价很高。遵循瀑布式开发流程，项目开发时需要小步快跑，及时验证，否则返工几乎等于推倒重来。架构方面倾向于洋葱架构，先产生一个核心，然后核心不动，在核心基础上不断添加新的功能。

综上，Vibe Coding 的面世，替代了之前"只会死写代码"的初级和中级程序员，对高级程序员（拿到需求后撰写feature）、架构师（需求评审）、产品经理（需求对齐）的影响并不大。feature 之下我无敌，feature 之上一对一。AI 出现只是把程序员的入门门槛提高了，并不是取代。程序员必须跨过 feature 这条线，才能为公司产生价值。不能像以前那样，等着别人写 feature 提示词，然后我来开发。

#### 1.5.2 本项目版本与功能规划

**版本命名准则**：前端版本与 donkey 后端的 LangGraph 图版本对应。

版本格式按 `vx.y.z` 规划，如 `v0.0.1`、`v1.18.2` 等。x、y、z 取自然数（0 到正无穷）。

- `x` 对应前端版本或 donkey 后端图版本，前端只有 `v1.0.0`、`v2.0.0` 等。如果开发者修改了 LangGraph 图流程，则 `x+1`。
- 这些行为视为修改图流程：
  1. 修改 LangGraph State 结构。
  2. 修改 Edge 导致节点连接变化。
  3. 节点数量变化。根据 `harness/report/LangGraph的节点到底是什么东西.md` 调研结果：
     - **wrap-style 中间件**（`wrap_model_call` / `wrap_tool_call`）**不创建新节点**——嵌套在 `model` / `tools` 节点内部，洋葱式调用链；
     - **node-style 中间件**（`before_agent` / `before_model` / `after_model` / `after_agent`）**每个 hook 创建 1 个真节点**——作为 LangGraph 图中的独立节点执行，`before_*` 顺序执行、`after_*` 倒序执行；
     - **无 hook 中间件**（仅注册工具，不挂任何钩子）——0 节点，仅增加工具列表项；
     - Graph 主图中节点数量变化或者任何中间件的节点数量变化，`x+1`。
- 注意：LangGraph 节点代码修改、以及中间件内部节点修改属于代码优化，不算做图变化，因为没有影响到 State 和 Edge，因此 `x` 不 `+1`。

**wrap-style vs node-style 边界细则**（避免边界模糊）：

| 修改类型 | 是否触发 `x+1` | 例子 |
|---|---|---|
| wrap-style 中间件的参数调整（如 `max_retries` 改 2→3） | ❌ 不触发（代码优化，不改图） | ToolRetryMiddleware `max_retries=3` |
| wrap-style 中间件的代码改 bug | ❌ 不触发 | ToolErrorMiddleware 异常处理逻辑修复 |
| node-style 中间件的 hook 内部代码调整 | ❌ 不触发（仍是同一节点） | PIIMiddleware 检测规则调整 |
| node-style 中间件的 hook 数量调整（如 before_model 加一个） | ✅ 触发（节点数变化） | SummarizationMiddleware 新增 `before_agent` hook |
| wrap-style 中间件**新增** node-style hook（如 `wrap_tool_call` → `wrap_tool_call + before_model`） | ✅ 触发（从 0 节点变 +1） | ToolRetryMiddleware 增加 before_model |
| node-style 中间件**新增** wrap-style hook（如 `before_model` → `before_model + wrap_tool_call`） | ❌ 不触发（wrap-style 不增节点） | PIIMiddleware 增加 `wrap_tool_call` |
| 中间件**整体替换**（如 ToolError → ToolErrorV2，hook 模式变了） | ✅ 触发（节点结构变了） | 模型替换 |

- `y` 对应该图版本中各个节点与中间件的 id，取值正整数（1 到正无穷）。LangGraph 主图中的节点对应一个 id；一个中间件里可能包含多个节点，中间件的每个节点对应一个 id。举例：`x=1` 第一版图中，第一个主图节点版本号就是 `v1.1`，此后一个中间件包含两个节点，则这两个节点版本号分别为 `v1.2` 和 `v1.3`，以此类推。
- `z` 表示当前节点 id 的修改版本，某个节点每修改一次，`z+1`。

#### 1.5.4 最小化 v1 智能体的 LangChain 中间件录用名单

筛选 `harness/report/LangChain内置中间件速查表.md` 中 LangChain 自带中间件。录用名单（**10 项**，含 `FilesystemFileSearchMiddleware`——它与 workspace `tools/filesystem.py` 内置 `@tool` **功能正交不重叠**，详见 §1.2.4 三层模型容错分析）：

每项中间件后标注 **hook 风格**（wrap-style / node-style / both / 无），便于维护者判断该中间件对 LangGraph 主图节点数的影响（详见 §1.5.2 边界说明 + §4.4.1 节点清单）：

| 中间件 | 功能 | hook 风格 | 对主图节点数影响 |
|---|---|---|---|
| **ToolErrorMiddleware** | 工具异常 → ToolMessage | **wrap-style**（`wrap_tool_call`） | 0（嵌套） |
| **ToolRetryMiddleware** | 工具调用指数退避重试 | **wrap-style**（`wrap_tool_call`） | 0（嵌套） |
| **ModelRetryMiddleware** | 模型调用指数退避重试 | **wrap-style**（`wrap_model_call`） | 0（嵌套） |
| **SummarizationMiddleware** | 接近 token 上限压成摘要 | **node-style**（`before_model`） | +1（before_model） |
| **ModelCallLimitMiddleware** | 限制模型调用次数防失控 | **node-style**（`before_model` + `after_model`） | +2（before + after） |
| **PIIMiddleware** | PII redact/mask/hash/block | **both**（`before_model` + `after_model`，**框架始终编译为 2 节点**——见下方注 2） | +2（before + after） |
| **TodoListMiddleware** | 注入 `write_todos` + 系统提示 | **both**（`after_model` 节点 + `wrap_model_call` 包装） | +1（after_model） |
| **LLMToolSelectorMiddleware** | 预筛选工具列表 | **wrap-style**（`wrap_model_call`） | 0（嵌套） |
| **ContextEditingMiddleware** + **ClearToolUsesEdit** | 清理旧 tool 结果 + `[cleared]` 占位 | **wrap-style**（`wrap_model_call`） | 0（嵌套） |
| **FilesystemFileSearchMiddleware** | 注入 `glob_search` + `grep_search` 工具 | **无 hook**（仅工具注册） | 0（仅多 2 个工具，0 节点） |

> **hook 类型依据**（基于 `.venv/lib/python3.12/site-packages/langchain/agents/middleware/*.py` 源码实证 + `LangChain_doc/middleware/built-in.md` + `LangChain_doc/middleware/custom.md:33-43` 钩子系统说明）：
> - **wrap-style**：中间件类**仅重写** `wrap_model_call` / `wrap_tool_call`（不重写 `before_*` / `after_*`），被洋葱式嵌入到 `model` / `tools` 节点内部，不增图节点；
> - **node-style**：中间件类**重写**了 `before_*` / `after_*` 中的至少一个，每个 hook 被 LangGraph 工厂（`factory.py:1642-1688`）编译为独立图节点；
> - **PIIMiddleware 注 2**：**无论 `apply_to_input` / `apply_to_output` / `apply_to_tool_results` 如何配置，PIIMiddleware 始终编译为 2 节点**——因为 LangGraph 工厂**只检查子类是否重写了方法**，不检查方法体是否早返回。`pii.py:799-846` 重写了 `after_model`，即使默认 `apply_to_output=False` 让 body 立即 `return None`，`after_model` 节点仍存在。**配置标志只控制"该节点做什么"，不控制"该节点是否存在"**——这是 donkey 选用 PIIMiddleware 时的关键成本；
> - **TodoListMiddleware** 同时挂 `after_model` 节点 + `wrap_model_call` 包装（实测；源码 `todo.py` 含两个方法）；
> - **FilesystemFileSearchMiddleware 无 hook** 依据："The middleware adds two search tools to agents"（LangChain 内置中间件文档）——仅工具注入，不需要任何 hook；
>
> 详细的主图节点清单（合计 10 个节点）见 §4.4.2。

各中间件具体描述（保留原内容）：

- **ToolErrorMiddleware**：把工具异常转成 ToolMessage 反馈给模型，让模型能自我修正。
- **ToolRetryMiddleware**：工具调用失败时按指数退避自动重试，应对外部 API 的瞬时网络故障。可配最大重试次数、初始/最大延迟、抖动以及失败后行为（继续/抛错/自定义）。
- **ModelRetryMiddleware**：模型调用失败时按指数退避自动重试，处理模型 API 的瞬时错误（429/503 等）。可配退避参数和失败处理（返回错误消息或重新抛异常）。
- **SummarizationMiddleware**：文本侧压缩：接近 token 上限，把旧消息压成文本摘要、保留最近 N 条。
- **ModelCallLimitMiddleware**：限制单次 run 或整条 thread 内的模型调用次数，防止 agent 失控循环、烧光 API 配额或成本失控。
- **PIIMiddleware**：检测并处理 PII：内置支持 email/credit_card/ip/mac_address/url 等类型，可配置 redact/mask/hash/block 策略，可应用到输入、输出、流式输出或工具结果。
- **TodoListMiddleware**：为 agent 注入 `write_todos` 工具与配套系统提示，使其能够规划多步计划并跟踪进度，适合需要协调多工具、多步骤的复杂任务。
- **LLMToolSelectorMiddleware**：在调用主模型前先用一个小模型（或主模型）对工具列表做筛选，仅把与当前查询最相关的 K 个工具喂给主模型，减少 token 消耗选择准确性，适合工具数 10+ 的场景（donkey 场景：用户加大量 Skill 时 per-skill `load_skill_<name>` 工具会膨胀到 30+，**必备**）。
- **ContextEditingMiddleware + ClearToolUsesEdit**（前者是后者 `edits` 参数的实例）：前者清除上下文中所有 `role:tool` 的工具执行结果；后者在被清理位置添加 `[cleared]` 占位符号。
- **FilesystemFileSearchMiddleware**：为 agent 提供 `glob_search`（按 glob 模式匹配文件名）和 `grep_search`（基于 ripgrep 的内容正则检索），常用于代码库探索、定位文件或搜索代码内容（**仅搜索，不涉及文件读写修改**——与 `tools/filesystem.py` 内置 `@tool` 功能正交）。

#### 1.5.5 最小化 v1 智能体不录用中间件名单

- **ModelFallbackMiddleware**：retry 大模型都不行就死球，还降什么级。如果降级大模型的上下文长度与主模型不一样怎么办？所以不折腾，直接禁用。
- **ToolCallLimitMiddleware**：与 ModelCallLimitMiddleware 功能重叠（前者按工具名细粒度限流、后者按模型调用次数粗粒度限流），v1 粗粒度已够用，工具级细粒度留给 fork 用户（合规 §1.2.3 引擎层不可配置）。
- **ProviderToolSearchMiddleware**：很少有供应商提供此功能，所以不使用。
- **HumanInTheLoopMiddleware**：v1 最小化智能体不需要，后续 v2 版本专攻 HITL，再添加。
- **LLMToolEmulator**：测试用中间件，不用于最小化智能体。
- **ShellToolMiddleware**：命令行功能由 workspace `tools/commandline.py` 内置 `@tool` 实现（每次新建进程 + timeout，不走持久 shell），避免 ShellToolMiddleware 持久会话 + HITL 冲突与 HostExecutionPolicy 无 timeout 的已知问题。
- **FilesystemMiddleware**（deepagents）：deepagents 专有 + 默认 backend 不是磁盘——官方明确 "By default, these tools write to a local 'filesystem' in your graph state"，违反 §4.6.1 收编要求（用户期望真实磁盘 IO）+ 宪法 N-12（禁止依赖 deepagents）。
- **SubAgentMiddleware**（deepagents）：deepagents 专有 + 违反宪法 N-02（subagent 禁止）。donkey 哲学"agent = 人"，不存在"子智能体"把人降级为子工具的概念（参见 §1.2.3 P4 表第 4 行）。
- **RubricMiddleware**（deepagents）：deepagents 专有 + 官方明确 `RubricMiddleware requires deepagents>=0.6.5. It is in beta; the API may change in the future`。Beta API 不稳定 + 违反宪法 N-12（禁止依赖 deepagents）+ §2.1 已声明本项目不绑 LangSmith（与 LangSmith 自带的 LangSmith Tracing 自检机制冲突）。
- **SkillsMiddleware**（deepagents，`built-in.md` 不收录、`agents.md:1107-1233` 描述）：deepagents 专有 + 自研 Skills 系统已在 §4.3 落地（基于 LangChain `AgentMiddleware.wrap_model_call` 模式 + `LangChain_doc/multi-agent/skills-sql-assistant.md:165-225` 的 SkillMiddleware 参考实现），无 deepagents 依赖需求。
- **MemoryMiddleware**（deepagents，`agents.md:1107-1233` 描述）：deepagents 专有 + v3 自研 SqliteStore 已在做（§4.10 TD-02 完整路线图：~5 人周工作量 + 接口契约参考 `Saver和Store.md §七 + §十二`）。

## 第 2 章 项目背景与必要性

### 2.1 行业趋势与政策环境

**趋势判断**：

1. **Agent 从"框架"走向"目录"**：LangChain 1.x 以 `create_agent` 为顶层工厂（`LangChain_doc/agents.md:19-25`：工厂函数定义 + 4 个最小用法示例），其运行底层即 LangGraph 编译图（`LangChain_doc/runtime.md:5`：create_agent runs on LangGraph's runtime）；LangChain 把项目形态定义为 `langgraph.json` + `graphs` 映射 + 依赖文件（`LangGraph_doc/application-structure.md:42,96-112`：目录树 + Dependencies + graphs 键映射）；MDA 更进一步，把 agent 明确表述为"a directory of files"（`managed-deep-agents-overview.md:3`）。**"目录即智能体"已成为官方共识形态**，donkey 与之同频。
2. **能力以中间件（middleware）插件化组合**：LangChain 提供 19 项内置中间件（重试、回退、摘要、HITL、PII、调用上限、shell、文件检索等，`LangChain_doc/middleware/built-in.md:15-35`：内置中间件 19 项表格）；Deep Agents 提供 filesystem / skills / memory / subagent 中间件（`LangChain_doc/deep-agent-from-scratch.md:870-875`：deepagents 中间件 5 项表格）。引擎侧收编能力（§4.2.3）是当前主流架构。
3. **Skills 成为用户指导 ReAct 智能体工作流的事实标准**：Markdown + YAML frontmatter（`name` / `description`）+ 渐进披露（`LangChain_doc/deep-agent-from-scratch.md:459-473`：渐进披露概念 + frontmatter YAML 模板；`Managed_deep_agents/langsmith/python/managed-deep-agents-skills.md:5`：frontmatter-based progressive disclosure 官方说法）。Skills 可以指导智能体第一步做什么、第二步做什么……但 Skills 中的 scripts 脚本无法开箱即用、协议不完善，所以无法完全替代 MCP 与内置工具，Skills 在实际生产中更多地充当工作流指导者的角色。donkey 采纳统一标准格式的 SKILL 以获得生态兼容。
4. **MCP 成为工具接入事实标准**：LangChain 通过 `MCPAdapter` 支持 http / stdio / in-process 等形态（`LangChain_doc/mcp.md:45-71` Transports 章节列出三种 target 类型 + `tools.md:1733-1752` "Tools from MCP servers" 章节给出 http 示例）。donkey v1 直接复用 `MCPConfig` JSON 格式，不自造格式。
5. **托管方案尚不稳定**：MDA 处于 **public beta，且仅在 LangSmith Cloud 美国区可用**（`managed-deep-agents-project-structure.md:8`、`managed-deep-agents-overview.md` 页内 Note）。这是 donkey 选择"自建本地 runtime、不绑定托管平台"的直接理由。本项目全程不使用 LangSmith。
6. **合规与数据边界**：智能体工作区天然承载凭据、对话历史与业务代码，跨境托管与数据出境会成为企业选型的一票否决项。donkey 默认全本地运行，workspace 迁移由用户自主控制（§9.4）。

**v1 典型场景**：

1. **随身工程师**：在 A 机器的 `/data/agents/ada/` 写好 Skills 与 Tools，`zip -r` 后拷到 B 机器解压，`donkey load` 通过后直接 `donkey run`。
2. **私有代码助手**：workspace 内 `tools/` 只暴露白名单工具，`mcp/mcp.json` 接远程文档 MCP，不暴露 shell。
3. **流程固化**：把团队规范写成 `skills/xxx/SKILL.md`，description 精确描述触发条件，模型按需加载（渐进披露）。
4. **（超出 v1 承诺）需要 diff 审阅的编程助手**：fork donkey，在引擎层加入 diff 中间件与客户端展示，workspace 层仍使用标准 4 类材料（fork 指南见 §10.3.2 Q-08）。

|---|---|---|---|---|
| OpenClaw | 属主隐藏目录 `~/.openclaw/<agent>/`，多 Agent 共存 | 低：目录内多实体耦合（P1/P2） | 低（配置项驱动） | donkey 必须做"单目录 = 单实体"的原子边界 |
| OpenCode / Claude Code / Codex CLI | 工具配置在 `~/.config/<tool>`，工作数据在各自项目目录 | 中：配置与数据分离但不可整体打包 | 不适用（单一用途） | 证明 B 类工程能力（diff、路径权限）是**引擎层**能力：需要 harness + 前端联动开发，workspace 配置无法获得（§1.2.3） |
| Superpowers 等 Skills 仓库 | 纯 Skills 目录 | 高 | 极低 | 证明 Skills 是可独立移植的最小单元；donkey 把 Skills 提升为四大材料之一 |
| CrewAI / LangGraph 应用 | 代码即智能体 | 中：可打包但需装依赖、配环境变量 | 高（要改代码） | D 类形态强在定制，弱在开箱即用；donkey v1 明确不覆盖（§4.3） |
| Managed Deep Agents | 项目目录（`agent.py` 必填 + 12 项可选文件） | 中：可上传部署，但 `.env` 不入 build archive（`managed-deep-agents-project-structure.md:69`），且受托管平台约束 | 低 | MDA 的 4 类材料划分被 donkey 采纳；MDA 收编其余能力，donkey 同样收编 |

**差异化定位**：donkey 不是"更好的某个智能体产品"，而是 **智能体材料层的可移植运行时**——材料归用户，运行归引擎；需要改引擎的，走 fork 路线。

### 2.4 业务痛点与机会点

- **痛点 1（P1/P2）**：无法把"我的智能体"当一个文件/一个 zip 交付给别人。**机会**：workspace-as-artifact。
- **痛点 2（P4）**：能力分属两层而用户常常误以为"换个配置就能换形态"。真正想拿到 diff 审阅、精细权限的用户，无论换 workspace 还是换配置都得 fork。**机会**：把两层边界写清楚——**材料层开放到 workspace，引擎层开放到源码（可 fork）**，两条路都留门。
- **痛点 3（可验证性）**：配置写错时，错误以"模型不听话"的形式出现，排查成本高。**机会**：load 前置、静态/动态两阶段检查。
- **痛点 4（信任边界模糊）**：智能体能读写哪些文件、能执行什么、密钥存在哪里，用户说不清。**机会**：workspace 内显式声明路径权限与工具白名单（§5.6）。

### 2.5 项目必要性说明

1. **不做的代价**：每个新的智能体形态都要重写一遍 harness（提示词拼装、工具注册、Skills 发现、上下文治理），重复投入且质量不可控；其中材料层部分写本不该重写，引擎层重写则确实需要专业开发。
2. **做的收益**：引擎一次投入后，**材料层**新增形态的成本 = 新写一个 workspace；**引擎层**新增能力由 fork 者在其分支上迭代，不阻塞主线用户。
3. **时机**：LangChain 1.x 已提供足够的内置中间件与 API，donkey 不需要自研 Agent Loop 底座（§9.1）。
4. **风险可控**：v1 范围收窄至单进程 + 单 workspace + 三种客户端（cli / web / gui），可在一期验证核心假设（可移植性 + 跨客户端复用）。

#### 3.2.3 验收标准（AC）

- **AC-1**：workspace 在 **≤ 100 MB** 范围内，`donkey load` 通过率 100%。**不设下限**。
  - **① 体积**：不设下限硬卡——"刚 init 完骨架，还没填业务内容"的 workspace 误报失败是反直觉的 check。
  - **② 静态检查（exit 11-14 段：providers/ / mcp.json / SKILL.md frontmatter / instruction.md）**：`donkey init` 产物中**除 `providers/` 外的部分 100% 通过**（`instruction.md` / `mcp/mcp.json` / `skills/example/SKILL.md` / `memory/` 占位）。
  - **③ `providers/` 的出厂态 = 未配置态**：`donkey init` 生成 26 个 provider stub（**全部 `enabled = false`**）+ `providers/default.toml`（`default_provider` / `default_model` 为空）。此时 `donkey load` 在**静态检查 1** 上报 **exit 11**（`ProviderTomlFieldError`），错误消息必须给出**三步配置指引**：① 把 `providers/<id>.toml` 的 `enabled` 改成 `true` → ② 填入真实凭据（`api_key` / `aws_*`）→ ③ 在 `providers/default.toml` 设 `default_provider` / `default_model`。
    > **为什么不再要求出厂态静态全绿**：v0 草案用 `api_key = "REPLACE_ME"` 占位符骗过"空 key = 硬错 exit 11"的静态检查；v1 引入 `providers/` 目录 + `enabled` 开关后，**未启用的 provider 文件完全惰性**（连空 key 都不检查），占位符 hack 被自然废除。"启用哪个 provider / 用哪个 model 作默认"是**必须由用户决策**的问题（调研 §11.2 / README §2.2 奥卡姆原则：error = 用户必须决策的硬问题）→ 归入 error（exit 11），而不是 warning。
    > **代价与补偿**：AC-1 静态口径由"出厂产物 100% 通过"修订为"**配置完成后 100% 通过**"（完成 = 至少 1 个 enabled provider + `default.toml` 填好 + 必填凭据到位）；未配置时的失败路径必须**自解释**（错误消息 = 配置教程），不允许出现裸 exit code。
  - **④ 动态检查（模型连通性 exit 15）**：需用户填入真实 `api_key` 后才通过。
- **AC-2**：workspace 迁移（zip → 解压 → 任意路径）后 `donkey run` 不出现路径相关错误。
- **AC-3**：`donkey init` 幂等：重复执行不破坏已存在文件（除非 `--force` 且 check 出错）。
- **AC-4**：换 workspace 后模型、工具、Skills、提示词全部随之切换，无需重启 donkey。
- **AC-5**：v1 官方模板**不承诺**提供 diff 审阅、路径权限交互等引擎层能力；如需这些能力，由 fork 路线提供。

```python
def test_scenario_1_new_workspace(tmp_path):
```

**长期记忆选型论证**（v3 SqliteStore 技术路线，§4.10 TD-02 展开）：

调研依据见 `harness/report/Saver和Store.md`：

- **§1 概念区分**：Saver = thread 内短期；Store = 跨 thread 长期；二者物理隔离、语义独立（`Saver和Store.md §1`）。
- **§2 Store 类型**：LangGraph 官方 9 个 Store 实现（InMemory / Postgres×2 / Redis×2 / Oracle×2 / MongoDB / Upstash），**无 SQLite Store**。这是 v3 自研的事实基础。
- **§3 Saver 类型**：13 个官方 Saver，**SqliteSaver 是唯一零配置本地文件选项**（其他都需要外部服务进程）。
- **§5.1 配对推荐**：Saver + Store 同款配对的现成选项 = PostgreSQL / MongoDB / Redis 三套，**均需外部服务进程**（daemon / docker / cloud）。

| 选项 | Saver | Store | 部署成本 | 是否覆盖 donkey 场景 |
|---|---|---|---|---|
| PostgreSQL | ✅ PostgresSaver | ✅ PostgresStore | 高（需 daemon / docker） | ❌ 违反 §1.2.2 P2 打包即走 |
| MongoDB | ✅ MongoDBSaver | ✅ MongoDBStore | 高（需 server） | ❌ 同上 |
| Redis | ✅ RedisSaver | ✅ RedisStore | 中（可自托管） | ❌ 仍有进程依赖 |
| SQLite + 自研 Store | ✅ SqliteSaver | 🛠️ v3 自研 | **零**（本地文件） | ✅ 唯一满足 §1.2.2 P2 的方案 |
| InMemoryStore | ❌ | ✅ InMemoryStore | 零 | ❌ 进程重启即丢（`Saver和Store.md §2.2`） |

**技术路线**：v3 自研 SqliteStore **仿照 LangGraph 官方 PostgresStore**（`Saver和Store.md §十二` 已列实现蓝本），不是漫无目的开发：

1. **接口契约**：`BaseStore` 必实现 5 个 async 方法（`aput / aget / adelete / asearch / alist_namespaces`，`Saver和Store.md §七`）。
2. **数据模型**：主键 `(namespace, key)`（namespace 为 `tuple[str, ...]`）；值用 `json.dumps` / `json.loads` 序列化（Postgres 用 JSONB，SQLite 用 TEXT + `json_extract`）。
3. **索引**：namespace 列加 GIN-like 索引（SQLite 用 FTS5 或自定义 LIKE 前缀匹配函数）。
4. **参考实现路径**：`langgraph-checkpoint-postgres` 包内的 `PostgresStore` 是官方参考；SQLite 端口本质是 SQL 方言移植 + JSONB→TEXT 适配。

**为什么不用 InMemoryStore 作为长期方案**：进程重启即丢全部长期记忆（`Saver和Store.md §2.2`），违反 §1.2.2 P2 跨机器迁移要求。

**工作量评估**：约 4~6 人周（含单元测试 + 集成测试 + 与 LangGraph `BaseStore` 主线适配）。详见 §7.1 成本表 v3 阶段项。

**`core/skills/` 模块详细设计**（实现 §1.2.4 三层模型 + §1.5.4 `LLMToolSelectorMiddleware` 协同）：

| 模块 | 职责 | 关键 API |
|---|---|---|
| `loader.py` | 启动时扫描 `skills/<name>/SKILL.md`，解析 frontmatter（用 `python-frontmatter` 库） | `discover_skills(workspace_path) -> list[SkillLevel1]` |
| `registry.py` | 把每个 SkillLevel1 包装成独立的 `load_skill_<name>` `@tool`，工具 description = `SkillLevel1.description` + 1 句触发短语（"Use when user mentions X"）；工具 docstring 包含 Level 2 加载逻辑 | `build_skill_tools(skills: list[SkillLevel1], reader: SkillReader) -> list[BaseTool]` |
| `reader.py` | 懒加载 Skill 主体：给定 skill 路径，返回 `SkillLevel2 = (md_body: str, level3_paths: list[str])` | `read_skill(skill_dir: Path) -> SkillLevel2` |
| `models.py` | 三级 dataclass：`SkillLevel1(name, description, dir_path)` / `SkillLevel2(md_body, level3_paths)` / `SkillLevel3(file_path, content)`（Level 3 仅在模型调用工具时返回：文件操作由 `tools/filesystem.py`、内容搜索由 `FilesystemFileSearchMiddleware.glob_search/grep_search`、shell 执行由 `tools/commandline.py`） | — |

**Per-skill tool 的运行时行为**（伪代码）：
```python
def _make_load_skill_tool(level1: SkillLevel1, reader: SkillReader) -> BaseTool:
    @tool
    def load_skill_<slugify(level1.name)>() -> str:
        """{level1.description}
        
        Use this skill when {level1.name} matches user's task.
        Returns the full SKILL.md body (Level 2) and lists any supporting files (Level 3 paths).
        """
        level2 = reader.read_skill(level1.dir_path)
        paths = "\n".join(f"- {p}" for p in level2.level3_paths) or "(none)"
        return f"# Skill: {level1.name}\n\n{level2.md_body}\n\n## Supporting files (Level 3)\n{paths}"
    return load_skill_<slugify(level1.name)>
```

**与中间件协同**：`LLMToolSelectorMiddleware`（§1.5.4 录用第 8 项）会预先筛选 per-skill `load_skill_<name>` 工具——用户加 30+ Skill 时，模型只看到与当前查询最相关的 K 个工具，避免工具列表膨胀污染 context window。

#### 4.4.1 Agent Loop 状态机（简化）


**Saver 触发时机**（由 LangGraph `SqliteSaver` 在 super-step 结束自动调用 `put` / `put_writes`，受 `durability` 参数控制——`LangGraph_doc/persistence.md:264-277`）：

| 触发场景 | 写入点 | 备注 |
|---|---|---|
| 正常 `Respond`（最终态）| super-step 末尾 | 默认行为；`__end__` 之前 persist |
| 用户主动中断智能体执行（`KeyboardInterrupt`）| 当前 super-step 的 `put_writes`（pending） | 进程退出后 `durability="exit"` 兜底落盘 |
| v2 HITL 中断（`HumanInTheLoopMW.after_model`）| 中断触发瞬间 | 状态保留等待恢复 |
| 工具异常重试超限 → `Retry/Escalate` | super-step 末尾 | `ToolRetryMiddleware` 兜底 |
| `ModelCallLimitMW` 超调用上限 | super-step 末尾 | 防止失控循环用 |

> **v1 落地范围**：v1 仅前 3 类（最终响应 / 用户中断 / HITL 中断已留位但未启用）。第 4、5 类由 §1.5.4 录用中间件的兜底行为触发。

具体节点数与边以 `[D-xx]` 系列决策为准；任何修改图结构、State、节点数的变化需 `x+1`（§1.5.2）。

| `core.api.import_session(path, from_sqlite_path)` | 库 API | **F003 session 实现**（F003-P4，v1 留接口，落地列入 v1.x）；详见 §5.5.4.4 |
| `core.api.run_session(path, session_id)` | 库 API | **F004 run 实现**（v1 落地） |
| `donkey init / load / session / run` | cli 客户端（argparse）/ web 客户端 / gui 客户端 | 三端共用 `core.api` 库 API；详见 §5.5.6（F005 web / F006 gui 同样只走核心库 API） |
| MCP `MCPConfig` dict | JSON | 与 Claude Desktop / Cursor / Cline 通用 |
| Skills `SKILL.md` | Markdown + YAML frontmatter | 与 MDA / DeepAgents 通用 |

**v2 范围**：HITL中间件+前端适配。

> **`manifest.json` 与包内 `templates/manifest.json` 是两个不同的文件**：前者落在 **workspace 根**（D-01 workspace manifest，由 `core/workspace/manifest.py` 写入，含 4 字段）；后者落在 **donkey 安装包内**（`core/workspace/templates/manifest.json`，模板文件清单，驱动 `render_templates` 的幂等渲染）。
>
> **`providers/` 目录的三个要点**（详见 §4.6.2 与 `harness/report/大模型toml参数设计.md §7`）：
> 1. **一 provider 一文件**——文件名 stem **必须逐字符等于 provider_id**（小写 kebab-case，如 `minimax.toml` / `openai-compatible.toml`）；未知 stem → `ProviderTomlScopeError`（exit 11）；
> 2. **`enabled` 开关**——每个 provider 文件自带；`false` = **完全惰性**（不校验字段 / 不要求 `api_key` / 不参与连通性检查）；缺省 `true`；
> 3. **`providers/default.toml` 是保留名**——只存 `default_provider` + `default_model`；`default_model` 必须存在于 default provider 文件的 `[models]` 表（跨文件校验，exit 11）。
>
> **为什么不留在根目录一个 `provider.toml`**：单文件塞 26 个 provider 节 → 字段隔离了但文件没隔离（与 P-1 "per-provider 独立 schema" 自相矛盾），用户改一个 provider 要在几百行里翻，且被迫用 `api_key = "REPLACE_ME"` 占位符骗过静态检查。目录化后：**目录列表 = 支持哪些供应商**，provider 增删改 = 单文件 diff，错误可定位到文件。

**`donkey init` 自动生成的 3 个内置 `@tool`**（沿用 OpenCode 设计，作为 Skill Level 3 的标准访问通道）：

| 工具文件 | 暴露的工具函数 | 用途 | 关键实现约束 | 与中间件职责边界 |
|---|---|---|---|---|
| `tools/filesystem.py` | `read_file` / `write_file` / `copy_file` / `move_file` / `delete_file` / `list_dir` / `stat` | **文件操作**（读、写、复制、移动、删除、列目录、stat 元数据） | 路径白名单由用户自管（donkey 不强制）；写操作集中在 `tools/filesystem.py` 内 | **不提供** `glob_search` / `grep_search`——这俩由 `FilesystemFileSearchMiddleware` 接管（§1.5.4 录用 10 项之一）。两者**功能正交不重叠** |
| `tools/commandline.py` | `run_shell(command: str, timeout: int = 60) -> str` | 执行本地 shell 命令 | `subprocess.run([...], shell=False)`；显式 timeout 掐断；**不**走持久 shell session（避免 HITL 冲突，`内置工具应该自己实现还是调用中间件.md §2.3`） | 与 `ShellToolMiddleware` 互斥（持久 shell + HITL 冲突） |
| `tools/webfetch.py` | `fetch_url(url: str, method: str = "GET", headers: dict \| None = None, timeout: int = 30) -> str` | HTTP 请求 | `httpx` / `requests`；显式 timeout；不持久化 cookies | 与 MCP server 提供的 web 工具互斥（用户可二选一） |

**filesystem 职责分工（用户明确划界）**：

| 工具来源 | 职责 | 调用场景 |
|---|---|---|
| `FilesystemFileSearchMiddleware`（LangChain 中间件，引擎侧） | `glob_search` + `grep_search` | "找文件"、"找内容"（满足 90% 的搜索场景，ripgrep 后端高效） |
| `tools/filesystem.py`（workspace 内置 `@tool`，材料层） | 文件操作：read / write / copy / move / delete / list_dir / stat | "读这个文件"、"改那个文件" |

> **设计哲学**：这 3 个内置工具 + `FilesystemFileSearchMiddleware` 中间件共同构成 Skill Level 3 的完整访问通道——**功能正交、按场景选用**。用户**可以删除或重写**这 3 个内置工具（保留用户控制权），但 `FilesystemFileSearchMiddleware` 是引擎层收编项，删不掉。删除内置工具后，文件操作不可达，但 glob/grep 内容搜索仍可达；Level 1/2 始终由 per-skill tool 保障。详见 §1.2.4 三层模型容错分析表。

**显式排除**（workspace 内不出现）：

- ❌ `agent.py` / `main.py` / 任何 Python 入口
- ❌ `middleware/`（中间件属引擎侧）
- ❌ `connectors/` / `channel/` / `schedules/` / `evals/` / `identity/` / `sandbox/`
- ❌ `memory.py`（长期记忆文件）
- ❌ `mcp/*.py`（自定义 MCP server 代码）
- ❌ `.git/`（donkey 不自动 `git init`）

#### 4.6.2 核心配置字段

> **本节是 F002 load 阶段 `providers/` 目录校验的字段契约**：**一 provider 一文件**（`providers/<provider_id>.toml`）+ 1 个全局文件（`providers/default.toml`）；每个 provider 文件内含 `enabled` 开关 + `api_key` / `api_host` / `models` 子表 + 11 个通用字段（enabled / api_key / api_host / models / timeout / max_retries / temperature / max_tokens / top_p / stop / stream）；具体 per-provider 专属字段（如 `providers/anthropic.toml` 的 `[thinking]` / `providers/google.toml` 的 `[thinking_config]` / `providers/bedrock.toml` 的 `aws_*` 等）详见 `harness/report/大模型toml参数设计.md` §8.3。

**全局字段**（`providers/default.toml`）：

| 字段 | 类型 | 必填 | 备注 |
|---|---|---|---|
| `default_provider` | `str` | ✅ | provider_id（白名单 v1 = 26 家，见调研 §3.1；不在白名单 / v2+ 候选 / 永久黑名单 / 暂不支持清单（v1 后两者均空） → F002 load 抛 `ProviderTomlScopeError` 伞形 exit 11；详见调研 §3.0 Provider 治理原则）。**且必须指向一个存在的、`enabled = true` 的 `providers/<provider_id>.toml`**；指向缺失 / 已禁用的文件 → exit 11 |
| `default_model` | `str` | ✅ | 必须存在于 `providers/<default_provider>.toml` 的 `[models]` 子表中；否则 F002 `ProviderTomlMissingModelError`（exit 11）——**跨文件校验** |

**per-provider 文件通用字段**（在 `providers/openai.toml` / `providers/anthropic.toml` / `providers/qwen.toml` / ... 各自文件内声明；P-1 "per-provider 独立 schema" + P-6 "一 provider 一文件"）：

| 字段 | 类型 | 必填 | 备注 |
|---|---|---|---|
| `enabled` | `bool` | ❌（**缺省 `true`**） | **per-provider 开关**（P-7，对齐 Cherry Studio toggle）：`false` = 该文件**完全惰性**——不校验字段 / 不要求 `api_key` / 不参与连通性检查（**唯一例外**：文件名 stem 的 scope 校验仍执行，防拼错文件名） |
| `api_key` | `str` | ⚠️ **按 provider 分档**（调研结论见调研 §9.2） | TOML 明文，**绝不读环境变量**（P-2）。缺失映射为 `""`，**绝不返回 `None`**（否则触发 LangChain `_resolve_gateway_config` env var 回退，违反 P-2）。**A 档本地**（`ollama` / `meta`）：空 → **合法**，无 warning；**B 档端点属性未知**（`openai-compatible` / `xiaomi`）：空 → **合法 + warning**（端点是否校验鉴权未知；解析层填占位符 `"not-needed"`，因 openai SDK 拒绝空串）；**C 档云端 provider**（21 个）：空 → **硬错 exit 11**（`ProviderTomlFieldError`）——实测空 key 100% 在**构造 ChatModel 阶段**失败（`Missing credentials`），且报错文案指向 env var（违背 P-2），早失败比运行时炸更准；**`bedrock` 不使用 `api_key` 字段**（见下），其 `aws_secret_access_key` 等 4 个 `aws_*` 字段为空时同样 → **硬错 exit 11**。**三档判定只对 enabled 文件生效** |
| `api_host` | `str` (URL) \| `"default"` (仅 ollama) | ❌（**3 个例外必填**：`openai-compatible` / `meta` / `databricks`；其余 23 个选填） | 自定义 API 端点；Ollama 允许 `api_host = "default"` 等价于 `http://localhost:11434`（P-3）。**注意**：本项目用 `api_host`（与 Cherry Studio 对齐），不用 `base_url` |
| `models` | `table` | ✅ | 该 provider 注册的 model 列表；每个 model 是子节 `[models.model_id]`（**provider 作用域已由文件名确定**，不再嵌套 `[<provider>.models.*]`），可覆盖 provider 级 `temperature` / `max_tokens` 等 |
| `timeout` | `float` | ❌ | 请求超时秒数，默认 60 |
| `max_retries` | `int` | ❌ | 重试次数，默认 6（LangChain 全局） |
| `temperature` | `float` | ❌ | 全 provider 默认值；model 级可覆盖 |
| `max_tokens` | `int` | ❌ | 全 provider 默认值；model 级可覆盖 |
| `top_p` / `stop` / `stream` | 各 provider 类型不同 | ❌ | 通用采样 / 流式参数；provider 专属变体（如 Anthropic 的 `top_k`——**受限模型只接受 top_p=1 且禁传 top_k**）按 `harness/report/大模型toml参数设计.md §8.3` 校验；F002 load 阶段硬越界 → `ProviderTomlFieldValueError`（exit 11） |

**字段拼写错误 / 类型错 / 硬越界**（如 `temprature` / `api_key = 42` / `temperature = 3.0` / `api_host` 非 URL 格式）→ F002 load 抛 `ProviderTomlLoadError` 伞形类（exit 11）；子类见 README §3.2.1。**多文件布局下，错误消息必须携带文件路径**（`providers/openai.toml: ...`）——"是哪个文件错了"是用户修复的第一步。

**`providers/bedrock.toml` 特殊**：**不使用 `api_key` 字段**，改用 4 个独立字段 `aws_access_key_id` / `aws_secret_access_key` / `aws_region` / `aws_session_token`，由 `boto3.Session(...)` 显式构造（**不读** env var 与 `~/.aws/credentials`，与 P-2 完全对齐）。详见调研 §8.3 `providers/bedrock.toml`。

**`providers/meta.toml` / `providers/xiaomi.toml` 多平台路由**：保留 `api_key` + `api_host` + `routing_platform`（取 `ollama` / `replicate` / `together` / `fireworks` 等）；详见调研 §8.3。

**`providers/openai-compatible.toml` 元 provider**：`api_host` **必填**（与其它 provider 不同）。

**「零 enabled provider」= 硬错 exit 11**：`providers/` 下没有任何 `enabled = true` 的文件时，load 直接失败（`ProviderTomlFieldError`），错误消息给出三步配置指引（① 启用某个 provider → ② 填凭据 → ③ 填 `providers/default.toml`）。理由："启用哪个 provider / 用哪个 model 作默认"必须由用户决策（§5.5.3 奥卡姆原则）；代价见 §3.2.3 AC-1 静态口径修订。

**`api_key = ""` TOML loader 强约束**（P-2 + 调研 §9.1.1）：缺失 / `None` 一律映射为 `""`（空串），**绝不返回 `None`**——避免触发 LangChain `_resolve_gateway_config` 内部 `OPENAI_API_KEY` 等环境变量回退。

**未支持的 provider 处理**：

- 配置未识别 provider（任何不在 §3.1 白名单或 §3.5 v2+ 候选的 provider_id，含此前可能被列入"暂不支持清单"的 provider） → F002 load 抛 `ProviderTomlScopeError`（exit 11），错误信息引导"改用 [openai_compatible] 或在 issue 中提交 §3.1 升级评估"。v1 范围内永久黑名单与暂不支持清单当前均为空（详见调研 §3.0 / §3.3 / §13.4 / §14.7）。
- 配置 `[baidu]` / `[iflytek]` / `[sensetime]` → F002 load 抛 `ProviderTomlScopeError`（exit 11）——v2+ 候选（调研 §3.5），v1 留接口位，v2+ 启动自研（v2+ 候选清单 = 3 家）。
- v2+ 候选**不设独立错误类**——`baidu` / `iflytek` / `sensetime` 只是"**未排期开发**"（调研 §3.5），不是独立报错，与"白名单外 provider"同属 scope 判定且用户修复动作相同 → 统一归入 `ProviderTomlScopeError`（exit 11），**伞形下恒为 7 个子类**（见 README §3.2.1）。

**Skills / MCP 文件字段**：

| 文件 | 字段 | 必填 | 备注 |
|---|---|---|---|
| `mcp/mcp.json` | `mcpServers.<name>` | ❌ | 允许 `{"mcpServers": {}}` |
| `skills/<name>/SKILL.md` | frontmatter `name` | ✅ | **Level 1 必填**；与目录名一致（建议 `^[a-zA-Z0-9_]+$` snake_case） |
| `skills/<name>/SKILL.md` | frontmatter `description` | ✅ | **Level 1 必填**；自然语言描述触发条件；会作为 `load_skill_<name>` 工具的 description 主体（轻度改写 + 1 句触发短语） |
| `skills/<name>/SKILL.md` | frontmatter 下方 Markdown 主体 | ❌（强烈建议） | **Level 2 内容**；模型调用 `load_skill_<name>` 时返回 |
| `skills/<name>/SKILL.md` 之外的 `skills/<name>/*` 文件 | 任意扩展名 | ❌ | **Level 3 内容**；模型用 `tools/filesystem.py` 内置工具读取；常见：`reference/` `scripts/` `templates/` |

**Skills frontmatter schema 严格性**：
- 仅 `name` + `description` 两个字段必填（与 MDA / Anthropic Agent Skills 协议对齐）；
- **不允许**自定义额外字段（如 `when_to_use` / `version` / `tags` 等）——donkey v1 不解析它们，避免 schema 漂移；
- 若用户想加元信息，写在 Markdown 主体第一行（Level 2）即可，会随 `load_skill_<name>` 一起披露。

#### 4.6.3 数据生命周期

| 阶段 | 责任方 | 行为 |
|---|---|---|
| 采集 | `core` | 工具执行结果、模型回复、用户输入 |
| 模板预创建 | `donkey init`（F001-P2） | `memory/sessions.sqlite3`（**单文件双表**：SqliteSaver 自有 `checkpoints` / `writes` 表 + donkey 自管 `sessions_metadata` 表 + 索引；v1 schema 就绪） + `memory/store.sqlite3`（**v1 仅空文件**，schema 推迟 v3 SqliteStore 实施） + `memory/knowledge.sqlite3`（v1 仅空文件，schema 待向量引擎选型后正式化）；详见下文 "sessions.sqlite3 单文件双表设计" + "memory/ 模板边界" |
| 存储 | `SqliteSaver`（短期 message 历史） + `donkey.core`（会话元数据写入 `sessions_metadata`） | 已存在的 sqlite3 模板文件被持续读写 |
| 归档 | 用户 | workspace zip 备份；`memory/*.sqlite3` 可**选择性**带 / 不带（"运行数据可选择性导出"——即使是模板身份，导出策略仍可剔除）|
| 销毁（含 `--force`） | 用户 / `donkey init --force` | `donkey init --force` 等于"恢复出厂设置"——遍历 `templates/manifest.json` 含 `memory/*.sqlite3` 全部 → 删除 → schema builder 重建；SqliteSaver 历史 + `sessions_metadata` 元数据**一并清空**；用户备份：`cp memory/sessions.sqlite3 /tmp/backup.sqlite3` 后再 `--force` |
| 长期存储 | 自研 `SqliteStore`（v3） | `memory/store.sqlite3`（init 已预创建**空文件**，v1/v2 不挂 store；v3 SqliteStore 实施时由 Maintainer 添加 `store_items` 表建表 SQL） |
| 向量引擎（v3+ 候选） | 待选（sqlite-vec / faiss+sqlite） | `memory/knowledge.sqlite3`（init 已预创建空文件，schema 待选型） |

**`memory/ 模板边界`**：

- **`memory/` 目录与目录内全部三个 sqlite3 文件（`sessions.sqlite3` / `store.sqlite3` / `knowledge.sqlite3`）都是 donkey 模板**，由 `donkey init` 阶段预创建，纳入 `templates/manifest.json` 模板清单；
- 不在包内携带二进制 sqlite3 文件——`core/workspace/init.py::render_templates` 在 init 阶段**程序化构造**：
  - `memory/sessions.sqlite3`：构造 `SqliteSaver(conn)` 并调 `saver.setup()`（**实例方法**）创建 SqliteSaver 自身表（`checkpoints` / `writes`）+ donkey 自管 `sessions_metadata` 表 + 2 个索引（schema 在 v1 就绪，是 F002-P2 `SqliteSchemaError` 健康检查的**唯一**目标）；
  - `memory/store.sqlite3`：**v1 仅创建空 sqlite3 文件，不建任何表 / 索引**——schema 全部推迟到 v3 SqliteStore 实施时（届时 Maintainer 修改 F001-P2 §4.7.6 `build_store_sqlite` 添加 `store_items` 等建表 SQL + 同步 sessions_sqlite表结构一览.md §3 + §4.10 TD-02 路线图步骤 1）；v1/v2 donkey 本体不读 store.sqlite3（F004-P5 用 LangGraph `InMemoryStore` 顶替），空文件即正确契约；
  - `memory/knowledge.sqlite3`：**v1 仅创建空 sqlite3 文件，不预设 schema**——待 v3+ RAG 引擎（sqlite-vec / faiss+sqlite 等）选型后由 Maintainer 修改 `build_knowledge_sqlite` 添加建表 SQL；
- **`--force` 行为**（与"恢复出厂设置"语义对齐）：删 + 重建**全部模板文件**含 sqlite3；该语义与 §4.1.1 `donkey init --force` 行为一致；用户备份责任明确告知（写入 `memory/README.md`）；
- **"运行数据可选择性导出"**仍生效——sqlite3 文件虽属模板，导出 workspace zip 时仍可按需剔除（如客户端实现 `--include-memory` flag），"模板身份" ≠ "必须导出"；
- **退出码联动**：init 阶段 sqlite3 schema 健康；用户后续手工破坏（如手动编辑 / 误删表）触发 F002-P2 `SqliteSchemaError` (exit 16) ——这是该 exit code 现在唯一可靠的触发场景（init 阶段不再产生 schema 不健康文件）。

**`sessions.sqlite3` 单文件双表设计**：

- **同一 sqlite3 文件**承载两套表，避免文件数膨胀 / 备份成本翻倍 / 跨文件事务复杂性。
- **SqliteSaver 自有表**（`checkpoints` / `writes`，由 `langgraph-checkpoint-sqlite` 包管理）：
  - 短期 message 历史；
  - 主键语义：`thread_id` → 一组 checkpoint（含 parent 链）；
  - donkey 不修改、仅读 / 写。
- **`sessions_metadata` 表**（donkey 自管，**`donkey init` 阶段 schema builder 预创建**）：
  - 会话元数据：`thread_id` ↔ `title` 映射 + `created_at` / `updated_at` / `donkey_version` / `first_prompt`；
  - 用途：`donkey session list` / `remove --title X` 走此表，**不**用 SqliteSaver 状态反推（反推成本高、易错）；
  - 索引：`idx_sessions_metadata_title`（按 title 查）；`idx_sessions_metadata_updated_at`（按最近活动排序）；
  - **创建时机**：由 init 预创建（不是首次 `donkey session new` 时懒创建）——这样 sqlite3 文件在 init 后已成"就绪空 schema"，后续 `donkey session new` 是 INSERT，**不**需要 `CREATE TABLE IF NOT EXISTS` 分支路径。
- **两套表互不干扰**：`sessions_metadata` 表名加 `sessions_` 前缀 + SqliteSaver 文档化 schema 稳定（langgraph-checkpoint-sqlite 多年未变），命名冲突风险接近 0。
- **F002 load 阶段检查 `SqliteSchemaError` (exit 16)**：**5 项断言**同时通过——`PRAGMA table_info(checkpoints)` + `PRAGMA table_info(writes)` + `PRAGMA table_info(sessions_metadata)`（6 字段） + `sqlite_master` 查 `idx_sessions_metadata_title` / `idx_sessions_metadata_updated_at` + `PRAGMA integrity_check`；任一失败即抛（口径以 `harness/report/sessions_sqlite表结构一览.md` §7 为权威）。**触发场景**：init 后 schema 必健康，该 exit code 主要在用户手工破坏 sqlite3（含迁移拷贝污染 / 用户手动 rm 表）后触发。
- **`--force` 重建 sqlite3 的原子性**：`delete` + schema builder 重建在 Python 进程内串行执行；中途崩溃 → 下次 `donkey init`（或 `donkey load`）按幂等语义补齐（崩溃重建是幂等子路径的一部分，符合"未传 force = 缺失即补齐"原则）。

#### 4.6.4 数据治理

- **数据质量**：load 在 `donkey run` 前显式校验 sqlite3 schema、`providers/` 目录字段、Skills frontmatter（§5.5.3 检查清单 1-9 项）。
- **路径解析规则**（"绝对路径化"约束）：workspace 内的所有相对路径的引用以 workspace 绝对路径为唯一根（§1.2.2 P3）；进程 cwd / HOME / 属主隐藏目录约定均**不**作为 workspace 路径解析的隐含上下文。
- **安全分级**：`providers/` 下各 provider 文件的 `api_key` 字段（如 `providers/openai.toml` 的 `api_key` / `providers/anthropic.toml` 的 `api_key` / `providers/bedrock.toml` 的 `aws_secret_access_key` 等）视为高敏感，F002 load 异常自动脱敏（详见 §5.5.3）；donkey **绝不读** 环境变量（P-2），所有密钥仅从 TOML 明文加载。

> **v1 不引入 workspace 路径 basename 命名约束**：workspace 路径的 basename 允许任意字符（含 `-` / `.` / 空格 / Unicode 等），**不**强制遵循 Python 标识符命名规则。`donkey init` 与 `donkey load` 均不校验 basename 合法性。该决策避免为不存在的 v2/v3 假想场景（如 workspace-as-package 导入）写过早期约束；若 v2 引入对应需求，本节追加修订并同步 README §3.1 / §11 / verify 脚本。

#### TD-02 v3 SqliteStore 实施路线图

**为什么必须自研**（结论见 §4.2.1 长期记忆选型论证）：
- LangGraph 官方 9 种 Store 实现均无 SQLite（`Saver和Store.md §2.1`）；
- 官方"Saver + Store 同款配对"的三套现成方案（PostgreSQL / MongoDB / Redis，`Saver和Store.md §5.1`）均需外部服务进程，违反 §1.2.2 P2 "打包即走"；
- SQLite 是 donkey 唯一可接受的"零配置本地文件 + 跨会话长期记忆"组合。

**实施蓝本**：`Saver和Store.md §七 + §十二` 已给出 PostgresStore 的完整接口契约与自研要点速查。**官方 Postgres schema 蓝本**：`LangGraph_doc/stores.md:339-346` 的 `store_items` 推荐 schema（详见 sessions_sqlite表结构一览.md §3.3 第 0 行）：

```sql
CREATE TABLE store_items (
    namespace   TEXT[] NOT NULL,            -- SQLite 端口：以 JSON 数组字符串存
    key         TEXT   NOT NULL,
    value       JSONB  NOT NULL,            -- SQLite 端口：以 JSON TEXT + json_extract 适配
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (namespace, key)
);
CREATE INDEX ON store_items USING gin(namespace);  -- SQLite 端口：GIN→json_each + B-Tree
```

**SQLite 端口三处适配**：
1. **数组语法** → `namespace` 改为 JSON 字符串 `TEXT`（如 `'["alice","memories"]'`，参考 `LangGraph_doc/stores.md:73` "namespace may be serialized as list"）
2. **JSONB→TEXT** → `value` 用 `json.dumps` / `json.loads` 序列化 + `json_extract` 查询
3. **GIN 索引** → SQLite **无 GIN**——可走 `json_each` 展开为虚拟表 + B-Tree / FTS5 / 自定义 LIKE 前缀函数 / 触发器四条路，v3 启动期实测对比

实施要点：

1. **接口契约**：必实现 5 个 async 方法（`aput / aget / adelete / asearch / alist_namespaces`，`Saver和Store.md §7`）；
2. **数据模型**：主键 `(namespace, key)`；namespace 为 `tuple[str, ...]`，SQLite 端序列化为 JSON 字符串；值用 `json.dumps` / `json.loads` 序列化；
3. **索引**：namespace 列加前缀匹配索引（SQLite：FTS5 / 自定义 LIKE 前缀函数 / `json_each` 虚拟表；Postgres：GIN）；
4. **向量检索可选**：`query` 参数语义按 LangGraph `IndexConfig` 实现（可选，RAG 场景再启用）；
5. **参考实现**：`langgraph-checkpoint-postgres` 包内的 `PostgresStore`（`Saver和Store.md §五`）作为 SQL 方言移植源；本质是 PostgreSQL SQL → SQLite SQL 改写 + JSONB→TEXT + TEXT[]→JSON 字符串 三步适配。

**实施步骤**（v3 启动后按从简到难）：

| 步骤 | 工作量 | 依赖 |
|---|---|---|
| 1. 数据模型 + schema 落地（`store_items` 表 + namespace 索引） | 0.5 人周 | 无 |
| 2. `aput / aget / adelete / asearch / alist_namespaces` 5 个 async 方法实现 | 1.5 人周 | 步骤 1 |
| 3. 同步版本（`put / get / delete / search / list_namespaces`，可选但推荐） | 0.5 人周 | 步骤 2 |
| 4. 单元测试 + 集成测试（覆盖 prefix 匹配 / namespace tree / O(1) 主键查找 / DeltaChannel 反序列化兼容） | 1 人周 | 步骤 3 |
| 5. 与 LangGraph `BaseStore` 主版本对齐（跟 LangChain minor release 跑兼容性测试） | 0.5 人周 | 步骤 4 |
| 6. donkey `core/memory/store.py` 包装（与现有 `core/memory/saver.py` 对齐 API 风格） + donkey run / session 接入 | 0.5 人周 | 步骤 5 |
| 7. F002 load 阶段的"过期检查"（load 9 项检查中加入 store.sqlite3 schema 健康检查） | 0.5 人周 | 步骤 6 |
| **合计** | **~5 人周** | |

**与 LangChain 主线兼容策略**：
- 自研 Store 显式实现 `BaseStore` 接口（继承 `langgraph.store.base.BaseStore`）；
- 跟 LangChain 1.x 主线 minor release，定期跑兼容性测试（`Saver和Store.md §12` 的接口契约作为合规检查清单）；
- 若 LangGraph 官方未来推出官方 SQLite Store，donkey 自研版本降级为兼容层（参考 §8.3 风险应对"接受 + 转移"）。

**v1/v2 临时方案**（不引入技术债）：
- `create_agent(..., store=InMemoryStore())`：v1/v2 直接用 LangGraph 自带 `InMemoryStore`，接受"进程重启即丢"（v1 不需要长期记忆，v2 HITL 主要用短期）；
- 仅在 v3 触发条件（用户主动开 Scheduler + 长期记忆特性）时启用自研 SqliteStore。

### 5.2 阶段划分与里程碑

#### 5.2.1 Feature 与 Phase 划分原理

> **Feature 定义**（Feature = **一级命令**；F 编号与 §3.2.1 功能模块表一一对应，全文唯一）：
>
> | 编号 | 一级命令 | 核心库 API |
> |---|---|---|
> | **F001** | `donkey init` | `init_workspace(path, name, force)` |
> | **F002** | `donkey load` | `load_workspace(path) -> LoadResult` |
> | **F003** | `donkey session` | `list_sessions / new_session / remove_session / import_session` |
> | **F004** | `donkey run` | `run_session(path, session_id)` |
> | **F005** | `donkey web` | （前端，复用 F001–F004 核心 API） |
> | **F006** | `donkey gui` | （前端，复用 F001–F004 核心 API） |

> **Phase 定义**：Phase 是 Feature 内部更细的实施阶段。**Phase 不能再按一级命令划分**（一级命令已被 Feature 锁死）；Phase 必须按以下两条规则二选一进行切分。
>
> **切分规则**：
>
> | 规则 | 适用 Feature | 切分单位 | 理由 |
> |---|---|---|---|
> | **规则 A：按二级命令切** | 含二级命令的 Feature（如 F003 `donkey session list / new / remove / import`） | 每个二级命令 = 一个 Phase | 二级命令是用户可独立调用的原子入口，CI/脚本可直接调用验证；Phase 退出条件可等价于"该二级命令在边界用例下 exit code 全在预期段位" |
> | **规则 B：按退出码段位切** | 无二级命令的 Feature（如 F001 `donkey init`、F002 `donkey load`、F004 `donkey run`） | 每 N 个连续退出码 = 一个 Phase（N 由该 Feature 的失败场景数量决定） | 退出码本身已是可量化的"失败场景分类"，按段位切 Phase 让失败场景与 Phase 1:1 对应，避免主观形容词 |
>
> **每设计一个 Phase 必带三要素**：
>
> 1. **入口条件（Entry Gate）**：前置 Phase 的退出条件必须全部满足——可执行命令/测试验证通过；
> 2. **异常退出码（Exit Code）**：该 Phase 失败时返回的 exit code（落在该 Feature 段位内，段位表见 §5.5.3；具体码值到触发场景的映射在各自 Feature spec 中规定）；
> 3. **退出条件（Exit Gate）**：可执行、可验证的硬指标——由一段**可执行命令/测试**验证（参考 §5.5 验证脚本模式），不依赖 Maintainer 主观判断。
>
> **可量化保障**：
> - 任何 Phase 的退出条件必须能被自动验证脚本（如 `verify_phase_<f>_<n>.py`）跑出 PASS/FAIL；
> - 退出条件失败 = 该 Phase 未完成 = 禁止进入下一 Phase；
> - Maintainer 不能凭"代码看起来差不多"宣布 Phase 完成。
>
> **跨 Feature 滚动**：同一时间段内可同时推进多个 Feature 的同 Phase 任务，但每个 Feature 内部 Phase 严格串行。
>
> **立项书 §5.5 展开各 Feature 的 Phase 切分与码值分配**（§5.5.1~§5.5.6 的 Phase 表是**码值区间的权威源**）；具体 Phase 的 Error class 逐条映射、退出条件、提示词文件在 README §3 一览总表 + §12 提示词文件落地约定中规定。Phase 的精确定义（= dev unit，1 次 `/speckit.specify` 闭环，不与 exit code 子段或 Error class 分组混用）由 README §1.5 给出；提示词文件命名（1 Phase = 1 提示词文件 = 1 次闭环，格式 `featurexxx_phasexxx_<phase_name>.md`）见 README §12。
>
> **Phase 切分示例**（仅作原理示意，具体编号/退出码以 Feature spec 为准）：
>
> | Feature | 二级命令 / 段位 | 切分结果 |
> |---|---|---|
> | F001 init | 无二级命令 | 按退出码段位切：phase 1 = exit 1-2（path / permission 类），phase 2 = exit 3（template 类），phase 3 = exit 4（builtin tool 类） |
> | F002 load | 无二级命令 | 按退出码段位切：phase 1 = exit 11-13（静态检查 1-3 —— **`providers/` 目录全加载 / `mcp/mcp.json` 解析 / `SKILL.md` frontmatter**；exit 11 为 `ProviderTomlLoadError` 伞形码，覆盖 `providers/` 加载阶段所有子错误），phase 2 = exit 14-16（静态检查 4 + 动态检查 1-2 —— `instruction.md` / 模型连通 / sqlite schema），phase 3 = exit 17-19（动态检查 3-5 —— tools / skills / mcp 加载，20 预留） |

#### 5.5.1 F001 `donkey init`（v0.1.0）

F001 没有二级命令，Phase 切分按 §5.2.1 规则 B（按退出码段位切）。F001 段位 = exit `1-10`（见 §5.5.3 段位分配总表），具体 Phase 编号与码值到触发场景的映射在各自 F001 spec 中规定。

**F001 整体范围**：

- `core.api.init_workspace(path, name, force)` 的库 API 签名稳定（详见 §4.5）；
- workspace 目录结构按 §4.6.1 落地：五大必填目录（`tools/` / `mcp/` / `skills/` / `memory/` / **`providers/`**）+ 必填文件（`instruction.md` / **`providers/default.toml`** / `mcp/mcp.json` / `skills/example/SKILL.md`）；
- 三大内置工具模板（`tools/filesystem.py` / `tools/commandline.py` / `tools/webfetch.py`）作为 Skill Level 3 的标准访问通道（沿用 OpenCode 设计，详见 §1.2.4 与 §4.6.1）；
- 幂等 create/check、已有文件保护（`--force` 标志）；
- exit code 段位 1-10：F001 域 v1 **实装 4 码**（1 `PathNotFoundError` / 2 `PathPermissionError` / 3 `TemplateGenerationError` / 4 `BuiltinToolGenerationError`，连号使用），**5-10 预留**给 v1.x 试运行期新发现的错误（不预先造死错误类凑数）。

**关键实现约束**：

- `commandline.py` 走 `subprocess.run(shell=False, timeout=...)`，**不**走持久 shell session（避免与未来 v2 HITL 冲突，详见 §1.5.5）；
- `webfetch.py` 走 `httpx`/`requests` 同步调用 + 显式 timeout；
- `filesystem.py` **不**包含 glob/grep（这俩由 §1.5.4 录用的 `FilesystemFileSearchMiddleware` 中间件提供，引擎层收编项）；
- init 阶段生成的三大内置工具为**模板文件**，用户可删除/重写；删除后 Level 3 文件操作不可达，但 Level 1/2 由 per-skill tool 保障（详见 §1.2.4 三层模型容错分析表）。

**验收引用**：

- 业务验收：AC-3（init 幂等，§3.2.3）；
- 技术验收：F001 域 exit code 与段位表完全一致（§5.5.3）；

**冗余性设计原则**：
- 每个段位预留 **10 个码值**，吸收 v1.x 试运行期间发现的额外失败场景；
- 跨子命令冲突检测：donkey.core 内部 `exit_code` 计算函数 `compute_exit_code(check_results)` 自动按"子命令段位 → 触发子段位"映射，确保 CI/脚本能根据 exit code 段位判断失败大类，无需翻查具体码值；
- `0` 是唯一正常返回码；任何 `> 0` 都视为失败；
- `201+` 留给未来大版本（v2 / v3 / v4）——每个大版本占 100 个码值（含 1 个正常返回）。

**多错误优先级规则**：load 检查按本节 9 项检查清单顺序逐项执行，**遇到第一个 hard error 立即返回**——`exit_code` 取该错误的码值（位于段位内具体值），不累积多错误码。

**`warning` 不计入失败判定**：warning 状态（如 `providers/*.toml` 的 `temperature` 软越界 / `providers/openai-compatible.toml` 的空 `api_key` 等）不触发 non-zero exit code——CI 可配置 `--strict-warnings` 标志（v2 候选）将 warning 升级为 error。**注意**：donkey **不读**环境变量（P-2），所以"env var 已设 → 静默回退"这类 warning 不存在；**云端 provider 的空 `api_key` 不是 warning 而是硬错 exit 11**（实测失败在**构造期**而非运行时 401；本地端点（Ollama / vLLM / LiteLLM）本就不校验鉴权 → 按 provider 分三档，详见调研 §9.2 与 README §3.2.1）。

#### 5.5.4 F003 `donkey session`（v1.0）

F003 含 4 个二级命令，Phase 切分按 §5.2.1 规则 A（按二级命令切）——**每个二级命令 = 一个 Phase**：

| Phase（= 二级命令） | 段位 | 入口条件 | 退出条件（可执行验证） |
|---|---|---|---|
| F003-P1 = `donkey session list` | exit 21-22 | F002 load 9 项全部通过 | 1) 空 workspace exit 0 输出"无会话"；2) N 个会话按标题列表化输出；3) thread_id 不外露；4) sqlite3 锁等待 ≤ 1s |
| F003-P2 = `donkey session new` | exit 23-25 | F003-P1 退出条件通过 | 1) `donkey session new` exit 0 落 1 条 sqlite3 记录；2) `--first-prompt` 触发 LLM 总结 timeout ≤ 5s；3) 总结失败 / 超时 → **回退为首轮 prompt 前 20 字**（**绝不**回退成"无标题会话"），session 仍创建成功（exit 0）；4) 重复 100 次不报 sqlite 锁 |
| F003-P3 = `donkey session remove` | exit 26-27 | F003-P2 退出条件通过 | 1) 按 title 定位 thread 物理删除全部 checkpoint；2) 不存在的 title exit 段位 26-27 内错误码；3) 同一 workspace 重复 100 次 rm 不报文件锁 |
| F003-P4 = `donkey session import` | exit 28-30 | F003-P3 退出条件通过 | 1) 从外部 sqlite3 文件导入历史会话；2) 导入失败/格式错误 exit 段位 28-30 内错误码；3) 导入后 list 能看到导入的会话（标题 + thread_id 一致） |

> **F003 段位空间说明**：F003 段位 = exit `21-30`（共 10 码），由 4 个二级命令的 Error class 占用（list 2 + new 3 + remove 2 + import 3）。**`exit 0` 是全子命令唯一的正常返回码**（宪法 §4.4），本段位**不**为每个二级命令预留"正常码位"——段内 10 码全部是错误码（21-27 v1 实装 + 28-30 = import 的 v1.x 留接口位），**无通用错误预留码**。

**会话标题 = 唯一对外标识**，thread_id 仅作内部引用。F003 各 Phase 共同遵守此约定。

##### 5.5.4.1 F003-P1 = `donkey session list`

- **命令**：`donkey session list <PATH>` —— 扫描 `memory/sessions.sqlite3` 内所有会话，按**标题**展示（不暴露 thread_id）。标题为"无标题会话"时附占位符前缀便于识别。
- **库 API**：`core.api.list_sessions(path) -> list[SessionMeta]`。
- **段位**：exit `21-22`（详见 §5.5.3 段位表 + F003 spec）。

##### 5.5.4.2 F003-P2 = `donkey session new`

- **命令**：`donkey session import <PATH> --from <sqlite_file>` —— 从外部 sqlite 文件导入历史会话。

- **段位**：exit `28-30`（v1 留接口，落地列入 v1.x；详见 §5.5.3 段位表 + F003 spec）。

##### 5.5.4.5 `core.api.new_session` 标题总结机制（F003-P2 内部细节）

**为什么不在图内**（与 §1.2.3 + §4.4.2 一致）：

1. **职责分离**：标题是"会话显示层"，Agent Loop 是"推理图"，两者责任不同。把显示层挂在推理图里会让标题相关变更（字数限制、fallback 策略、多语言模板）触发 `x+1` 版本号抖动，与 §1.5.2 边界定义冲突。
2. **错误语义独立**：标题总结**不**该阻塞 session 创建（失败时回退为首轮 prompt 前 20 字，见下方"标题回退的三条硬规则"）。图内中间件抛错会触发 `interrupt` 整图终止；业务函数里 try/except 比中间件里干净。
3. **测试轻量**：测 `core.api.new_session` 一次 sqlite3 写入即可，不必跑整图。
4. **三端零适配**：CLI / Web / GUI 三个客户端**一行代码不用改**——它们都已经在调 `core.api.new_session(path, first_prompt=...)`。

**契约**：

```python
def new_session(
    path: Path,
    first_prompt: str | None = None,
    title: str | None = None,
) -> SessionMeta:
    """新建会话；可选首轮 prompt 用于标题总结。

    内部流程：
      0. 假定 memory/sessions.sqlite3 已由 donkey init 阶段 schema builder 预创建
         含 SqliteSaver 表（checkpoints / writes）+ sessions_metadata 表 + 索引；
         本函数不重复 CREATE TABLE IF NOT EXISTS（那会掩盖 init 缺失 / --force 后被外部破坏 等异常）。
      1. 分配 thread_id（UUID）
      2. 决定标题（**N-10**）——**三段式，先定标题再落库**：
         - 用户显式传 title:            用 title（≤ 20 字截断）
         - 用户传 first_prompt:
             ① 调 init_chat_model 总结 ≤ 20 字（超时 ≤ 5s）
             ② 总结成功  → 用总结结果
             ③ 总结失败 / 超时 / 空返回 → **回退为首轮 prompt 的前 20 字**
                （**绝不**回退成"无标题会话"）
         - 都不传:                      默认 "无标题会话"
      3. **落库（一次即可，两表各自写）**：
         - SqliteSaver 写 initial checkpoint（短期 message 历史）
         - INSERT INTO sessions_metadata（thread_id ↔ title 映射 + 元数据）
         （两者与 SqliteSaver history 解耦；标题在第 2 步已定稿，落库时不再变更）
    返回 SessionMeta(thread_id, title)

    标题总结失败**不**抛异常；session 创建本身始终成功（exit 0）。
    """
```

**标题回退的三条硬规则**（N-10 的可验证形式）：

| # | 规则 | 理由 |
|---|---|---|
| 1 | **给了 `first_prompt` 的会话，标题永远不是"无标题会话"** | 绝不允许出现"Agent Loop 都已经启动了，标题还是占位符"的状态——会话列表按标题展示，占位符标题会让用户无法区分会话 |
| 2 | **回退顺序：LLM 总结 → 首轮 prompt 前 20 字**（**不是**"无标题会话"） | prompt 前 20 字天然是"这次会话在聊什么"的最佳近似，且零成本、零延迟、零外部依赖 |
| 3 | **标题必须在 `new_session` 内、落库前定稿** | 标题是"会话显示层"（N-09 对外标识），必须在 Agent Loop 启动**之前**写进 `sessions_metadata`——不能等到第一轮对话结束后再补 |

**段位空间**：标题总结内部的 LLM 故障**不影响** `donkey session new` 的 exit code（回退到 prompt 前 20 字，session 创建成功，exit 0；仅在三端日志/UI 上提示"标题由首轮 prompt 截取生成"）。`donkey` 全子命令段位表（§5.5.3）中此场景**无新增段位**——因为它不外显为用户失败。F003-P2 的 3 个码值（23 / 24 / 25）分别对应 `SessionNewSqliteError`（`sessions_metadata` 写失败）/ `SessionNewLockError`（锁等待超时）/ `SessionNewCheckpointError`（SqliteSaver 写 initial checkpoint 失败）。

| Feature | 客户端 | 时间窗 | 主要工作 | 与后端关系 |

| F006 | **GUI = Electron 包壳** | T0+39w ~ T0+42w | 用 Electron 把 web build 包成桌面应用；补充原生能力胶水代码（菜单栏、文件对话框、通知、剪贴板） | **复用 Web 100% 渲染层** |

> **关键设计判断**：从 Web 到 GUI 不是"开发第三种客户端"，而是"Web 的桌面打包"。业界惯例（VSCode / Cursor / Claude Desktop / Continue.dev / Slack / Discord / Notion / Figma 均采用此架构）。Electron 内置 Chromium → **渲染层 100% 一致**，Web 与 GUI 共用同一份前端代码与同一组 e2e 测试。

**GUI 选型决策**：**F005 web 完成之前**敲定 GUI 选型为 **Electron**（不是 Tauri / Qt），关联时间窗 T0+34w ~ T0+38w。依据：
- 与 Web 同源（Chromium 渲染），包壳工作量最小（~2 人周）
- 工具链最成熟（electron-builder / electron-forge），社区资源最丰富
- donkey 是对话型 IDE（非 GPU 密集型 / 非秒级冷启场景），Electron 的 bundle 大、内存高劣势不触发
- Tauri（Rust 后端）虽更轻，但要求重新学习工具链，对单人项目 ROI 差
- Qt（C++/QML）虽原生最快，但与 Web 完全无关，违反 §1.5.3 "Web → GUI" 路径

**三端共用 donkey.core**：三种客户端均通过 `donkey.core.api` 暴露的库 API（`init_workspace` / `load_workspace` / `list_sessions` / `new_session` / `remove_session` / `import_session` / `run_session`）调用业务逻辑，不重复实现。

- **分层约束**（§4.1.1）：客户端层**不**直接 `import langchain` / `langgraph` / `sqlite3`；所有 LangChain / LangGraph / sqlite3 调用封在 `donkey/core/` 内。GUI 客户端的 Electron 主进程同样禁止 import 业务库——只做窗口管理 / IPC 桥接 / 原生 API 暴露。
- **功能对等**：每种客户端都覆盖同一组最小子命令集 —— `init` / `load` / `session {list,new,remove,import}` / `run`；任何客户端都不允许出现"功能仅 cli 独有"的情况。（二级命令名以 `remove` 为准，见 §5.5.4.3）
- **UI 复杂度**：cli 走 argparse + stdout；web 走浏览器；gui 走 Electron 壳。v1 客户端 UI 不追求花哨，能稳定跑完最小流程即可。
- **测试**：e2e **两套**——（a）CLI/Web 共享 pytest 用例（启动方式不同）；（b）GUI 仅验证 Electron 壳启动 + 渲染层与 Web 一致（不重复业务测试，靠 Web 测试覆盖）。
- **依赖**：Web 与 GUI 共一份 `package.json` + Web build pipeline；Electron 仅在 GUI 端追加 `electron` / `electron-builder` 两个 dev 依赖。

### 5.6 信任与安全预检（v1）

- `tools/` 内 `@tool` 函数白名单：用户自管，load 不深查。
- `mcp/mcp.json` 内 server 来源：用户自管。
- `providers/*.toml` 的 `api_key`（**仅 `enabled` 的 provider 文件参与判定**）：**按 provider 分三档 + bedrock 例外**（调研结论详见调研 §9.2）——A 档本地（`ollama` / `meta`）缺失或为空**合法**（无 warning）；B 档端点属性未知（`openai-compatible` / `xiaomi`）缺失或为空**合法 + warning**（端点是否校验鉴权未知，解析层填占位符 `"not-needed"`）；C 档云端 provider（21 个）缺失或为空 → **硬错 exit 11**（`ProviderTomlFieldError`）；`bedrock` 不用 `api_key`，其 `aws_secret_access_key` 等 4 个 `aws_*` 字段为空时同样 → **硬错 exit 11**；另含 `api_host` URL 格式硬校验（详见 `harness/report/大模型toml参数设计.md §7.3` / §9.2 + 立项书 §4.6.2）。

| R-07 | 自研 SqliteStore（v3）与 LangGraph `BaseStore` 主版本契约脱钩 | 中 | 中 | 中 | Maintainer | 缓解中（v3 启动期重点跟进） |

### 附录 F 关键决策记录（ADR）

> **宪法（核心不可妥协决策）**

- **N-01**：workspace 中禁止出现 `agent.py` 或任何 Python 入口文件。
- **N-02**：禁止 subagent / 子智能体相关目录或字段（`agent = 人`）。
- **N-03**：`donkey.core` 禁止 import 任何 client。
- **N-04**：`cli_client` 禁止直接 import `langchain` / `langgraph` / `sqlite3`。
- **N-05**：`donkey.core` 禁止 import `argparse` / `sys.argv` / `click` / `typer`。
- **N-06**：`donkey load` 失败时 exit code 非 0，但不修改 workspace 中任何文件。具体码值见 §5.5.3 段位分配总表（11-20 段位）。
- **N-07**：`donkey load` 不依赖 `init`：用户可能跳过 `init` 直接跑 load，此时 load 应继续检测并清晰报告"未 init"。
- **N-08**：`donkey load` 退出码空间 `11-20`，与 `init` `1-10` 严格不重叠。`donkey` 全子命令段位划分见 §5.5.3 段位分配总表。
- **N-09**：`donkey session` 的对外标识是标题，thread_id 仅作内部引用。
- **N-10**：`donkey session new` 默认标题"无标题会话"；若同时给了首轮 prompt，**必须**在 `core.api.new_session` **内部**由 LLM 总结 ≤ 20 字标题并写回 sqlite3；**严禁**实现为 `before_agent` 中间件（即**不**进 Agent Loop 图，**不**新增 LangGraph 节点，**不**触发 §1.5.2 的 `x+1`）。详见 §5.5.4.5。
- **N-11**：v1 必须同时交付 cli / web / gui 三种客户端，缺一不可（§1.5.3 / §3.2.1 / §5.5.6）。**开发顺序**（与 §5.2 阶段划分 + §5.5.6 一致）：CLI 在 **F001–F004** 期间渐进补齐（最薄壳，仅调 `donkey.core.api`）→ Web 主攻 v1 UI（最重，~200 人时）→ GUI = Electron 包壳（最轻，~40 人时，100% 复用 Web 渲染层）。三端在 v1 发布日**并列齐备**，但开发期按 CLI → Web → GUI 顺序推进；不允许 Web 未完成就启动 GUI（违反洋葱架构），也不允许跳过 CLI 直接做 Web（违反 §4.1.1 库 API 必须先稳定的约束）。
- **N-12**：禁止使用任何 LangSmith 相关代码（Cloud / Studio UI / Tracing / Deployment / Hub / `langchain[langsmith]` extras / `LANGSMITH_TRACING` 等环境变量）；禁止 `import langsmith` 或任何 `langsmith.*` 子包（包括用于"诊断智能体 / 打印运行轨迹"等用途）——智能体诊断统一走 `donkey.core` 自有输出（stdout 日志 / 事件流 / 后续自研 tracer），受 `harness/report/全开源最佳实践.md` §0 约束。

> **关键设计决策 [D-xx]**

- **[D-01]**：一个 workspace 目录 = 一个 Agent；workspace 自带 manifest。
- **[D-02]**：依赖与配置随 workspace 走；运行数据可选择性导出。
- **[D-03]**：workspace 有格式版本号，donkey 升级时提供迁移路径。
- **[D-04]**：`cli` / `web` / `gui` 客户端禁止直接 import `langchain` / `langgraph` / `sqlite3`（N-04）。
- **[D-05]**：`donkey init` 在 init 阶段**程序化构造** sqlite3 schema（非携带二进制模板）——`sessions.sqlite3` = `SqliteSaver(conn).setup()` + donkey 自管 `sessions_metadata` 表；`store.sqlite3` / `knowledge.sqlite3` v1 仅空文件占位，schema 推迟 v3。
- **[D-06]**：donkey 不依赖 LangSmith 任何形态；用 `stream_mode` + 自定义 Middleware + 标准 OpenTelemetry / Logging 替代（N-12）。
- **[D-07]**：Skills frontmatter 严格仅 `name` + `description` 两必填字段，不允许自定义字段。
- **[D-08]**：客户端三端（cli / web / gui）共用 `donkey.core.api` 库 API，不重复实现业务逻辑；开发顺序 CLI → Web → GUI（N-11）。
- **[D-09]**：donkey v1 不依赖 `deepagents` 包；Skills 加载器自研。
- **[D-10]**：workspace 内禁止出现 `agent.py` / `main.py` 或任何 Python 入口文件（创建 agent 的唯一官方入口 = `donkey.core.api.create_agent`）（N-01）。
- **[D-11]**：`store.sqlite3` / `knowledge.sqlite3` v1 仅占位空文件——不建占位表、不挂 store、donkey 本体不读；v3 SqliteStore 由 Maintainer 启动时实施（§4.10 TD-02）。
- **[D-12]**：F002 load 硬检查失败 → exit code ≠ 0，但不修改 workspace 中任何文件（N-06）。
- **[D-13]**：提供 fork 指南（配置边界、适配层说明、扩展点清单）。
- **[D-14]**：**AC-1 的出厂态豁免**——`donkey load` 的"100% 通过"口径 = **配置完成后**的 workspace；出厂态（26 个 stub 全 `enabled = false`、零 enabled provider）豁免，必然报 exit 11 + 三步配置指引；**零 enabled 不得降级为 warning**（会让动态检查无模型可测）。
- **[D-15]**：**subagent 永不纳入**——宪法 N-02"agent = 人"，任何版本号都不为其预留功能位（§1.5.3 版本表 / §5.4 甘特图均不得出现 subagent 交付物）。
- **[D-16]**：**v1 LLM 接入零自研解析层**——26 个 provider 全部复用 LangChain 官方类（唯一抽象 = `ReusableProvider`）；`provider_id` → LangChain 类的翻译由 donkey facade 完成（**禁止**直接把 TOML 的 `default_provider` 喂 `init_chat_model`）；donkey 在解析层的唯一职责是**配置层严格校验**（exit 11 伞形）；配置布局 = `providers/` 目录 + 一 provider 一文件 + `enabled` 开关。
